# 스윙바이 퍼즐 게임 — Claude Code 개발 계획 (v4, Godot)

> 이 문서는 Claude Code에게 주는 개발 지시서다. 프로젝트 루트의 `docs/PLAN.md`로 저장하고, 마일스톤 단위로 작업을 요청한다. v2에서 스테이지 구성(§7)과 제작 파이프라인(§8)을, v3에서 광고와 힌트(§14), 플랫폼과 스토어 출시(§15)를 추가했다. **v4에서 구현 스택을 TypeScript/Canvas/Capacitor에서 Godot 4 + GDScript로 교체했다**(§2, §21 참조). 물리 코어와 레벨 데이터는 사전에 시뮬레이션으로 검증을 마친 참조 구현이 부록에 포함되어 있으며, **숫자와 공식을 임의로 바꾸지 않는다.** 문서 안의 `§8.4` 같은 표기는 이 문서의 절 번호이고, `2장`, `2-3` 같은 표기는 게임의 장과 단계를 뜻한다.

---

## 0. Claude Code 작업 규칙

1. 마일스톤(§17) 순서대로 진행한다. 한 마일스톤이 끝나면 **멈추고**, 무엇을 만들었는지와 폰에서 확인하는 방법을 요약한 뒤 다음 지시를 기다린다.
2. 각 마일스톤 시작 시 계획을 먼저 짧게 제시하고, 이 문서와 다른 판단이 필요하면 구현 전에 이유와 함께 묻는다.
3. `core/`, `tools_shared/`, `monetization/`은 **노드(`Node`)·씬·`Vector2`·렌더링 API를 절대 쓰지 않는** 순수 GDScript로 유지한다. 게임과 검증 도구가 같은 코드를 공유하기 때문이다. 이유는 §2.1에 있다.
4. 물리 상수, 중력 공식, 충돌 판정, 레벨 수치를 바꾸는 변경은 반드시 레벨 회귀 테스트(§16.5)를 통과해야 한다. 테스트 기준값을 수정해서 통과시키지 않는다.
5. 마일스톤마다 git 커밋한다. 커밋 메시지는 한국어로 `M2: 조준·발사 입력 구현` 형식.
6. 사용자에게 보이는 문구는 모두 한국어이며 §13의 문구를 그대로 쓴다.
7. 스테이지 좌표를 손으로 작성하거나 추측으로 수정하지 않는다. 새 단계는 반드시 생성기(§8.4) 또는 사용자의 에디터 작업으로 만들고 검증기(§8.5)를 통과시킨다.
8. 광고 단위 ID, 서명 키, 스토어 계정 정보는 코드와 저장소에 넣지 않는다(§14.2, §15.5).
9. 루트에 `CLAUDE.md`를 만들어 이 §0 규칙, 명령어, 폴더 구조 요약, **고정한 Godot·애드온 버전**을 기록한다.

## 1. 게임 개요

- **장르:** 캐주얼 물리 퍼즐, 모바일 세로 화면, 한 손가락 조작.
- **목표:** 우주선을 한 번 발사해, 행성 중력을 이용한 스윙바이로 궤도를 꺾어 목적지에 도착시킨다.
- **플레이어가 정하는 것:** 우주선이 발사대 행성 표면의 어느 자리에 설지(그 자리의 법선이 곧 이륙 방향이다), 그리고 움직이는 행성이 있는 단계에서는 발사 시점. 발사 속도는 단계마다 고정이며, 발사 후에는 조작하지 않는다.
- **게임오버:** 행성 충돌, 블랙홀 흡수, 외계인 포격 피격, 외계인 우주선 충돌, 소행성 충돌, 맵 경계 충돌, 30초 안에 미도착.
- **그래픽:** 1979년 아케이드 〈아스테로이드〉 풍 벡터 선화. 검은 배경에 발광하는 선으로만 그린다.
- **출시:** 구글 플레이 우선, 이후 앱스토어. Godot 4로 만들고 엔진의 네이티브 익스포트로 앱을 만든다(§15).
- **수익:** 광고. 보상형 광고(힌트·건너뛰기) 중심, 전면 광고는 엄격히 제한(§14).
- **분량:** 초반부 5장 40단계(장마다 새 요소 도입) + 후반부 생성 단계(장당 10단계). §7 참조.
- **화면 구성:** 맵이 화면보다 크면 스크롤되며, 구석에 미니맵이 나타난다. 행성과 블랙홀은 중력 범위를 시각 효과로 표시한다.

### 1.1 설계 근거 (사전 검증에서 확인한 사실)

- 실제 역제곱 중력을 쓰면 성공 발사각 폭이 0.25~1°로 좁아 터치로는 운에 가깝다. 그래서 **중력은 표시된 중력 범위 안에서만 작용하고, 중심에서 강하며 경계에서 0이 되는 모델**(§5.3)을 채택했다. 이 모델로 성공 폭이 7~11°가 된다. "원 밖은 안전, 원 안은 끌린다"는 규칙이 화면에 그대로 보인다는 장점도 있다.
- 움직이는 행성이 주된 스윙바이를 맡으면 결과가 혼돈적이 된다. 그래서 큰 방향 전환은 고정 행성이 맡고, 공전 행성은 중력이 약한 **타이밍 관문** 역할만 한다.

| 저장 | `user://` + `FileAccess` | 엔진 기본, 플러그인 불필요 |

### 2.1 정밀도 규칙 (중요)

Godot 4의 `Vector2`는 성분이 **32비트 float**(`real_t`)다. 반면 GDScript의 맨 `float` 변수는 **64비트 double**이며, 부록 A·B의 검증값(§6.2의 성공 구간, §8.5의 `clearance`)은 double 기준으로 얻은 값이다.

- **시뮬레이션 상태(우주선 위치·속도, 중력원 위치, 총알 위치)는 `Vector2`에 담지 않는다.** 반드시 `x: float`, `y: float`처럼 분리된 `float` 변수나 `PackedFloat64Array`로 다룬다.
- `core/`, `tools_shared/` 안에서는 `Vector2`, `Vector2i`, `Transform2D`를 쓰지 않는다.
- `Vector2`는 화면 좌표(입력, 카메라, 그리기 인자)에서만 쓴다. 이 영역은 정밀도가 결과에 영향을 주지 않는다.
- 거리는 `sqrt(dx*dx + dy*dy)`로 계산한다. `Vector2.distance_to()`나 `Vector2.length()`를 쓰지 않는다(정밀도 + 연산 순서).

이 규칙을 어기면 §16.5의 회귀 테스트가 조용히 어긋난다. M1에서 §6.2 표와 일치하는지가 최종 확인이다.

### 2.2 레벨 데이터를 `.tres`가 아니라 JSON으로 두는 이유

- 생성기가 시드 수천 개에서 후보를 쏟아내므로 텍스트로 가볍게 쓰고 읽어야 한다.
- 채택된 단계의 좌표 변경이 git diff에서 바로 읽혀야 한다(§0.7 규칙의 감시 수단).
- 에디터(§8.7)는 인스펙터가 아니라 전용 캔버스 UI를 쓰므로 `Resource`의 인스펙터 이점이 필요 없다.
- 로드 시 `JSON.parse_string` → `core/level.gd`의 타입 있는 `RefCounted` 객체로 변환하고, 그 시점에 스키마를 검사한다.

### 2.3 명령어

CLI 도구는 `godot --headless --path . --script res://tools/<도구>.gd -- <인자>` 형태다. 매번 길게 쓰지 않도록 루트에 `run.sh`(Windows는 `run.ps1`) 래퍼를 둔다.

| 명령 | 하는 일 |
|---|---|
| `./run.sh solve [단계ID]` | 전 각도 스캔(§16.1) |
| `./run.sh validate [단계ID\|장번호]` | 전체 검증(§16.3) |
| `./run.sh gen --recipe <파일> --slot <칸> [--count N] [--seeds N]` | 후보 생성(§16.4) |
| `./run.sh fan <단계> [시작각] [끝각] [간격]` | 궤적 부채꼴 SVG(§16.2, 선택) |
| `./run.sh test` | gdUnit4 전체 실행(§16.5) |
| `./run.sh bench` | 단일 전수 스캔 성능 측정(§17 M0 관문) |

에디터에서 게임을 실행하는 것(F5)과 안드로이드 원클릭 배포는 Godot 에디터에서 직접 한다.

## 4. 좌표계와 단위

- **월드 좌표:** 원점은 맵 좌상단, x는 오른쪽, **y는 아래쪽**이 양수. 단위는 "유닛". Godot 2D의 좌표계와 방향이 같으므로 변환이 필요 없다.
- **월드 각도 θ(내부):** 도(°) 단위, 0° = 오른쪽, **−90° = 위쪽**, 시계 방향이 양수(y가 아래이므로). 레벨 데이터·물리·테스트는 모두 이 각도를 쓴다. Godot의 `atan2(y, x)`·`Node2D.rotation`과 같은 규약이다.
- **θ는 두 가지를 겸한다(§5.9):** 우주선이 발사대 행성 표면에 서 있는 **위치**이자, 그 자리에서 이륙하는 **방향**이다. 발사 좌표는 `start + PAD_R·(cos θ, sin θ)`이고 속도는 `speed·(cos θ, sin θ)`다. 파라미터가 하나인 것은 종전과 같다.
- **표시 각도(UI):** 0° = 위쪽, 시계 방향 증가, 0~360°. 변환: `ui = fposmod(world + 90.0, 360.0)`.
- **각도 양자화:** 조준 각도는 **0.5° 단위**로 반올림한다. 같은 각도를 다시 재현할 수 있어야 퍼즐이 된다.
- **시간:** 초. 모든 시뮬레이션은 고정 스텝 `DT = 1.0/240.0`초.
- **속도:** 유닛/초. 가속도: 유닛/초².
- **1 유닛 = 월드 공간 1 픽셀**로 두고, 화면 배율은 `Camera2D.zoom`으로 만든다(§11).

## 5. 물리 명세

참조 구현은 부록 A(검증 완료 JavaScript)이고 GDScript 이식 초안은 부록 D다. **연산 순서까지 동일하게** 유지한다.

### 5.1 상수

`core/constants.gd`에 아래를 둔다.

| 상수 | 값 | 뜻 |
|---|---|---|
| `DT` | `1.0/240.0` | 고정 스텝(초) |
| `SHIP_R` | `5.0` | 우주선 충돌 반경 |
| `MAX_FLIGHT` | `30.0` | 비행 제한(초) |
| `PAD_R` | `22.0` | 발사대 행성 중심 → 우주선 중심. **실제 발사 좌표를 정한다**(§5.9) |
| `ARC` | `90.0` | 우주선이 걸어 다닐 수 있는 범위(돔 중심 방향 ±ARC) |

`PAD_R`을 24 이상으로 키우면 1-4의 성공 폭이 11.25°에서 6.50°로 무너진다(§6.2의 측정). 22는 그 절벽에서 2유닛 아래로 잡은 값이다.

### 5.2 두 개의 시계

- **단계 시계 `level_step`:** 단계가 시작(또는 재시작)되면 0부터 매 스텝 증가한다. **발사 전에도 흐른다.** 공전 행성 위치는 `t = level_step * DT`로 계산한다.
- **비행 시계 `flight_step`:** 발사 순간 0에서 시작. 외계인 사격 타이밍과 30초 제한에 쓴다.
- 발사는 스텝 경계에서만 일어난다. 손을 뗀 프레임의 현재 `level_step`이 `launch_step`이 된다.
- 재시작 시 두 시계 모두 0으로 초기화한다.

### 5.3 중력

중력원은 행성(`planets`)과 블랙홀(`holes`)이며 같은 공식을 쓴다. 중력원 중심까지 거리를 `r`, 중력 범위를 `R`, 세기를 `g`라 하면:

```
r ≥ R 이면: 가속도 0
r < R 이면: 크기 = g × (1 − r/R)²,  방향 = 우주선 → 중력원 중심
```

여러 중력원의 가속도는 단순 합산한다. `r < 1`이면 0으로 처리(0 나눗셈 방지).

### 5.4 한 스텝의 순서 (반드시 이 순서)

1. 현재 시각 `t`에서 가속도 계산
2. 속도 갱신 `v += a·DT`, 위치 갱신 `p += v·DT` (반암시적 오일러)
3. 시각 `t + DT` 기준으로 충돌 판정, 아래 순서로 **처음 걸린 것**이 결과
   1. 행성: `거리 < planet.r + SHIP_R` → `planet`
   2. 블랙홀: `거리 < rH + 2` → `hole`
   3. 소행성: `거리 < rock.r × 0.85 + SHIP_R` → `rock`
   4. 외계인 몸체: `거리 < 13 + SHIP_R` → `ufo`
   5. 맵 경계: 우주선 중심이 `[SHIP_R, w − SHIP_R] × [SHIP_R, h − SHIP_R]` 밖 → `wall`
   6. 목적지: `거리 < goal.r` → `win`
4. 결과가 없으면 비행 시계 증가 후 외계인 사격 처리(5.5)
5. 총알 이동 및 피격 판정 → `shot`
6. 비행 시간이 `MAX_FLIGHT` 이상이면 `drift`

거리는 `sqrt(dx*dx + dy*dy)`로 계산한다(§2.1).

### 5.5 외계인 사격

- 각 외계인은 `delay` 초에 첫 사격 시도, 이후 `interval` 초마다 시도한다(비행 시계 기준).
- 시도 시점에 우주선이 `range` 안에 있으면, 그 순간 우주선 위치를 향해 속도 `bs`의 총알을 발사한다(예측 사격 없음). 범위 밖이면 이번 시도는 건너뛴다.
- 총알은 직진하며, 수명 5초가 지나거나 맵 밖 20유닛을 벗어나면 제거한다.
- 발사 전에는 사격하지 않는다.
- 부록 A는 다음 사격 시각을 외계인 객체에 `_next`로 얹어 두고 시뮬레이션마다 지운다. GDScript 이식에서는 **레벨 객체를 건드리지 말고** 시뮬레이션 상태(`SimState`) 안의 `PackedFloat64Array next_fire`로 옮긴다. 레벨 객체가 불변이어야 `WorkerThreadPool` 병렬 스캔이 안전하다.

### 5.6 공전 행성

`orbit: {cx, cy, rad, period, phase}`가 있으면 위치는
`angle = phase + 2π·t/period`, `x = cx + rad·cos(angle)`, `y = cy + rad·sin(angle)`. period가 음수면 반대 방향. 블랙홀과 소행성, 외계인은 고정이다.

### 5.7 예측선

- 조준 중 매 프레임, 현재 `level_step`에서 발사했다고 가정하고 `step_ship`만 `preview / DT` 스텝 돌려 경로를 얻는다(총알은 무시).
- **실제 비행과 같은 함수**를 써야 한다. "보이는 대로 날아간다"가 이 게임의 신뢰 기반이다.
- 예측 중 충돌 결과가 나오면 거기서 멈추고 그 지점에 작은 × 표시.
- 단계별 `preview` 초가 길이를 결정한다(1단계 1.8초 → 6단계 0.8초).

### 5.8 결정론 보장

- 시뮬레이션은 **`_physics_process`에 걸지 않는다.** `game/clock.gd`가 `_process(delta)`에서 자체 누산기를 돌린다: `acc += min(delta, 0.1)`; `while acc >= DT and steps < 48: step(); acc -= DT`. 이렇게 해야 게임과 headless 도구가 같은 스테핑 코드를 쓴다.
- 앱이 백그라운드로 가면(`platform/lifecycle.gd`, §15.2) 누산기를 0으로 리셋하고 일시정지한다.
- 난수는 시뮬레이션 결과에 쓰지 않는다. 소행성 모양, 별 배경 같은 장식에만 `seed` 기반 mulberry32(`core/rng.gd`)를 쓴다. `RandomNumberGenerator`의 전역 상태에 의존하지 않는다.

### 5.9 발사대 행성 (v4.1에서 추가)

우주선은 출발점의 고정된 한 점에서 쏘는 것이 아니라, `start`를 중심으로 하는 **작은 행성 표면에 서 있다가 그 자리에서 법선 방향으로 이륙**한다.

```
발사 좌표 = start + PAD_R · (cos θ, sin θ)
발사 속도 = speed  · (cos θ, sin θ)
```

- 돔 중심 방향은 `atan2(goal.y − start.y, goal.x − start.x)`이고, 우주선은 그 방향 **±`ARC`(90°)** 안에서만 걸을 수 있다. 반원 밖은 도달할 수 없으므로 생성기·검증기가 이를 제약으로 쓴다(§8.4, §8.5).
- **이 방식이 §6.2의 검증값을 거의 바꾸지 않는 이유:** 이륙이 법선 방향이므로, 돔 표면에서 쏘는 것은 같은 직선 경로를 `PAD_R`만큼 앞에서 시작하는 것과 같다. 출발점이 중력 범위 밖이면 궤적이 그대로다. 차이는 (ㄱ) 돔 표면이 중력 범위에 걸칠 때 (ㄴ) 공전 행성이 있어 시간이 중요할 때만 생긴다.
- 실제 측정: 돔 반경 22에서 1-1·1-4·2-1·3-1·5-1은 §6.2와 **완전히 동일**하고, 4-1만 9.00°→9.50°로 바뀐다(§6.2의 표).
- `PAD_R`은 전역 상수다. 레벨마다 다르게 두지 않는다 — 플레이어가 배운 조작 감각이 단계마다 달라지면 안 된다.

렌더링용 표면 반경(18유닛)은 `PAD_R`보다 작다. 우주선 중심이 22에 있고 길이가 14이므로 꼬리가 표면에 살짝 묻혀 "얹혀 있는" 모양이 된다. 이 값은 그림에만 쓰고 물리에는 쓰지 않는다(§12.3).

### 6.1 스키마

JSON 파일의 구조는 아래와 같고, `core/level.gd`가 이 구조를 타입 있는 객체로 읽는다(`?`는 선택 항목).

```
Level {
  id: String                    // "1-1"
  name: String
  w: float, h: float            // 맵 크기(유닛)
  speed: float                  // 발사 속도

  start: { x, y }
  goal: { x, y, r }
  planets?: Planet[], holes?: Hole[], rocks?: Rock[], ufos?: Ufo[]
  hint?: String                 // 첫 시도에만 표시
  meta: {
    chapter: int, slot: int, role: String
    intro?: "planet" | "rock" | "hole" | "ufo" | "orbit" | "wide"

}
Planet { x, y, r, g, R, sides: int, ring?: bool,
         role?: "required" | "optional" | "gate",

Hole   { x, y, rH, g, R, role?: "required" | "optional" }
Rock   { x, y, r, seed: int }
Ufo    { x, y, range, interval, delay, bs }
```

- `loader.gd`는 모르는 키를 만나면 **오류로 처리**한다(오타로 조용히 무시되는 것을 막는다).

**출발점 여유와 §8.5 규칙 8 (M1에서 발견, v4.1에서 결론)**

출발점에서 각 단계의 가장 가까운 중력원까지 실측한 여유는 다음과 같다.

| 단계 | 가장 가까운 중력원 | 거리 `r` | 범위 `R` | 여유 `R−r` | 출발점 가속도 |
|---|---|---|---|---|---|
| 1-1 | 행성0 | 357.95 | 170 | +187.95 | 0 |
| 1-4 | 행성0 | 161.55 | 150 | +11.55 | 0 |
| 2-1 | 블랙홀 | 280.00 | 180 | +100.00 | 0 |
| 3-1 | 행성0 | 205.18 | 150 | +55.18 | 0 |
| **4-1** | **행성0** | **167.63** | **170** | **−2.37** | **0.165 u/s²** |
| 5-1 | 행성0 | 210.95 | 170 | +40.95 | 0 |

4-1의 출발점은 범위 안으로 2.37유닛 들어가 있다. 다만 그 지점의 가속도는 0.165 u/s²로 해당 행성 최대 세기(850)의 0.02% 수준이라 실제 궤도에 미치는 영향은 거의 없다. 발사 전에는 우주선이 움직이지 않으므로(§5.2) 조준 중에 끌려가는 문제도 없다.

**결론 (v4.1에서 확정).** 발사대 행성을 도입하면서 규칙 8을 다시 썼다. `PAD_R = 22`에서 각 단계의 실제 발사 지점 가속도를 재면 다음과 같다.

| 단계 | 정답 θ에서의 발사 지점 가속도 | 돔 표면 전체의 최댓값 |
|---|---|---|
| 1-1, 2-1, 3-1, 5-1 | 0 | 0 |
| 1-4 | 2.45 u/s² | 3.64 |
| **4-1** | **13.35 u/s²** | **17.47** |

4-1의 13.35는 그 행성 최대 세기(850)의 1.6%다. 초기 속도 150 u/s에 대해 0.3초 동안 약 2°의 편향을 만든다 — 성공 폭이 9.5°이므로 감당 범위이고, 예측선이 그 휘어짐을 그대로 보여주므로 플레이어가 속지 않는다. 따라서 "가속도 1 u/s² 미만" 같은 임계값은 **너무 엄해서 쓰지 않는다.**

대신 역할을 둘로 나눈다.

- **합격 기준(§8.5 규칙 8)은 물리적 유효성만 본다** — 돔 표면의 어느 지점도 행성·블랙홀·소행성의 충돌 판정 안에 들어가면 안 된다. 무언가의 **안에서** 시작할 수는 없기 때문이다.
- **설계 품질은 경고로 본다** — 발사 지점 가속도가 1 u/s² 이상이면 보고한다. 지금 1-4와 4-1이 여기 걸리며, 이는 의도된 기록이다.
- **새로 만드는 단계는 생성기가 애초에 막는다** — §8.4 1단계의 배치 제약을 `PAD_R + 30`으로 올린다. 기존 단계에 소급 적용하지 않는다.

이렇게 하면 검증기가 모든 단계의 관문이라는 §8.1 원칙을 지키면서, 검증된 6단계를 손대지 않고, 앞으로 만들 단계의 품질도 떨어뜨리지 않는다.

### 6.3 배치 원칙 (생성기와 에디터가 따를 기본값)

1. 출발점에서 첫 중력 범위 경계까지 350유닛 이내. 멀수록 각도 오차가 증폭된다.
2. 공전 행성은 `g ≤ 700`, `R ≤ 110` 수준의 약한 관문으로만 쓴다. 주 스윙바이를 맡기면 결과가 혼돈적이 된다.
3. 의도하지 않은 경로는 소행성·외계인으로 막는다.
4. 행성 `g`는 750~850, `R`은 130~170, 블랙홀은 `g` 900, `R` 180, `rH` 16을 기준으로 삼는다. 이 범위를 벗어나면 성공 폭이 급격히 좁아지는지 반드시 스캔으로 확인한다.

## 7. 스테이지 구성과 난이도 곡선

> 이 절은 콘텐츠 설계이며 엔진과 무관하다. v3에서 바뀌지 않았다.

### 7.1 전체 구조

- **초반부(1~5장, 40단계):** 장마다 새 요소 하나를 도입하고, 8단계에 걸쳐 익히고 섞는다. 사람이 설계 의도를 정하고 생성기·에디터로 제작한다.
- **후반부(6장~, 장당 10단계):** 새 요소 없이 기존 요소 조합으로 난이도를 올린다. 레시피 규칙(§7.5)으로 생성기가 후보를 만들고, 에디터에서 골라 다듬는다.
- 단계 ID는 `장-번호` 형식(`1-1`, `4-8`, `7-10`).
- 사전 검증된 6개 단계는 각 장의 핵심 위치에 고정 배치한다(표의 ★).

### 7.2 장 안의 단계 역할 (8단계 패턴)

| 칸 | 역할 | 설계 의도 | 목표 성공 폭 |
|---|---|---|---|
| 1 | 도입 | 새 요소를 거의 단독으로, 실패해도 이유가 명확하게 | 7° 이상 |
| 2 | 연습 | 같은 요소, 다른 배치로 한 번 더 | 7° 이상 |
| 3 | 변형 | 같은 요소를 다른 방식으로 사용(급회전, 반대 방향 등) | 6° 이상 |
| 4 | 휴식 | 쉬운 조합으로 긴장을 풀어 줌. 직전 단계보다 난이도 점수가 낮아야 함 | 8° 이상 |
| 5 | 조합 | 새 요소 + 이전 장 요소 | 6~8° |
| 6 | 조합 심화 | 요구 중력원 증가, 예측선 짧아짐 | 5~7° |
| 7 | 도전 | 장에서 가장 어려운 단계 | 4~6° |
| 8 | 마무리 | 긴 맵에서 장의 요소를 모두 사용하는 긴 항로. 도전보다 폭은 넓게 | 5° 이상 |

난이도는 톱니 모양으로 오른다. 장의 1단계는 직전 장 7단계보다 쉽고, 장이 넘어갈수록 기준선이 올라간다.

### 7.5 후반부 생성 규칙 (6장 이후)

장 번호를 `c`(6 이상), 칸을 `s`(1~10)라 하면:

| 칸 | 역할 | 목표 최소 성공 폭 |
|---|---|---|
| 1 | 워밍업 | `W(c)` |
| 2, 3 | 연습 | `W(c) − 0.5` |
| 4 | 휴식 | `W(c) + 2` |
| 5, 6, 7 | 조합 | `W(c) − 1` |
| 8 | 휴식 | `W(c) + 1.5` |
| 9 | 도전 | `W(c) − 2` |
| 10 | 마무리(긴 맵) | `W(c) − 0.5` |

- `W(c) = max(4.5, 7 − 0.4 × (c − 6))`, 어떤 경우에도 **최소 성공 폭은 2.5° 미만 금지**(0.5° 양자화 기준 서로 다른 성공 각도가 5개 이상).
- 예측선: `max(0.5, 0.7 − 0.05 × (c − 6))`초.
- 요구 중력원 수: 칸 1~4는 2~3, 칸 5~9는 3~4, 칸 10은 4~5.
- 위험 요소 조합은 장마다 하나의 "테마"를 정한다(예: 6장 블랙홀 밭, 7장 포격 회랑, 8장 이중 공전). 테마는 Claude Code가 제안하고 사용자가 고른다.

## 8. 스테이지 제작 파이프라인

### 8.1 방식 결정: 생성기 + 검증기 + 에디터

세 가지 방식을 비교해 **혼합 방식**을 채택한다.

| 방식 | 장점 | 한계 |
|---|---|---|
| Claude Code가 좌표를 직접 작성 | 도구 개발 불필요 | 중력 궤도는 직관으로 예측이 안 됨. 사전 검증에서 감으로 배치했을 때 성공 폭이 0.25~1°에 그쳤고, 격자 탐색을 거쳐야 7~11°가 나왔다. 수십 단계를 이렇게 만들 수 없다 |
| 에디터로 사람이 전부 제작 | 재미와 모양을 사람이 직접 판단 | 한 단계마다 수십 번의 배치·확인 반복. 풀이 가능성을 사람이 보장하기 어려움 |
| **생성기 + 검증기 + 에디터** | 생성기가 풀이가 보장된 후보를 대량으로 만들고, 검증기가 난이도를 수치화하고, 사람은 에디터에서 고르고 다듬기만 한다 | 초기 도구 개발 비용 |

역할 분담:
- **Claude Code:** 도구 개발, 레시피 작성, 생성기 실행, 결과 요약 보고. 좌표를 손으로 쓰지 않는다.
- **사용자:** 에디터에서 후보를 플레이해 보고 고르기, 필요하면 위치를 살짝 옮기기, 채택.
- **검증기:** 게임에 들어가는 모든 단계의 최종 관문. 규칙을 통과하지 못하면 채택·커밋할 수 없다.

### 8.2 작업 흐름

```
① 레시피 작성      Claude Code가 §7.3 표를 recipes/ch2.json 으로 옮김
② 후보 생성        ./run.sh gen --recipe recipes/ch2.json --slot 3 --count 6
③ 결과 보고        candidates/2-3/*.json + 요약표(성공 폭, 난이도 점수, 비행 시간) + 궤적 썸네일 SVG
④ 에디터에서 선택   Godot 에디터 → 스윙바이 탭 → 후보 목록 → 플레이 테스트 → 필요 시 수정
⑤ 채택             에디터 [채택] → levels/data/2-3.json 저장(정답·지표 자동 기록)
⑥ 전체 검증        ./run.sh validate → 통과 시 커밋
```

사용자가 Claude Code에 요청하는 예:
- "2장 레시피 만들고 2-2~2-8 후보를 칸마다 5개씩 생성해줘. 요약표만 보여줘."
- "2-5 후보 3번을 채택했어. 검증 돌리고 커밋해줘."
- "7장 테마 후보 3개 제안해줘."

② 생성은 **오래 걸리는 배치 작업**이다(§8.9). 실행해 두고 다른 일을 하는 흐름을 전제로 한다.

### 8.3 레시피 형식

```json
{
  "chapter": 2,
  "defaults": { "speed": 160, "startZone": "bottom", "goalZone": "top" },
  "slots": [
    {
      "slot": 2, "role": "연습", "intro": null,
      "map": { "w": 400, "h": 760 },
      "preview": 1.0,
      "required": [ { "type": "hole", "count": 1 } ],
      "optional": [],
      "hazards": { "ufos": 0, "rocksMax": 6 },
      "window": { "min": 7, "max": 12 },
      "timing": null,
      "seedCount": 500
    }
  ]
}
```

- `required`: 성공 경로가 **반드시 거쳐야 하는** 중력원. `optional`: 배치하되 필수가 아닌 중력원(방해·장식). 공전 행성은 `{ "type": "orbit", "count": 1, "role": "gate" }`.
- `startZone`, `goalZone`: `bottom | top | left | right | center | any`.
- `timing`: 공전 단계에서 `{ "minFraction": 0.3, "maxFraction": 0.4 }`.
- `seedCount` 기본값은 **500**이다(v3의 2000에서 낮춤, 이유는 §8.9). 후보가 부족하면 늘려 재실행한다.

### 8.4 생성기 알고리즘 (`tools/generate.gd` + `tools_shared/generator.gd`)

사전 검증에서 실제로 성공한 절차를 그대로 자동화한다.

1. **배치 샘플링:** 시드별로 출발점을 `startZone`에 두고, 필수·선택 중력원을 무작위 배치한다. 제약: **출발점은 모든 중력 범위 밖 `PAD_R + 30`(= 52)유닛 이상**(돔 표면 전체가 범위 밖이어야 한다, §5.9), 첫 필수 중력원의 범위 경계는 출발점에서 350유닛 이내, 중력원 중심끼리 `R₁ + R₂ − 60` 이상 떨어짐(범위 약간 겹침 허용), 맵 경계에서 `r + 20` 이상.
2. **각도 전수 스캔:** 목적지와 소행성 없이 −180°~180°를 0.25° 간격으로 시뮬레이션(외계인·총알 포함). 궤적마다 "지금까지 들어간 중력 범위" 비트마스크를 기록한다.
3. **목적지 격자 평가:** 맵을 10유닛 격자로 나누고, 궤적이 `goal.r` 이내로 지나간 칸에 그 각도를 표시한다. 단, **모든 필수 중력원 범위를 이미 거친 뒤**에 지나간 경우만 인정한다. 칸마다 연속 성공 각도 구간의 최대 폭을 구한다.
4. **목적지 선택:** `goalZone` 안에서, 출발점과 거리가 맵 대각선의 40% 이상이고 중력원 중심에서 `R × 0.5` 이상 떨어진 칸 중 폭이 레시피 범위에 드는 최선의 칸. **주 구간이 돔 중심 방향 ±`ARC` 안에 들어야 한다**(§5.9). 목적지를 정하면 돔 중심 방향도 정해지므로, 이 검사는 목적지 후보마다 다시 해야 한다.
5. **지름길 차단:** 목적지를 넣고 다시 전수 스캔. 주 구간 외에 폭 1° 이상의 성공 구간이 있으면, 그 궤적 위에서 주 구간 궤적들과 35유닛 이상 떨어진 지점에 소행성을 놓고 반복한다. `rocksMax` 안에서 해결 안 되면 이 시드는 폐기.
6. **공전 타이밍:** 공전 행성이 있으면 주기를 24등분한 발사 시점마다 3~5를 수행해, 주 구간 폭이 최소 폭 이상인 시점의 비율이 `timing` 범위인지 확인.
7. **장식 소행성:** 선택적으로 2~4개, 주 구간 궤적들에서 30유닛 이상 떨어진 곳에.
8. **검증(§8.5) 통과 후보만** 저장하고, 난이도 점수 순으로 정렬해 상위 `count`개를 출력.

**병렬화:** `WorkerThreadPool.add_group_task()`로 시드 단위 병렬 처리한다. 워커 안에서는 레벨 객체를 절대 변경하지 않는다(§5.5의 `next_fire` 규칙이 이것 때문이다). 진행률을 10초마다 한 줄씩 출력해, 긴 배치 작업 중에도 살아 있음이 보이게 한다.

### 8.5 검증기 (`tools/validate.gd`, `tools_shared/metrics.gd`)

에디터와 CLI가 같은 지표 코드를 쓴다(노드 금지 규칙은 `core`와 동일).

**지표**

| 지표 | 정의 |
|---|---|
| `main_window` | 가장 넓은 연속 성공 구간 폭(°). 공전 단계는 최적 발사 시점 기준 |
| `solution` | 주 구간 중앙 각도(0.5° 반올림)와 발사 스텝 |
| `flukes` | 주 구간 외 성공 구간 목록과 합계 폭 |
| `essential` | 필수 중력원을 하나씩 제거했을 때 정답이 실패하는지 |
| `timing_fraction` | 발사 가능 시점 비율(공전 단계) |
| `timing_range` | 정답 각도로 성공하는 발사 시점 구간(주기 안의 초). 힌트의 공전 표시에 사용 |
| `flight_time` | 정답 비행 시간 |
| `clearance` | 정답 경로가 행성·블랙홀·소행성 판정 경계에 가장 가까이 간 거리 |
| `difficulty` | §8.6 점수 |

**필수 규칙(하나라도 어기면 실패)**

1. `main_window ≥ max(2.5, 레시피 최소 폭)`
2. 주 구간 외 성공 구간은 각각 1° 미만, 합계 2° 미만
3. `required` 중력원은 모두 `essential`
4. `flight_time ≤ 15초`
5. `clearance ≥ 6유닛`
6. 공전 단계는 `timing_fraction`이 레시피 범위 안
7. 저장된 `solution`으로 시뮬레이션하면 `win`
8. **돔 표면(`start` 중심 반경 `PAD_R`)의 어느 지점도 행성·블랙홀·소행성의 충돌 판정 안에 들어가지 않음** — 무언가의 안에서 출발할 수는 없다. 근거는 §6.2의 결론
9. **정답 θ가 돔 중심 방향 ±`ARC` 안** — 반원 밖은 우주선이 걸어갈 수 없으므로 도달 불가능한 단계가 된다

**경고(통과는 하되 보고)**

- `main_window`가 레시피 최대 폭 초과(너무 쉬움)
- `clearance < 10`(아슬아슬해서 의도치 않게 어려울 수 있음)
- **발사 지점(정답 θ)의 합산 가속도가 1 u/s² 이상** — 돔 표면이 중력 범위에 걸쳐 있다는 뜻이다. 검증된 1-4(2.45)와 4-1(13.35)이 여기 걸리며 이는 의도된 기록이다(§6.2). 생성기가 만든 단계가 여기 걸리면 배치 제약이 새는 것이므로 원인을 찾는다
- 장 안에서 휴식 칸(4, 8)의 난이도 점수가 직전 칸보다 높음
- 장 1칸의 점수가 이전 장 7칸보다 높음

사전 검증 6단계의 실측값(규칙 보정 근거): 비행 시간 3.3~6.0초, `clearance` 8.1~18.2유닛, 고정 중력원은 모두 `essential`, 공전 관문은 비필수.

### 8.6 난이도 점수

```
A = clamp((8 − main_window) / 5.5, 0, 1) × 3.0          성공 폭
B = min((필수 중력원 수 − 1) × 0.6, 1.8)                 연계 수
C = min((외계인 수 + 비필수 블랙홀 수) × 0.4, 1.2)       위험 요소
E = clamp((1.8 − preview) / 1.3, 0, 1) × 1.5            예측선
F = 공전 단계면 clamp((0.5 − timing_fraction) / 0.3, 0, 1) × 1.5, 아니면 0
G = 맵이 두 축 모두 화면 초과면 1.0, 한 축이면 0.5, 아니면 0
difficulty = A + B + C + E + F + G      (대략 0~10)
```

가중치는 초기값이다. M8에서 플레이 테스트 후 조정하고, 조정하면 모든 단계의 점수를 다시 계산해 곡선 경고를 확인한다.

### 8.7 스테이지 에디터 (`addons/swingby_editor/`, EditorPlugin)

v3에서는 웹 페이지(`/?editor=1`)와 Vite 개발 서버 플러그인으로 만들 예정이었으나, Godot에서는 **에디터 플러그인**으로 만든다. 캔버스·드래그 핸들·되돌리기·파일 저장을 에디터가 이미 제공하므로 직접 만들 코드가 크게 줄어든다.

- `plugin.cfg` + `EditorPlugin`으로 메인 화면 탭 "스윙바이"를 추가한다. `addons/`는 익스포트 필터에서 제외되므로 배포 빌드에 들어가지 않는다(§19).
- 파일 저장은 `FileAccess`로 직접 한다. **쓰기 경로는 `res://levels/data/`와 `res://candidates/`로 제한**하고, 그 밖의 경로 요청은 거부한다.
- 되돌리기·다시하기는 `EditorUndoRedoManager`를 쓴다(50단계 제한은 에디터 설정을 따른다).
- 데스크톱 Godot 에디터 사용을 기본으로 한다.

**화면 구성**

```
┌──────────────────────────────┬────────────────┐
│                              │ 단계 정보       │
│   맵 캔버스                   │  ID, 맵 크기, 속도│
│   + 궤적 오버레이              │  예측선         │
│                              ├────────────────┤
│                              │ 선택 요소 속성   │
│                              ├────────────────┤
│                              │ 검증 결과       │
│                              │  지표, 규칙 ✓/✗ │
│                              │  난이도 점수     │
├──────────────────────────────┴────────────────┤
│ 선택│행성│공전│블랙홀│소행성│외계인│출발│목적지 ┃ 되돌리기 다시하기 ┃ 플레이 │ 채택 │
└───────────────────────────────────────────────┘
```

**기능**

- 요소 추가·삭제·드래그 이동(5유닛 격자 스냅, Shift로 해제). 중력 범위 원의 테두리 손잡이로 `R` 조절, 공전 행성은 중심 이동과 반경 손잡이.
- 속성 패널에서 모든 수치를 입력·슬라이더로 수정. 필수/비필수/관문 역할 지정.
- **실시간 검증:** 수정 후 **600ms** 뒤 `WorkerThreadPool`에서 1° 간격 대략 스캔 → 결과 표시 → 0.25° 정밀 스캔으로 갱신. 진행률 표시. (디바운스가 v3의 300ms에서 늘어난 이유는 §8.9.)
- **궤적 오버레이:** 2° 간격 부채꼴을 실패 원인별 색으로(충돌 주황, 벽 회색, 블랙홀 보라, 피격 빨강, 성공 초록). 주 구간은 굵게.
- **타이밍 지도(공전 단계):** 가로 발사 시점 × 세로 각도의 성공 여부 격자. 칸을 누르면 그 조건의 궤적을 강조.
- **후보 목록:** `candidates/<단계ID>/`를 불러와 썸네일과 지표로 비교.
- **플레이 테스트:** 실제 게임 씬을 띄워 플레이, 뒤로 가면 마지막 시도 궤적을 에디터에 겹쳐 표시.
- **정답 재생:** 저장된 `solution`으로 비행을 재생.
- **채택:** 필수 규칙 통과 시에만 활성화. `meta`(정답, 지표, 난이도, 수정일)를 채워 `levels/data/<ID>.json`에 저장하고 `chapters.gd` 목록 반영을 안내.
- JSON 복사·붙여넣기.

### 8.8 비교 대상으로 검토했던 대안 (참고)

레벨을 Godot 씬(`.tscn`)으로 두고 에디터의 `CanvasItem` 기즈모를 그대로 쓰는 방식도 검토했다. 드래그 편집은 공짜로 얻지만, 생성기가 씬을 대량 출력해야 하고 후보 비교·검증 지표 표시를 결국 커스텀 UI로 붙여야 하며 git diff가 읽기 어려워진다. 그래서 §2.2대로 JSON + 전용 캔버스를 택했다.

### 8.9 생성기 성능과 그 영향 (v4에서 추가)

GDScript는 JIT가 없는 인터프리터이므로 같은 수치 루프가 Node(V8)보다 느리다. **v4에서 실제로 측정했다**(M0, Intel Xeon 2.10GHz 4코어):

| 단계 | Node 22 | Godot 3.5 GDScript (무타입) | 비율 |
|---|---|---|---|
| 1-1 (행성1, 소행성5) | 0.089초 | **4.90초** | 55× |
| 5-1 (행성2, 블랙홀, 외계인2, 소행성6) | 0.694초 | **9.01초** | 13× |

비율이 크게 다른 이유는 5-1의 총알·외계인 처리가 Node 쪽에서도 무겁기 때문이다. **비율보다 Godot의 절대 시간이 판단 기준이다.**

위 수치는 **상한**이다. Godot 3.5의 옛 VM에 `Array`(Variant 박싱)를 쓴 트랜스리터레이션이고, 실제 구현은 Godot 4의 재작성된 VM에 정적 타입과 `PackedFloat64Array`를 쓴다. 두 요인을 합쳐 **2~4배 빨라질 것으로 보며, 1-1 기준 1.2~2.5초를 예상한다.** 확정 수치는 사용자가 Godot 4에서 `./run.sh bench`를 돌려 나온다.

이 차이가 실제로 어디에 걸리는지 구분해 둔다.

| 작업 | 빈도 | 영향 |
|---|---|---|
| 에디터 실시간 검증 (단일 스캔) | 요소를 옮길 때마다 | **UX에 직결.** 여기가 느리면 에디터가 못 쓸 물건이 된다 |
| `solve` / `validate` (단계당 1~12 스캔) | 커밋 전마다 | 수 초~수십 초. 감당 가능 |
| 생성기 배치 (시드 × 여러 스캔) | 장마다 몇 번 | 수십 분~한 시간대. 실행해 두고 다른 일을 한다 |

대응:
- **M0에서 벤치마크를 먼저 재고 그 결과로 판단한다**(§17 M0의 관문). 기준은 1-1 전수 스캔(1440각도) 1회.
- 에디터 실시간 검증은 1° 대략 스캔(360각도)을 먼저 보여주고 0.25°로 갱신하는 2단계 방식 + 600ms 디바운스로 체감을 확보한다.
- 레시피 `seedCount` 기본값을 2000 → 500으로 낮춘다. 후보가 부족하면 늘려 재실행한다.
- 내부 루프는 `Array`·딕셔너리 대신 `PackedFloat64Array`를 쓰고, 루프 안에서 객체를 새로 만들지 않는다.
- 전수 스캔은 궤적 대부분이 일찍 벽에 부딪혀 끝난다(1-1 기준 1440각도 중 1219개가 `wall`). 평균 스텝 수는 최대치보다 훨씬 작다.

벤치마크가 5초를 넘으면 GDScript 단독을 고집하지 않고, `core/`만 GDExtension(Rust/C++) 또는 C#으로 빼는 선택지를 사용자와 상의한다. 그 경우에도 게임과 도구가 **같은 코어 하나**를 쓴다는 원칙(§0.3)은 유지한다 — GDExtension으로 만들면 게임(Godot)과 CLI가 같은 바이너리를 공유할 수 있다.

M0 측정 결과, 상한(4.90초)조차 5초를 넘지 않았다. **GDScript 단독 진행이 가능하다고 본다.**

### 8.9.1 공전 단계 생성 비용 (M0 측정에서 드러난 문제)

§8.4의 6단계를 문자 그대로 읽으면 공전 행성이 있는 시드마다 "주기를 24등분한 발사 시점마다 3~5를 수행"한다. 시드 하나가 **스캔 약 120회**(24시점 × 지름길 차단 반복)가 되고, 스캔 1회를 3초로 잡으면 시드 하나에 6분, 500시드면 코어 4개로도 **12시간**이 넘는다. 4장 전체가 공전 단계이므로 이대로는 못 쓴다.

제안하는 수정(**M8에서 사용자 확인 후 적용**):

1. 기준 위상 하나(예: `phase` 그대로)에서 3~5단계를 먼저 수행해 후보를 거른다.
2. **거기서 살아남은 시드에 대해서만** 24등분 타이밍 검사를 돌린다.

통과율이 몇 %라면 비용이 그만큼 줄어 실용 범위에 들어온다. 지표 정의(`timing_fraction`)와 검증 규칙 6은 그대로다 — 계산 순서만 바꾸는 것이라 결과가 달라지지 않는다. 다만 1단계에서 쓰는 기준 위상이 운 나쁘게 나쁜 시점이면 좋은 시드를 놓칠 수 있으므로, M8에서 기준 위상을 2~3개로 늘리는 것과 비교해 정한다.

## 9. 게임 흐름과 상태 머신

### 9.1 앱 화면

`Title` → `LevelSelect` → `Play` → `Result` → (`Play` 재시도 | 다음 `Play` | `LevelSelect`)

- `scenes/main.gd`가 루트에서 화면 씬을 교체한다. `Result`는 `Play` 위에 겹치는 오버레이라 씬을 지우지 않는다(뒤의 궤적이 보여야 한다, §13.4).
- 씬 교체는 `add_child`/`queue_free`로 직접 하고, `change_scene_to_file`은 쓰지 않는다(전환 중 상태 유지가 필요하다).

### 9.2 Play 내부 상태

`game/session.gd`가 아래 상태를 관리한다.

| 상태 | 들어오는 조건 | 하는 일 | 나가는 조건 |
|---|---|---|---|
| `ready` | 단계 시작·재시작 | 단계 시계 진행(공전 행성 움직임), 조준·화면 이동 허용 | 조준 드래그 시작 → `aiming` |
| `aiming` | 조준 드래그 중 | 각도 갱신, 예측선, 각도 표시 | 발사 조건 충족 후 손 뗌 → `flying` / 취소 → `ready` |
| `flying` | 발사 | 시뮬레이션, 카메라 추적, 궤적 기록 | 결과 발생 → `ending` |
| `ending` | 결과 발생 | 시뮬레이션 정지, 폭발 또는 도착 연출 0.8초 | 연출 종료 → `Result` 화면 |

`ready`와 `aiming`에서 단계 시계는 계속 흐른다. `ending` 동안 공전 행성 애니메이션은 계속 보이지만 판정은 멈춘다.

## 10. 입력 명세 (한 손가락)

### 10.0 단위 환산 (v4에서 추가)

v3의 px 기준값은 **CSS 픽셀**(≈ 안드로이드 dp) 기준이다. Godot의 `InputEventScreenTouch.position`은 뷰포트 픽셀(실제 기기 픽셀)이므로 그대로 비교하면 고DPI 기기에서 기준이 3배 좁아진다.

- `platform/dp.gd`에 `dp(v: float) -> float`를 두고, 아래 모든 px 값을 `dp()`로 감싸 쓴다.
- 환산 계수는 `DisplayServer.screen_get_scale()`을 우선 쓰고, 값이 유효하지 않으면 `screen_get_dpi() / 160.0`로 대체한다. 데스크톱에서는 1.0로 본다.
- 계산한 계수는 `CLAUDE.md`에 남기고, M2 실기기 확인에서 조준 감도가 자연스러운지 사용자에게 확인받는다.

### 10.0.1 입력 설정

- `InputEventScreenTouch` / `InputEventScreenDrag`를 `_unhandled_input`에서 처리한다. **`index == 0`인 첫 번째 포인터만 추적**하고 추가 손가락은 무시한다.
- 프로젝트 설정에서 `input_devices/pointing/emulate_mouse_from_touch = true`(데스크톱 테스트용), `emulate_touch_from_mouse = true`.
- `Input.set_use_accumulated_input(false)`로 조준 입력 지연을 줄인다.

### 10.1 누르는 순간의 해석 (`ready` 상태에서만)

1. 누른 점이 미니맵 영역 안 → **미니맵 이동 모드**
2. 그 외 **어디를 눌러도 조준 모드**

v4.0까지는 우주선 근처(`dp(90)`)를 눌러야 조준이 시작됐다. 발사대 행성(§5.9)을 도입하면서 조준 기준점이 우주선이 아니라 **돔 중심**이 되었으므로, 화면 어디를 눌러도 방향이 정해진다. 우주선을 손가락으로 가리지 않아도 되고, 화면 구석에서 끌면 미세 조정이 쉬워진다.

### 10.2 조준 모드

- 방향 벡터 = 손가락 위치 − **돔 중심(`start`)의 화면 위치**. 우주선이 그 방향의 표면 자리로 걸어간다.
- 벡터 길이가 `dp(26) + 표면 반경` 이상이면 각도 θ를 계산해 0.5° 단위로 양자화하고, `±ARC`로 잘라낸 뒤 우주선 위치·예측선·표시 각도를 갱신한다. 손가락이 멀수록 같은 움직임에 대한 각도 변화가 작아지므로 자연스러운 미세 조정이 된다.
- 그보다 가까우면 "취소 영역": 예측선을 숨기고 행성 둘레에 취소 표시.
- **툭 친 것은 발사하지 않는다.** 화면 어디나 조준이 시작되므로 실수 발사를 막아야 한다. 손을 뗄 때 **`dp(8)` 이상 움직였거나 250ms 이상 눌렀을 때만** 발사한다. 둘 다 아니면 취소로 처리한다.
- 손을 뗄 때 취소 영역이면 **취소**(각도는 마지막 값 유지, 예측선 숨김).
- 손가락이 화면 밖으로 나가거나 앱이 포커스를 잃으면(`NOTIFICATION_APPLICATION_FOCUS_OUT`) 발사하지 않고 취소.

### 10.3 화면 이동

- **빈 곳을 끌어 화면을 옮기는 조작은 없다.** §10.1 규칙 2와 물리적으로 양립할 수 없다(누르면 조준이 되어 버린다). 큰 맵은 §10.4의 미니맵으로 살펴본다.
- 한 손가락만 추적한다는 §10.0.1 규칙은 그대로다. 두 손가락 이동은 넣지 않는다.
- M4에서 큰 맵(4-1, 5-1)을 실기기로 확인할 때 미니맵만으로 항로 파악이 되는지 판단한다. 안 되면 미니맵을 키우거나 발사 전 자동 훑기 연출을 검토한다.

### 10.4 미니맵 이동 모드

- 누른 점과 드래그 중인 점에 해당하는 월드 위치로 카메라 중심을 즉시 옮긴다.

### 10.5 비행 중·연출 중

- 필드 입력 무시. HUD의 재시작 버튼만 동작한다.

### 10.6 보조

- 진동: `platform/haptics.gd`로 발사·게임오버·도착 시 짧게(§15.2). 설정에서 끌 수 있다.

## 11. 카메라와 뷰포트

`Camera2D` 하나를 `Play` 씬에 두고 아래를 설정한다. v3에서 직접 짜기로 했던 클램프·추적은 대부분 엔진 기능으로 대체된다.

- **프로젝트 스트레치 모드는 `disabled`.** 뷰포트를 실제 화면 픽셀로 두고, 배율은 카메라가 담당한다(벡터 선이 항상 선명해야 한다).
- **배율:** `scale = min(화면폭 / 400, 사용가능높이 / 760)`, `camera.zoom = Vector2(scale, scale)`. 사용 가능 높이는 상단 HUD와 안전 영역을 뺀 값. 1~4단계(최대 400×760)는 대부분의 폰에서 한 화면에 들어오고, 5·6단계는 스크롤된다.
- 화면이 가로로 넓은 기기(태블릿·데스크톱)는 이 배율 그대로 가운데 정렬하고 좌우 여백은 검정.
- **클램프:** `limit_left/top/right/bottom`을 맵 사각형으로 설정. 맵이 뷰포트보다 작은 축은 엔진이 자동으로 가운데 정렬하지 않으므로, 그 축은 `limit`을 뷰포트 중앙에 고정되도록 계산해 넣는다.
- **`ready` 진입 시:** 출발점을 중심으로. `reset_smoothing()`으로 전환 튐을 막는다.
- **`flying`:** 목표점 = 우주선 위치 + 속도 × 0.35(앞을 조금 더 보여줌). `position_smoothing_enabled = true`, `position_smoothing_speed = 6.0`으로 v3의 `cam += (목표 − cam) × (1 − e^(−6·dt))`와 같은 감쇠를 얻는다.
- **화면 이동·미니맵 이동 중에는 스무딩을 끈다**(즉시 반응해야 한다).
- **맵 경계 표시:** 맵 사각형을 옅은 선으로 그리고 모서리에 짧은 꺾쇠. 맵 밖은 사선 해칭으로 "벽"임을 표시.

## 12. 렌더링 명세

필드는 `scenes/play/field.gd`(`Node2D`) 하나의 `_draw()`에서 §12.2 순서대로 그린다. 노드를 요소마다 만들지 않는다 — 그리기 순서를 명시적으로 통제하기 위해서다. `queue_redraw()`는 프레임당 1회.

### 12.1 팔레트

| 토큰 | 값 | 용도 |
|---|---|---|
| `bg` | `#000000` | 배경 |
| `line` | `#E6EDF5` | 기본 선(행성, 소행성, 우주선, UI) |
| `line_dim` | `#E6EDF5` 30% | 맵 경계, 별, 비활성 요소 |
| `gravity` | `#4FC3F7` | 행성 중력 범위 |
| `hole` | `#B388FF` | 블랙홀 |
| `danger` | `#FF5252` | 외계인, 총알, 사격 범위, 실패 표시 |
| `goal` | `#FFD54F` | 목적지 |

- 선 굵기 1.5유닛(화면에서 최소 `dp(1)`), `draw_polyline`의 `antialiased = true`.
- **발광(기본):** 각 선을 두 번 그린다. 먼저 굵기 4유닛·투명도 18%로, 그 위에 굵기 1.5유닛 원색으로. 설정의 발광 효과가 "낮음"이면 바깥 선을 생략한다. `render/draw_lib.gd`의 헬퍼 하나로 처리한다.
- **`WorldEnvironment` 글로우는 기본값으로 쓰지 않는다.** 저사양 안드로이드에서 2D 글로우 후처리 비용이 크고, Compatibility 렌더러에서의 동작을 신뢰할 수 없다. M11에서 중급·저사양 기기 실측으로 60fps가 유지되는 것이 확인되면 설정의 발광 "보통"을 글로우 방식으로 교체하는 것을 **제안**하되, 이중 선 방식을 폴백으로 남긴다.
- 채우기는 쓰지 않는다. 예외는 블랙홀 지평선(검정 채움)뿐.

### 12.2 그리기 순서

별 배경 → 맵 경계 → 중력 범위 효과 → 외계인 사격 범위 → 궤적 → 소행성 → 행성 → 블랙홀 → 외계인 → 목적지 → 총알 → 예측선 → 우주선 → 연출 효과

미니맵은 별도 `CanvasLayer`에 그린다(화면 좌표, 카메라 영향을 받지 않아야 한다). HUD도 같은 `CanvasLayer` 계열.

### 12.3 요소별

- **별 배경:** 맵 크기에 비례해 1000유닛²당 약 0.2개, 1~1.5px 점, 카메라 이동의 30%만 따라 움직여 시차 효과. 위치는 `core/rng.gd`의 시드 난수로 만들어 매 실행 같게 한다.
- **행성:** 반경 `r`의 정`sides`각형 윤곽, 초당 6° 회전. `ring: true`면 기울어진 타원 고리(행성 뒤쪽 절반은 가려진 듯 생략).
- **중력 범위:** 반경 `R`의 점선 원(대시 4·간격 6, `gravity` 35%). 여기에 **안쪽으로 수축하는 원 3개**를 2.4초 주기로 엇갈려 그려 "끌려 들어감"을 표현(R에서 r로 줄어들며 투명도 0→40%→0).
- **블랙홀:** 반경 `rH` 검정 채움 + `hole` 윤곽, 주위에 회전하는 나선 호 3개. 중력 범위 효과는 `hole` 색, 1.2초 주기로 더 빠르게.
- **소행성:** `seed`로 만든 9~12꼭짓점 불규칙 다각형(꼭짓점 반경 r×0.75~1.15), 느리게 회전. 판정은 §5.4대로 원.
- **외계인:** 고전 비행접시 실루엣(너비 26유닛), `danger` 색. 사격 범위는 붉은 점선 원 20%. 비행 중 우주선이 범위 안에 들어오면 원이 60%로 밝아지고 맥동. 사격 순간 짧은 섬광.
- **총알:** 진행 방향 4유닛 짧은 선, `danger`.
- **목적지:** 서로 반대로 회전하는 두 겹 마름모 + 반경 `goal.r`에서 바깥으로 퍼지는 원 1.5초 주기, `goal` 색.
- **우주선:** 길이 14·폭 10 이등변 삼각형, 뒷변이 안쪽으로 파인 아스테로이드식. 발사 전엔 조준 각도, 비행 중엔 속도 방향.
- **발사대 행성(§5.9):** 반경 18유닛의 원. 돔 중심 방향 ±`ARC` 구간(우주선이 걸을 수 있는 표면)은 밝게, 뒤쪽 절반은 `line` 22%로 옅게 그려 작은 행성임을 보인다. 표면에 5° 간격 짧은 눈금, 15°마다 긴 눈금을 `gravity` 색으로 세운다 — **이 눈금이 곧 각도 눈금이므로 별도 계기판을 두지 않는다.** 걸을 수 있는 양 끝에는 더 긴 눈금으로 한계를 표시한다. 조준 중에는 눈금 전체가 밝아진다. 그리는 반경(18)은 `PAD_R`(22)보다 작아 우주선 꼬리가 표면에 묻힌다.
- **이륙 방향 표시:** 조준 중 우주선 코앞에서 바깥으로 16유닛 짧은 선, `goal` 색.
- **궤적:** 비행 중 1/30초마다 위치 기록, 최근 2.5초만 표시, 오래될수록 흐리게. 결과 화면 뒤에서도 남겨 두어 다음 시도의 단서가 되게 한다. 재시도 시 **직전 시도 궤적을 20% 투명도로 1회분 유지**.
- **예측선:** 0.05초 간격 점, 끝으로 갈수록 흐려짐. 충돌 예측 지점엔 × 표시. **점은 우주선에서 바깥으로 흐르게 한다**(위상을 시간에 따라 밀어 준다) — 정지한 점렬보다 "이쪽으로 나간다"가 즉시 읽힌다. 모션 줄이기(§12.4)를 켜면 흐름을 멈춘다.
- **폭발:** 우주선 삼각형을 이루던 선분 3개 + 파편 선 7개가 회전하며 흩어짐, 0.8초.
- **도착:** 우주선이 목적지 중심으로 빨려 들어가며 작아지고, 목적지 원이 크게 한 번 퍼짐, 0.8초.

폭발·도착 연출은 `Tween`으로 진행도만 만들고 그리기는 `_draw()`에서 한다. `GPUParticles2D`는 쓰지 않는다(선화 통일감과 저사양 기기 비용 때문).

### 12.4 모션 줄이기

설정에 **모션 줄이기** 항목을 둔다(§13.6). 켜면 중력 범위 수축 원·목적지 파동·섬광을 끄고 정적인 점선 원만 남긴다. 게임 규칙 정보(범위)는 그대로 보인다. 웹의 `prefers-reduced-motion`에 해당하는 OS 설정을 Godot에서 읽을 수 없으므로 앱 자체 설정으로 제공한다.

### 12.5 미니맵

- 맵이 뷰포트보다 큰 단계에서만 표시. HUD 재시작 버튼 아래 오른쪽 구석.
- 크기: 맵 비율 유지, 최대 너비 `dp(96)`·최대 높이 `dp(150)`. 반투명 검정 배경 + `line_dim` 테두리.
- 표시: 행성·블랙홀(점 + 중력 범위 옅은 원), 외계인(붉은 점), 목적지(노란 점), 우주선(흰 점, 비행 중 깜빡임), 현재 뷰포트(흰 사각형 윤곽). 소행성은 작은 회색 점.
- 입력은 §10.4.

## 13. UI와 문구

모든 화면은 안전 영역을 반영한다(`DisplayServer.get_display_safe_area()`를 읽어 루트 `Control`의 마진에 반영). 폰트는 시스템 한글 폰트, 숫자·로고만 `Oxanium`을 프로젝트에 포함(한글 폴백 필수). 공용 `ui/theme.tres`에 색·글꼴·버튼 스타일을 모은다.

### 13.1 타이틀

- 로고 "SWINGBY"를 벡터 선으로 그리고, 아래 작은 글씨로 "스윙바이".
- 배경에서 우주선 한 대가 행성을 스쳐 꺾여 나가는 데모가 반복 재생.
- 버튼: **시작하기**

### 13.2 단계 선택

- 상단에 장 탭(1장 행성, 2장 블랙홀 …). 탭 아래에 단계 카드 그리드(초반부 8칸은 2열 4행, 후반부 10칸은 2열 5행).
- 카드: 단계 ID, 이름, 클리어 표시(✓), 잠김 표시.
- 단계는 순서대로 열린다. 장의 마지막 단계를 클리어하면 다음 장 탭이 열린다. `OS.is_debug_build()`이고 `--dev` 인자가 있으면 전부 열림.
- 장 탭 옆 `?` 버튼으로 그 장의 새 요소 소개 카드(§7.4)를 다시 볼 수 있다.
- 상단 뒤로 버튼 → 타이틀.

### 13.2.1 새 요소 소개 카드

- `meta.intro`가 있는 단계를 처음 시작할 때, 게임 화면 위에 카드 한 장을 띄운다. 요소 그림(해당 요소를 벡터로 작게 애니메이션) + 제목 + 설명 한두 문장 + **확인** 버튼.
- 본 기록은 저장 데이터 `seen_intros`에 남긴다.

### 13.3 HUD (플레이 중)

- 좌상단: 뒤로 버튼(단계 선택으로), 단계 표기 `1-1 첫 스윙바이`
- 우상단: 힌트 버튼(전구 아이콘, 받은 힌트가 있으면 작은 점 표시), 재시작 버튼(원형 화살표 아이콘)
- 조준 중 화면 하단: `각도 23.5°`
- 첫 시도의 `ready` 상태에서만 하단에 레벨 `hint` 표시, 조준 시작하면 사라짐.
- 버튼은 최소 `dp(44)` × `dp(44)` 터치 영역.

| 항목 | 설명 문구 | 버튼 상태 |

## 14. 광고와 힌트

### 14.1 원칙

- 광고는 흐름을 끊지 않는 곳에만 둔다. **조준·비행 중 화면에는 어떤 광고도 없다.**
- 수익의 중심은 **보상형 광고**(플레이어가 원해서 보는 광고)다. 전면 광고는 빈도를 엄격히 제한한다.
- 배너 광고는 쓰지 않는다. 한 손가락 터치 게임이라 실수 클릭 위험이 크고 화면도 좁다.
- 광고 판단 로직은 `monetization/`의 순수 함수로 작성하고 테스트한다. 실제 SDK 호출은 `platform/ads.gd` 인터페이스 뒤에 둔다.
- 광고를 불러오지 못하거나 오프라인이어도 게임은 완전히 동작해야 한다.

### 14.2 광고 제공자 구조

GDScript에는 인터페이스가 없으므로 `platform/ads.gd`를 **기본 구현이 모두 실패를 반환하는 베이스 클래스**로 두고 상속한다.

```
class_name AdProvider extends RefCounted
# RewardPlacement: "hint_preview" | "hint_direction" | "skip"
func init_ads() -> void                                  # 동의 절차 포함
func is_rewarded_ready() -> bool
func show_rewarded(placement: String) -> String           # "rewarded" | "dismissed" | "failed"
func is_interstitial_ready() -> bool
func show_interstitial() -> String                        # "shown" | "failed"
func can_open_privacy_options() -> bool
func open_privacy_options() -> void
```

- 비동기 결과는 `await`로 받는다(`show_rewarded`는 코루틴). 호출 측은 반드시 타임아웃(10초)을 걸고, 초과하면 `"failed"`로 처리한다.
- **AdMockProvider** (`ads_mock.gd`, 에디터·디버그 빌드): 화면에 "테스트 광고" 오버레이를 2초 띄운 뒤 결과 반환. 실행 인자 `--ads=fail`이면 항상 실패, `--ads=dismiss`면 항상 중간에 닫힘, `--ads=slow`면 5초 지연. 예외 흐름 확인용.
- **AdMobProvider** (`ads_admob.gd`, 앱): Godot용 AdMob 플러그인(예: `poing-studios/godot-admob-android`, iOS는 대응 플러그인)으로 구현. **착수 시점에 Godot 버전과 호환되는 플러그인 버전을 확인해 `CLAUDE.md`에 고정 기록한다.** 이 플러그인은 커뮤니티 유지보수이므로 Godot 업그레이드 시 호환성을 먼저 확인한다(§21의 위험 항목).
- 개발·비공개 테스트 빌드는 **반드시 구글이 제공하는 테스트 광고 ID**를 쓴다. 실제 광고 단위 ID는 출시 빌드에서만.
- 광고 단위 ID는 `platform/ads_config.gd`(git 제외)에서 읽고, 형식 예시 `ads_config.example.gd`를 저장소에 둔다.

### 14.3 보상형 광고: 힌트와 건너뛰기

| 항목 | 효과 | 열리는 조건 | 유지 |
|---|---|---|---|
| 긴 예측선 | 이 단계의 예측선 길이가 2.5초로 늘어남 | 언제든 | 이 단계에 영구 적용 |
| 방향 표시 | 조준할 때 우주선 둘레에 성공 발사 방향을 초록 호로 표시. 공전 단계는 공전 궤도 위에 "이 구간에 있을 때 발사" 표시도 추가 | 이 단계에서 2회 이상 실패 | 이 단계에 영구 적용 |
| 건너뛰기 | 이 단계를 `skipped`로 기록하고 다음 단계를 엶 | 이 단계에서 5회 이상 실패 | 나중에 직접 클리어하면 `cleared`로 바뀜 |

- 방향 표시의 호는 `meta.solution.angle`을 중심으로 `meta.metrics.main_window`의 80% 폭으로 그린다(구간 가장자리는 불안정하므로). 공전 표시는 `meta.metrics.timing_range`를 공전 각도로 바꿔 그린다.
- **첫 힌트 무료:** 게임 전체에서 처음 쓰는 힌트(긴 예측선 또는 방향 표시) 1회는 광고 없이 준다. 건너뛰기는 해당 없음.
- 광고를 끝까지 보지 않고 닫으면 보상 없음.
- 모든 단계가 `cleared` 또는 `skipped`면 다음 장이 열린다. 단계 선택 카드에서 건너뛴 단계는 ↷ 표시로 구분한다.

### 14.4 전면 광고 규칙 (`ad_policy.should_show_interstitial`)

전면 광고는 **성공 후 [다음 단계]로 넘어갈 때만** 검토하고, 아래를 **모두** 만족할 때만 보여준다.

1. 넘어가는 단계가 2장 이후다(1장 전체는 광고 없음).
2. 마지막 전면 광고 이후 클리어 3회 이상.
3. 마지막 전면 광고 이후 180초 이상.
4. 앱 실행 후 120초 이상.
5. 최근 90초 안에 보상형 광고를 보지 않았다.
6. 넘어가는 단계에 새 요소 소개 카드가 뜨지 않는다.

- 실패 후 재시도, 단계 선택으로 이동, 앱 복귀, 앱 시작 시에는 절대 호출하지 않는다.
- 광고가 준비되지 않았으면 기다리지 않고 바로 다음 단계로 넘어간다.
- 수치(3회, 180초, 120초, 90초)는 `monetization/ad_policy_config.gd` 한곳에 모은다.
- 시각은 `Time.get_ticks_msec()`가 아니라 **호출자가 넘긴 값**으로 판단한다(순수 함수 유지, 테스트 가능).

### 14.5 동의와 개인정보

- 첫 실행 시 Google UMP(사용자 메시지 플랫폼) 동의 절차를 거친다. 양식은 법적으로 필요한 지역 사용자에게만 뜬다. 이어서 iOS에서는 앱 추적 투명성(ATT) 요청을 띄운다. 거부하면 비개인화 광고로 동작한다.
- iOS 추적 요청 문구(`NSUserTrackingUsageDescription`): "맞춤 광고를 보여드리는 데 사용돼요. 허용하지 않아도 게임은 똑같이 즐길 수 있어요."
- 설정 화면의 **개인정보 옵션**으로 동의 양식을 다시 열 수 있다(해당 지역에서만 표시).
- 게임 코드 자체는 개인정보를 수집·전송하지 않는다. 수집 주체는 광고 SDK뿐이며, 스토어 신고(§15.4)도 이 기준으로 작성한다.

### 14.6 테스트 (`test_ad_policy.gd`, `test_hints.gd`)

- 전면 광고 규칙 1~6 각각의 경계값(예: 179초 거부, 180초 허용).
- 실패 후 재시도 경로에서 전면 광고 판단이 호출되지 않음.
- 힌트 열림 조건(실패 2회, 5회), 첫 힌트 무료 1회, 건너뛰기 후 다음 단계·다음 장 열림 판정.
- 보상형 결과가 `dismissed` 또는 `failed`면 보상이 주어지지 않음.

## 15. 플랫폼과 스토어 출시

### 15.1 앱 빌드 (Godot 익스포트)

v3의 Capacitor 앱 셸은 필요 없다. Godot의 안드로이드 익스포트가 그 역할을 한다.

- **Android를 먼저** 빌드한다. iOS는 Mac과 Xcode 환경이 준비되면 추가하며, 그때 게임 코드 변경 없이 익스포트 프리셋만 추가되도록 유지한다.
- 착수 시 Godot 안정 버전과 AdMob 플러그인 호환 버전을 확인해 `CLAUDE.md`에 고정 기록한다. **버전을 올릴 때는 플러그인 호환을 먼저 확인한다.**
- 익스포트 설정:
  - 렌더러 **Compatibility (GLES3)**
  - 아키텍처 **arm64-v8a만** (armeabi-v7a 제외 — 설치 크기 절감, §18)
  - 세로 고정: `display/window/handheld/orientation = portrait`
  - `display/window/stretch/mode = disabled` (§11)
  - `application/run/low_processor_mode = false` (게임 루프가 계속 돈다)
  - 익스포트 필터에서 `addons/swingby_editor/`, `addons/gdUnit4/`, `tests/`, `tools/`, `recipes/`, `candidates/`, `docs/` 제외
- 앱 이름 "스윙바이", 앱 ID `com.<개발자명>.swingby`(출시 전 사용자와 확정).

### 15.2 플랫폼 계층 (`platform/`)

엔진이 대부분을 제공하므로 v3보다 계층이 얇다. 저장·진동·생명주기는 전용 모듈 없이 엔진 API를 직접 쓰되, 광고만 인터페이스로 감싼다.

| 모듈 | 앱 | 에디터·디버그 |
|---|---|---|
| 저장 (`save/save.gd`) | `user://swingby.save.v1.json` + `FileAccess` | 같음 |
| `haptics.gd` | `Input.vibrate_handheld(ms)` | 아무 동작 안 함 |
| `lifecycle.gd` | `NOTIFICATION_APPLICATION_PAUSED/RESUMED`, `NOTIFICATION_WM_GO_BACK_REQUEST` | `NOTIFICATION_APPLICATION_FOCUS_OUT/IN` |
| `ads.gd` | `AdMobProvider` | `AdMockProvider` |
| `dp.gd` | §10.0 환산 | 1.0 |

- **저장:** 앱 시작 시 한 번 읽어 메모리에 두고, 변경 시 500ms 디바운스로 기록. `pause` 시 즉시 기록. 읽기 실패·JSON 파싱 실패 시 기본값으로 시작하고 손상 파일은 `.bak`으로 옮긴다.
- **생명주기:** `paused` 시 시뮬레이션 일시정지, 누산기 리셋, 소리 끄기. `resumed` 시 그대로 이어서 진행(고정 스텝이라 결과가 달라지지 않음).
- **Android 뒤로 버튼:** `NOTIFICATION_WM_GO_BACK_REQUEST`를 받아 힌트 시트·결과 화면 닫기 → 플레이에서 단계 선택 → 단계 선택에서 타이틀 → 타이틀에서 "게임을 종료할까요?" 확인. 프로젝트 설정의 `quit_on_go_back`은 **끈다**(직접 처리해야 한다).
- **진동:** 발사 시 가벼운 충격(20ms), 게임오버 시 강한 충격(60ms), 도착 시 성공 알림(짧게 2회). 설정에서 끌 수 있다. iOS는 `vibrate_handheld`의 동작이 제한적이므로 M12에서 실기기 확인.

### 15.3 성능 규칙

- `WorldEnvironment` 글로우 기본 사용 금지. 발광은 §12.1의 이중 선 방식.
- 요소마다 노드를 만들지 않고 `field.gd` 한 곳의 `_draw()`에서 그린다. `queue_redraw()`는 프레임당 1회.
- 매 프레임 객체 할당 최소화: 예측선·궤적 점 배열은 `PackedVector2Array`를 미리 잡아 재사용한다.
- 폰트·텍스처를 프레임 중에 처음 로드하지 않도록 `Play` 진입 전에 예열한다.
- 목표: 중급 Android 기기에서 60fps, 저사양 기기에서 발광 "낮음" 설정 시 50fps 이상.

### 15.4 출시 준비물 (`store/` 폴더)

Claude Code가 초안을 만들고 사용자가 확인한다.

- **아이콘·스플래시:** 벡터 선화 우주선과 휘어진 궤도. 1024px 원본에서 플랫폼별 크기 생성.
- **스크린샷 구성안 5장:** 스윙바이 궤적, 블랙홀, 외계인, 넓은 맵과 미니맵, 단계 선택. 실제 게임 화면에 짧은 한국어 문구.
- **스토어 문구:** 짧은 설명, 전체 설명, 검색 키워드.
- **개인정보처리방침(한국어):** 게임은 개인정보를 직접 수집하지 않고 광고 SDK가 광고 식별자 등을 처리한다는 내용과 문의처. 공개 URL이 필요하므로 정적 호스팅(예: GitHub Pages)에 올릴 수 있는 HTML로 작성.
- **데이터 보안·개인정보 라벨 메모:** 구글 플레이 데이터 보안 양식과 애플 개인정보 라벨에 적을 항목을, 착수 시점의 AdMob 공식 안내 기준으로 정리.

- **등급 설문:** 구글 플레이와 앱스토어의 연령 등급 설문. "광고 포함" 표시.
- **오픈소스 고지:** Godot(MIT)과 사용한 애드온의 라이선스 고지를 설정 화면이나 스토어 문구에 포함한다. (v3에는 없던 항목 — 엔진 사용으로 새로 필요해졌다.)

## 16. 검증 도구와 테스트

모든 CLI 도구는 `SceneTree`를 상속한 스크립트이고 `_initialize()`에서 실행 후 `quit(코드)`한다. 인자는 `OS.get_cmdline_user_args()`로 받는다(`--` 뒤의 인자).

### 16.1 `./run.sh solve [단계ID]`

- 각도 −180°~180°를 0.25° 간격으로 전부 시뮬레이션해 결과별 개수와 **성공 연속 구간**을 출력한다.
- 공전 행성이 있는 단계는 주기를 12등분한 발사 시점마다 반복한다.
- 출력 예: `1-1 첫 스윙바이  t=0.00  성공: -69.25..-62.5 (7.00°)  {wall:1219, rock:128, planet:65, win:28}`
- 이 출력이 §6.2 표와 일치하는 것이 M1의 완료 기준이다.

### 16.2 `./run.sh fan <단계> [시작각] [끝각] [간격]` (선택)

궤적을 결과별 색으로 그린 SVG를 `tools/out/`에 저장. 레벨 디자인 시 눈으로 확인하는 용도. SVG는 문자열로 직접 써서 저장한다(렌더링 불필요).

### 16.3 `./run.sh validate [단계ID|장번호]`

- §8.5 필수 규칙과 경고를 검사하고 표로 출력한다. 인자가 없으면 `chapters.gd`에 등록된 전 단계.
- 실패가 하나라도 있으면 종료 코드 1. 커밋 전에 반드시 실행한다.

### 16.4 `./run.sh gen --recipe <파일> --slot <칸> [--count N] [--seeds N]`

- §8.4 알고리즘. 결과를 `candidates/<단계ID>/cand-XX.json`과 `summary.md`(지표 표), `cand-XX.svg`(궤적 썸네일)로 저장한다.
- 10초마다 진행률 한 줄 출력(§8.4).

### 16.5 테스트 (`./run.sh test`, gdUnit4)

**test_physics.gd**
- 중력 범위 밖(`r ≥ R`)에서 가속도 0.
- `r = R/2`에서 크기 `g × 0.25`.
- 공전 행성 `t = period`일 때 위치가 `t = 0`과 같음.

**test_determinism.gd**
- 같은 단계·각도·발사 스텝으로 두 번 시뮬레이션하면 결과와 최종 스텝 수가 동일.
- 예측선(`predict`)의 모든 점이 같은 조건의 실제 비행 경로 앞부분과 정확히 일치.
- **같은 레벨 객체로 시뮬레이션을 반복해도 결과가 같다**(§5.5의 `next_fire` 분리가 지켜졌는지 확인. v4에서 추가).

**test_levels.gd** — 회귀 기준(부록 A 참조 구현으로 확인된 값)과 전 단계 정답 확인

| 단계 ID | 각도 | launch_step | 기대 결과 |
|---|---|---|---|
| 1-1 | −66 | 0 | win |
| 1-4 | −134 | 0 | win |
| 2-1 | −75.5 | 0 | win |
| 3-1 | −30 | 0 | win |
| 4-1 | −44 | 800 | win |
| 4-1 | −44 | 0 | planet |
| 5-1 | −12 | 0 | win |

추가로 위 6개 단계의 성공 연속 구간 최대 폭이 §6.2 표 값에서 ±0.5° 이내인지 검사한다(4-1은 launch_step 800 기준 **9.5°**, 발사대 행성 도입 후 값이다). 그리고 `chapters.gd`에 등록된 **모든 단계의 `meta.solution`이 `win`** 인지 검사한다(빠른 검사, 전수 스캔은 `validate`가 담당).

**test_metrics.gd**
- 사전 검증 6단계에 대해 `essential`, `clearance`, 비행 시간이 §8.5 실측값 범위와 일치.
- 난이도 점수 공식이 알려진 입력에 대해 기대값을 반환.

- **완료 기준:** 에디터에서 빈 검은 화면이 뜨고, `./run.sh test`가 통과(빈 테스트)하며, 벤치마크 수치를 보고하고 위 표의 판단을 사용자와 확인했다.

**M0 실행 결과 (2026-09-17)**

Godot 4를 구할 수 없는 환경이어서(네트워크 정책상 github.com 차단) Godot 3.5.2 headless로 트랜스리터레이션을 돌려 대신 측정했다. GDScript는 3.x·4.x 모두 `float`이 double이므로 정확성 검증은 그대로 유효하다.

| 항목 | 결과 |
|---|---|
| 정확성 | **통과.** 1-1과 5-1 모두 성공 구간과 결과별 개수가 §6.2·부록 C와 **완전히 일치** |
| 속도 (상한) | 1-1 **4.90초**, 5-1 **9.01초** (Godot 3.5, 무타입, Xeon 2.10GHz) |
| Godot 4 예상 | 1-1 **1.2~2.5초** (§8.9) |
| 관문 판단 | **> 5초 아님 → GDScript 단독 진행.** ≤2초인지 2~5초인지는 사용자가 `./run.sh bench`로 확정 |

정확성이 먼저 통과한 것이 이 마일스톤의 가장 큰 소득이다. §2.1(`Vector2` 금지, double 사용)이 실제로 부록 A의 값을 재현한다는 것을 코드를 더 쓰기 전에 확인했다.

남은 확인 두 가지는 사용자 환경에서 해야 한다.
1. `./run.sh bench` — Godot 4에서의 확정 수치와 §17 M0 판단표 적용.
2. gdUnit4 설치 — 이 환경에서 내려받을 수 없어 `addons/`가 비어 있다(§16.5).

## 20.1 v4.1 변경 — 발사대 행성

데모(조작 감각 확인용 프로토타입)로 조준 방식을 세 가지 시험한 결과다.

1. **골프식 홀드 스윕**(누르고 있으면 각도가 돌아감) — 시험 후 **버렸다.** 성공 폭이 7~11°인 게임에서 각도가 저절로 돌면 플레이어가 각도를 고르는 게 아니라 잡아채게 되어, 정밀 조준 퍼즐이 타이밍 게임으로 바뀐다. 4장은 공전 타이밍과 겹쳐 이중 타이밍이 된다.
2. **반원 계기판**(우주선은 제자리, 바늘만 회전) — 동작은 하지만 "각도를 설정한다"는 느낌이라 버렸다.
3. **발사대 행성**(우주선이 표면을 걸어 다니다 그 자리에서 이륙) — **채택.** 각도가 설정값이 아니라 우주선이 서 있는 위치가 된다.

바뀐 절: §1(플레이어가 정하는 것), §4(θ의 정의), §5.1(`PAD_R`, `ARC` 추가), **§5.9 신설**, §6.2(4-1 기준값과 돔 반경 측정), §8.4(배치 제약 `PAD_R + 30`, 목적지 ±`ARC` 검사), §8.5(규칙 8 재정의 + 규칙 9 추가 + 경고 추가), §10.1~10.3(어디든 터치, 화면 이동 삭제), §12.3(발사대 행성, 흐르는 예측선), §16.5(4-1 폭 9.5°).

**부작용 하나:** §10.3의 "빈 곳을 끌어 화면 이동"이 사라졌다. 어디를 눌러도 조준되는 것과 양립할 수 없다. 큰 맵은 미니맵으로만 살펴본다. M4에서 실기기로 확인해 부족하면 그때 보완한다.

## 부록 A. 물리 참조 구현 (검증 완료, JavaScript)

**이것이 정답의 기준이다.** GDScript로 옮길 때 로직과 연산 순서를 그대로 유지한다. 이식 초안은 부록 D.

```js
// ===== 결정론적 물리 코어 (게임과 검증기에서 공용) =====
const DT = 1/240;
const SHIP_R = 5;
const MAX_FLIGHT = 30;

function dist(ax,ay,bx,by){ const dx=ax-bx, dy=ay-by; return Math.sqrt(dx*dx+dy*dy); }
function bodyPos(b, t){
  if(!b.orbit) return [b.x, b.y];
  const o = b.orbit, a = o.phase + 2*Math.PI*t/o.period;
  return [o.cx + o.rad*Math.cos(a), o.cy + o.rad*Math.sin(a)];
}
function gravs(L){ return (L.planets||[]).concat(L.holes||[]); }
function accel(G, x, y, t){
  let ax=0, ay=0;
  for(const b of G){
    const [bx,by] = bodyPos(b,t);
    const dx=bx-x, dy=by-y, r2=dx*dx+dy*dy, R2=b.R*b.R;
    if(r2>=R2 || r2<1) continue;
    const r=Math.sqrt(r2), f=1-r/b.R, m=b.g*f*f;
    ax+=m*dx/r; ay+=m*dy/r;
  }
  return [ax,ay];
}
// 우주선 1스텝 + 충돌 판정 (총알 제외). 반환: null=계속, 문자열=결과
function stepShip(L, G, s, t){
  const [ax,ay]=accel(G,s.x,s.y,t);
  s.vx+=ax*DT; s.vy+=ay*DT; s.x+=s.vx*DT; s.y+=s.vy*DT;
  const tt=t+DT;
  for(const p of (L.planets||[])){ const [px,py]=bodyPos(p,tt); if(dist(px,py,s.x,s.y)<p.r+SHIP_R) return 'planet'; }
  for(const h of (L.holes||[])){ if(dist(h.x,h.y,s.x,s.y)<h.rH+2) return 'hole'; }
  for(const a of (L.rocks||[])){ if(dist(a.x,a.y,s.x,s.y)<a.r*0.85+SHIP_R) return 'rock'; }
  for(const u of (L.ufos||[])){ if(dist(u.x,u.y,s.x,s.y)<13+SHIP_R) return 'ufo'; }
  if(s.x<SHIP_R||s.y<SHIP_R||s.x>L.w-SHIP_R||s.y>L.h-SHIP_R) return 'wall';
  if(dist(L.goal.x,L.goal.y,s.x,s.y)<L.goal.r) return 'win';
  return null;
}
function fireUfos(L, st, ship, ft){
  for(const u of (L.ufos||[])){
    if(u._next===undefined) u._next=u.delay;
    while(ft>=u._next){
      const dx=ship.x-u.x, dy=ship.y-u.y, d=Math.sqrt(dx*dx+dy*dy);
      if(d<u.range) st.bullets.push({x:u.x,y:u.y,vx:dx/d*u.bs,vy:dy/d*u.bs,age:0});
      u._next+=u.interval;
    }
  }
}
function stepBullets(L, st, ship){
  for(const b of st.bullets){ b.x+=b.vx*DT; b.y+=b.vy*DT; b.age+=DT; }
  st.bullets=st.bullets.filter(b=>b.age<5&&b.x>-20&&b.y>-20&&b.x<L.w+20&&b.y<L.h+20);
  for(const b of st.bullets){ if(dist(b.x,b.y,ship.x,ship.y)<3+SHIP_R) return 'shot'; }
  return null;
}
// 전체 비행 시뮬레이션 (검증용)
function simulate(L, angleDeg, launchStep){
  const G=gravs(L);
  for(const u of (L.ufos||[])) delete u._next;
  const a=angleDeg*Math.PI/180;
  const s={x:L.start.x,y:L.start.y,vx:Math.cos(a)*L.speed,vy:Math.sin(a)*L.speed};
  const st={bullets:[]};
  let t=launchStep*DT, n=0, maxN=MAX_FLIGHT/DT;
  while(n<maxN){
    const r=stepShip(L,G,s,t); t+=DT; n++;
    if(r) return r;
    fireUfos(L,st,s,n*DT);
    const rb=stepBullets(L,st,s); if(rb) return rb;
  }
  return 'drift';
}
if(typeof module!=='undefined') module.exports={DT,SHIP_R,MAX_FLIGHT,bodyPos,gravs,accel,stepShip,fireUfos,stepBullets,simulate};
```

```js
const S = require('./sim.js');
const LEVELS = require('./levels.js');
const which = process.argv[2] !== undefined ? [parseInt(process.argv[2]) - 1] : LEVELS.map((_, i) => i);

  const L = LEVELS[i];

  const launches = orbiting
    ? Array.from({ length: 12 }, (_, k) => Math.round(k * Math.abs(orbiting.orbit.period) / 12 / S.DT))
    : [0];
  for (const ls of launches) {
    const counts = {}, wins = [];
    for (let a = -180; a < 180; a += 0.25) {
      const r = S.simulate(L, a, ls);
      counts[r] = (counts[r] || 0) + 1;
      if (r === 'win') wins.push(a);
    }
    const runs = [];
    for (const a of wins) {
      const last = runs[runs.length - 1];
      if (last && Math.abs(a - last[1] - 0.25) < 1e-6) last[1] = a; else runs.push([a, a]);
    }
    const txt = runs.map(([s, e]) => `${s}..${e} (${(e - s + 0.25).toFixed(2)}°)`).join(' ');
    console.log(`L${i + 1} ${L.name}  t=${(ls * S.DT).toFixed(2)}  성공: ${txt || '없음'}  ${JSON.stringify(counts)}`);
```

## 부록 D. GDScript 이식 초안 (미검증)

> **이 코드는 아직 실행해 검증하지 않았다.** M0의 벤치마크와 M1의 §6.2 일치 확인을 통과해야 확정된다. 부록 A가 기준이고 이 코드가 기준이 아니다. 차이가 나면 이 초안을 고친다.

설계 메모:

- 레벨을 `Dictionary`로 받는다. 부록 A와 1:1로 대조하기 위해서다. M1에서 `core/level.gd`의 타입 있는 객체로 감싸되, **산술 표현은 한 글자도 바꾸지 않는다**(딕셔너리 조회를 필드 접근으로 바꾸는 것만 허용).
- `Vector2`를 쓰지 않는다. 모든 상태는 `PackedFloat64Array`(64비트)다. §2.1.
- 외계인의 다음 사격 시각은 레벨 객체가 아니라 `_next_fire`에 둔다. 부록 A는 `u._next`로 레벨을 변경하는데, 그러면 `WorkerThreadPool` 병렬 스캔에서 레벨을 공유할 수 없다. §5.5.
- `deg_to_rad()`, `TAU`, `Vector2.distance_to()`를 쓰지 않는다. 값은 같더라도 연산 순서를 부록 A와 눈으로 대조할 수 있어야 한다.
- `n * DT`는 **곱셈으로 유지한다.** 누산(`ft += DT`)으로 바꾸면 부동소수점 오차가 쌓여 결과가 달라진다.
- `MAX_FLIGHT / DT`는 배정밀도에서 정확히 `7200.0`이다(v4에서 확인). 그래도 부록 A와 같게 float 비교로 둔다.
- 스크래치 버퍼를 인스턴스 필드로 둬 루프 안 할당을 없앴다. M0 벤치마크가 느리면 `_body_pos`·`_accel`을 `_step_ship` 안으로 인라인하는 것을 먼저 시도한다 — 단, **연산 순서는 유지**한다.

```gdscript
# core/sim.gd — 부록 A의 1:1 이식 초안
class_name Sim
extends RefCounted

const DT := 1.0 / 240.0
const SHIP_R := 5.0
const MAX_FLIGHT := 30.0

var _bp := PackedFloat64Array([0.0, 0.0])              # body_pos 결과
var _ac := PackedFloat64Array([0.0, 0.0])              # accel 결과
var _ship := PackedFloat64Array([0.0, 0.0, 0.0, 0.0])  # x, y, vx, vy
var _bullets := PackedFloat64Array()                   # 5개씩 [x, y, vx, vy, age]
var _next_fire := PackedFloat64Array()                 # 외계인별 다음 사격 시각

static func dist(ax: float, ay: float, bx: float, by: float) -> float:
	var dx := ax - bx
	var dy := ay - by
	return sqrt(dx * dx + dy * dy)

func _body_pos(b: Dictionary, t: float) -> void:
	if not b.has("orbit"):
		_bp[0] = b["x"]
		_bp[1] = b["y"]
		return
	var o: Dictionary = b["orbit"]
	var a: float = o["phase"] + 2.0 * PI * t / o["period"]
	_bp[0] = o["cx"] + o["rad"] * cos(a)
	_bp[1] = o["cy"] + o["rad"] * sin(a)

func _accel(gravs: Array, x: float, y: float, t: float) -> void:
	var ax := 0.0
	var ay := 0.0
	for b in gravs:
		_body_pos(b, t)
		var dx: float = _bp[0] - x
		var dy: float = _bp[1] - y
		var r2: float = dx * dx + dy * dy
		var b_range: float = b["R"]
		var r2_max: float = b_range * b_range
		if r2 >= r2_max or r2 < 1.0:
			continue
		var r: float = sqrt(r2)
		var f: float = 1.0 - r / b_range
		var m: float = b["g"] * f * f
		ax += m * dx / r
		ay += m * dy / r
	_ac[0] = ax
	_ac[1] = ay

# 반환 "" = 계속, 그 외 = 결과 문자열
func _step_ship(level: Dictionary, gravs: Array, t: float) -> String:
	_accel(gravs, _ship[0], _ship[1], t)
	_ship[2] += _ac[0] * DT
	_ship[3] += _ac[1] * DT
	_ship[0] += _ship[2] * DT
	_ship[1] += _ship[3] * DT
	var tt: float = t + DT
	var sx: float = _ship[0]
	var sy: float = _ship[1]
	for p in level.get("planets", []):
		_body_pos(p, tt)
		if dist(_bp[0], _bp[1], sx, sy) < p["r"] + SHIP_R:
			return "planet"
	for h in level.get("holes", []):
		if dist(h["x"], h["y"], sx, sy) < h["rH"] + 2.0:
			return "hole"
	for a in level.get("rocks", []):
		if dist(a["x"], a["y"], sx, sy) < a["r"] * 0.85 + SHIP_R:
			return "rock"
	for u in level.get("ufos", []):
		if dist(u["x"], u["y"], sx, sy) < 13.0 + SHIP_R:
			return "ufo"
	if sx < SHIP_R or sy < SHIP_R or sx > level["w"] - SHIP_R or sy > level["h"] - SHIP_R:
		return "wall"
	var goal: Dictionary = level["goal"]
	if dist(goal["x"], goal["y"], sx, sy) < goal["r"]:
		return "win"
	return ""

func _fire_ufos(ufos: Array, ft: float) -> void:
	for i in ufos.size():
		var u: Dictionary = ufos[i]
		while ft >= _next_fire[i]:
			var dx: float = _ship[0] - u["x"]
			var dy: float = _ship[1] - u["y"]
			var d: float = sqrt(dx * dx + dy * dy)
			if d < u["range"]:
				var bs: float = u["bs"]
				_bullets.append(u["x"])
				_bullets.append(u["y"])
				_bullets.append(dx / d * bs)
				_bullets.append(dy / d * bs)
				_bullets.append(0.0)
			_next_fire[i] += u["interval"]

# 부록 A와 같은 순서: 전부 이동 → 수명·범위로 거르기 → 살아남은 것만 피격 판정
func _step_bullets(level: Dictionary) -> String:
	var w: float = level["w"]
	var h: float = level["h"]
	var count: int = _bullets.size() / 5
	var kept: int = 0
	for i in count:
		var o: int = i * 5
		_bullets[o] += _bullets[o + 2] * DT
		_bullets[o + 1] += _bullets[o + 3] * DT
		_bullets[o + 4] += DT
		var bx: float = _bullets[o]
		var by: float = _bullets[o + 1]
		if _bullets[o + 4] < 5.0 and bx > -20.0 and by > -20.0 and bx < w + 20.0 and by < h + 20.0:
			if kept != i:
				var d: int = kept * 5
				for k in 5:
					_bullets[d + k] = _bullets[o + k]
			kept += 1
	_bullets.resize(kept * 5)
	for i in kept:
		var o: int = i * 5
		if dist(_bullets[o], _bullets[o + 1], _ship[0], _ship[1]) < 3.0 + SHIP_R:
			return "shot"
	return ""

# 전체 비행 시뮬레이션. gravs는 호출자가 한 번 만들어 재사용하면 더 빠르다.
func simulate(level: Dictionary, angle_deg: float, launch_step: int) -> String:
	var gravs: Array = []
	gravs.append_array(level.get("planets", []))
	gravs.append_array(level.get("holes", []))
	var ufos: Array = level.get("ufos", [])

	_next_fire.resize(ufos.size())
	for i in ufos.size():
		_next_fire[i] = ufos[i]["delay"]
	_bullets.resize(0)

	var a: float = angle_deg * PI / 180.0
	var start: Dictionary = level["start"]
	_ship[0] = start["x"]
	_ship[1] = start["y"]
	_ship[2] = cos(a) * level["speed"]
	_ship[3] = sin(a) * level["speed"]

	var t: float = launch_step * DT
	var n: int = 0
	var max_n: float = MAX_FLIGHT / DT
	while n < max_n:
		var r: String = _step_ship(level, gravs, t)
		t += DT
		n += 1
		if r != "":
			return r
		_fire_ufos(ufos, n * DT)
		var rb: String = _step_bullets(level)
		if rb != "":
			return rb
	return "drift"
```
