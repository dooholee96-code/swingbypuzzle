# 스윙바이 퍼즐 게임 — Claude Code 개발 계획 (v5, TypeScript/웹)

> 이 문서는 Claude Code에게 주는 개발 지시서다. 프로젝트 루트의 `docs/PLAN.md`로 저장하고, 마일스톤 단위로 작업을 요청한다. v2에서 스테이지 구성(§7)과 제작 파이프라인(§8)을, v3에서 광고와 힌트(§14), 플랫폼과 스토어 출시(§15)를 추가했고, v4에서 구현 스택을 Godot 4 + GDScript로 교체했다. **v5에서 다시 TypeScript + Vite + Canvas 2D로 돌아오고, 웹을 개발 수단이 아니라 첫 번째 출시 형태로 올렸다**(§2, §15, §21 참조). 물리 코어와 레벨 데이터는 사전에 시뮬레이션으로 검증을 마친 참조 구현이 부록에 포함되어 있으며, **숫자와 공식을 임의로 바꾸지 않는다.** 문서 안의 `§8.4` 같은 표기는 이 문서의 절 번호이고, `2장`, `2-3` 같은 표기는 게임의 장과 단계를 뜻한다.

## 0. Claude Code 작업 규칙

1. 마일스톤(§17) 순서대로 진행한다. 한 마일스톤이 끝나면 **멈추고**, 무엇을 만들었는지와 폰에서 확인하는 방법을 요약한 뒤 다음 지시를 기다린다.
2. 각 마일스톤 시작 시 계획을 먼저 짧게 제시하고, 이 문서와 다른 판단이 필요하면 구현 전에 이유와 함께 묻는다.
3. `src/core/`, `src/tools-shared/`, `src/monetization/`은 **DOM·브라우저 API·Node API를 절대 쓰지 않는** 순수 TypeScript로 유지한다. 게임과 검증 도구가 같은 코드를 공유하기 때문이다. 이유는 §2.1에 있다. `npm run check`가 이 규칙을 기계로 검사한다.
4. 물리 상수, 중력 공식, 충돌 판정, 레벨 수치를 바꾸는 변경은 반드시 레벨 회귀 테스트(§16.5)를 통과해야 한다. 테스트 기준값을 수정해서 통과시키지 않는다.
5. 마일스톤마다 git 커밋한다. 커밋 메시지는 한국어로 `M2: 조준·발사 입력 구현` 형식.
6. 사용자에게 보이는 문구는 `src/i18n/` 사전에서만 꺼낸다. **한국어(`ko.ts`)가 원본이며 §13의 문구를 그대로 쓴다.** 영어·일본어·중국어(간체)는 그 키를 따른다(§13.7).
7. 스테이지 좌표를 손으로 작성하거나 추측으로 수정하지 않는다. 새 단계는 반드시 생성기(§8.4) 또는 사용자의 에디터 작업으로 만들고 검증기(§8.5)를 통과시킨다.
8. 광고 단위 ID, 서명 키, 스토어 계정 정보는 코드와 저장소에 넣지 않는다(§14.2, §15.6).
9. 루트에 `CLAUDE.md`를 만들어 이 §0 규칙, 명령어, 폴더 구조 요약, **고정한 Node·의존성 버전**을 기록한다.
10. **화면에 영향을 주는 변경은 실제로 브라우저에 띄워 보고 끝낸다.** 확인 없이 "완료"라고 보고하지 않는다. 이것이 v5로 돌아온 이유 중 하나다(§21, §16.6).

## 1. 게임 개요

- **장르:** 캐주얼 물리 퍼즐, 모바일 세로 화면, 한 손가락 조작.
- **목표:** 우주선을 한 번 발사해, 행성 중력을 이용한 스윙바이로 궤도를 꺾어 목적지에 도착시킨다.
- **플레이어가 정하는 것:** 우주선이 발사대 행성 표면의 어느 자리에 설지(그 자리의 법선이 곧 이륙 방향이다), 그리고 움직이는 행성이 있는 단계에서는 발사 시점. 발사 속도는 단계마다 고정이며, 발사 후에는 조작하지 않는다.
- **게임오버:** 행성 충돌, 블랙홀 흡수, 외계인 포격 피격, 외계인 우주선 충돌, 소행성 충돌, 맵 경계 충돌, 30초 안에 미도착.
- **그래픽:** 우주 동화풍 8비트 픽셀 아트 "달토끼 당근 로켓"(§12). NES 팔레트, 한 아트 픽셀 = 월드 1유닛이라 그림 크기가 판정 크기다. (v5까지는 〈아스테로이드〉 풍 벡터 선화였다.)
- **출시:** **웹을 먼저 낸다**(GitHub Pages). 이어서 같은 코드를 Capacitor로 감싸 구글 플레이, 그다음 앱스토어(§15).
- **수익:** 광고. 보상형 광고(힌트·건너뛰기) 중심, 전면 광고는 엄격히 제한(§14).
- **분량:** 초반부 5장 40단계(장마다 새 요소 도입) + 후반부 생성 단계(장당 10단계). §7 참조.
- **화면 구성:** 맵이 화면보다 크면 스크롤되며, 구석에 미니맵이 나타난다. 행성과 블랙홀은 중력 범위를 시각 효과로 표시한다.

### 1.1 설계 근거 (사전 검증에서 확인한 사실)

- 실제 역제곱 중력을 쓰면 성공 발사각 폭이 0.25~1°로 좁아 터치로는 운에 가깝다. 그래서 **중력은 표시된 중력 범위 안에서만 작용하고, 중심에서 강하며 경계에서 0이 되는 모델**(§5.3)을 채택했다. 이 모델로 성공 폭이 7~11°가 된다. "원 밖은 안전, 원 안은 끌린다"는 규칙이 화면에 그대로 보인다는 장점도 있다.
- 움직이는 행성이 주된 스윙바이를 맡으면 결과가 혼돈적이 된다. 그래서 큰 방향 전환은 고정 행성이 맡고, 공전 행성은 중력이 약한 **타이밍 관문** 역할만 한다.

## 2. 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어 | **TypeScript** (`strict`, `noUncheckedIndexedAccess`) | 물리 코어를 부록 A(JavaScript)에서 연산 순서 그대로 옮길 수 있다 |
| 번들러·개발 서버 | **Vite** | HMR, `--host`로 같은 Wi-Fi 폰에서 즉시 확인, 정적 파일로 빌드 |
| 렌더러 | **Canvas 2D** (프레임워크 없음) | 한 프레임에 선 몇백 개뿐이라 충분하다. 엔진도 WebGL도 필요 없다 |
| 물리 | **자체 고정 스텝 코어**(§5) | 결정론과 사전 검증값 재현이 목적 |
| 레벨 데이터 | JSON (`src/levels/data/<ID>.json`) | 생성기가 대량 출력하고 git diff로 검토해야 함. §2.2 |
| UI | 캔버스 위에 겹치는 **평범한 DOM 오버레이** + CSS | 화면 수가 적고 폰트·안전 영역·접근성을 브라우저가 처리해 준다 |
| 테스트 | **Vitest** | 물리·레벨 회귀 테스트, CI 연동 |
| CLI 도구 | **tsx** (`npm run solve` 등) | 게임과 **같은** `src/core/` 코드를 그대로 실행 |
| 웹 출시 | GitHub Actions → GitHub Pages (§15.1) | 푸시하면 검사·테스트·빌드·배포가 자동 |
| 앱 빌드 | **Capacitor** (Android 먼저, iOS는 Mac 준비 후) | 같은 코드베이스 그대로. WebView 셸만 추가된다 |
| 광고 | 웹 **Google H5 Games Ads**, 앱 **AdMob**(Capacitor 플러그인) | 웹에서 AdMob SDK는 쓸 수 없다. §14.2 |
| 저장 | `localStorage` (`swingby.save.v1`) | 브라우저·WebView 모두 동작 |

**왜 v4의 Godot에서 돌아왔는지**는 §21에 정리했다. 요약하면 (1) 이 게임에서 엔진이 대신해 주는 부분이 직접 짜도 수백 줄이고, (2) 엔진을 쓰는 동안 M2~M5 다섯 마일스톤을 **화면을 한 번도 못 보고** 작성했으며, (3) 웹 출시가 목표에 들어왔기 때문이다.

### 2.1 정밀도와 결정론 규칙 (중요)

JavaScript의 `number`는 언제나 64비트 double이므로 v4의 `Vector2` 32비트 문제는 사라졌다. 대신 **연산 순서**가 규칙의 전부다. 부록 A·B의 검증값(§6.2의 성공 구간, §8.5의 `clearance`)은 부록 A의 식을 글자 그대로 따랐을 때의 값이다.

- 거리는 `Math.sqrt(dx*dx + dy*dy)`로 계산한다. **`Math.hypot()`을 쓰지 않는다** — 오버플로를 피하려고 스케일링을 하므로 마지막 자리가 달라진다.
- **비행 시계는 `n * DT` 곱셈으로 유지한다.** 누산(`ft += DT`)으로 바꾸면 오차가 쌓여 §6.2 표가 어긋난다.
- **단계 시계 `t`는 반대로 누산한다.** 발사 시점(`launchStep * DT`)에서 시작해 스텝마다 `DT`를 더해 간다. 부록 A가 그렇게 되어 있다. `levelStep * DT`로 다시 계산하지 않는다.
- 부록 A의 식을 리팩터링하지 않는다. 괄호, 항의 순서, 중간 변수를 그대로 둔다.
- `src/core/`, `src/tools-shared/`, `src/monetization/`에서 DOM·`window`·`document`·`performance`·Node의 `fs`를 쓰지 않는다. 시각이 필요하면 **호출자가 넘긴다**.

`npm run check`가 `tsc --noEmit`과 §0.3 금지 API 검사를 함께 돌린다. 이 규칙을 어기면 §16.5의 회귀 테스트가 조용히 어긋난다.

### 2.2 레벨 데이터를 JSON으로 두는 이유

- 생성기가 시드 수천 개에서 후보를 쏟아내므로 텍스트로 가볍게 쓰고 읽어야 한다.
- 채택된 단계의 좌표 변경이 git diff에서 바로 읽혀야 한다(§0.7 규칙의 감시 수단).
- 게임은 `import.meta.glob('./data/*.json', { eager: true })`로 빌드 시점에 전부 묶고, CLI 도구는 같은 `parseLevel()`을 `fs`로 읽은 문자열에 적용한다. **스키마 검사 코드가 하나다.**

### 2.3 명령어

| 명령 | 하는 일 |
|---|---|
| `npm run dev` | 개발 서버(`--host`). 같은 Wi-Fi 폰에서 표시된 주소로 접속 |
| `npm run check` | `tsc --noEmit` + §0.3 금지 API 검사 + §12.6 색 리터럴 검사. **커밋 전 필수** |
| `npm test` | Vitest 전체(§16.5) |
| `npm run build` | 타입 검사 후 `dist/`로 정적 빌드 |
| `npm run preview` | 빌드 결과를 그대로 서빙(배포 전 최종 확인, §16.6) |
| `npm run solve [단계ID]` | 전 각도 스캔(§16.1) |
| `npm run validate [단계ID\|장번호]` | 전체 검증(§16.3) |
| `npm run gen -- --recipe <파일> --slot <칸>` | 후보 생성(§16.4) |
| `npm run bench` | 단일 전수 스캔 성능 측정(§8.9) |
| `npm run editor` | 스테이지 에디터(§8.7). 개발 서버의 `/editor` 경로 |

인자를 넘길 때는 `--`를 한 번 더 붙인다(npm 규칙).

## 4. 좌표계와 단위

- **월드 좌표:** 원점은 맵 좌상단, x는 오른쪽, **y는 아래쪽**이 양수. 단위는 "유닛". Canvas 2D의 좌표계와 방향이 같으므로 변환이 필요 없다.
- **월드 각도 θ(내부):** 도(°) 단위, 0° = 오른쪽, **−90° = 위쪽**, 시계 방향이 양수(y가 아래이므로). 레벨 데이터·물리·테스트는 모두 이 각도를 쓴다. `Math.atan2(y, x)`와 같은 규약이다.
- **θ는 두 가지를 겸한다(§5.9):** 우주선이 발사대 행성 표면에 서 있는 **위치**이자, 그 자리에서 이륙하는 **방향**이다. 발사 좌표는 `start + PAD_R·(cos θ, sin θ)`이고 속도는 `speed·(cos θ, sin θ)`다. 파라미터가 하나인 것은 종전과 같다.
- **표시 각도(UI):** 0° = 위쪽, 시계 방향 증가, 0~360°. 변환: `ui = fposmod(world + 90.0, 360.0)`.
- **각도 양자화:** 조준 각도는 **0.5° 단위**로 반올림한다. 같은 각도를 다시 재현할 수 있어야 퍼즐이 된다.
- **시간:** 초. 모든 시뮬레이션은 고정 스텝 `DT = 1.0/240.0`초.
- **속도:** 유닛/초. 가속도: 유닛/초².
- **1 유닛 = 월드 공간 1 픽셀**로 두고, 화면 배율은 카메라의 `scale`로 만든다(§11).

## 5. 물리 명세

참조 구현은 부록 A(검증 완료 JavaScript)이고, 실제 구현은 `src/core/`다. **연산 순서까지 동일하게** 유지한다(§2.1).

### 5.1 상수

`src/core/constants.ts`에 아래를 둔다.

| 상수 | 값 | 뜻 |
|---|---|---|
| `DT` | `1.0/240.0` | 고정 스텝(초) |
| `SHIP_R` | `5.0` | 우주선 충돌 반경 |
| `MAX_FLIGHT` | `30.0` | 비행 제한(초) |
| `PAD_R` | `22.0` | 발사대 행성 중심 → 우주선 중심. **실제 발사 좌표를 정한다**(§5.9) |
| `ARC` | `90.0` | 우주선이 걸어 다닐 수 있는 범위(돔 중심 방향 ±ARC) |

`PAD_R`을 24 이상으로 키우면 1-4의 성공 폭이 11.25°에서 6.50°로 무너진다(§6.2의 측정). 22는 그 절벽에서 2유닛 아래로 잡은 값이다.

### 5.2 두 개의 시계

- **단계 시계 `level_step`:** 단계가 시작(또는 재시작)되면 0부터 매 스텝 증가한다. **발사 전에도 흐른다.** 공전 행성 위치는 `t = level_step * DT`로 계산한다.
- **비행 시계 `flight_step`:** 발사 순간 0에서 시작. 외계인 사격 타이밍과 30초 제한에 쓴다.
- 발사는 스텝 경계에서만 일어난다. 손을 뗀 프레임의 현재 `level_step`이 `launch_step`이 된다.
- 재시작 시 두 시계 모두 0으로 초기화한다.

### 5.3 중력

중력원은 행성(`planets`)과 블랙홀(`holes`)이며 같은 공식을 쓴다. 중력원 중심까지 거리를 `r`, 중력 범위를 `R`, 세기를 `g`라 하면:

```
r ≥ R 이면: 가속도 0
r < R 이면: 크기 = g × (1 − r/R)²,  방향 = 우주선 → 중력원 중심
```

여러 중력원의 가속도는 단순 합산한다. `r < 1`이면 0으로 처리(0 나눗셈 방지).

### 5.4 한 스텝의 순서 (반드시 이 순서)

1. 현재 시각 `t`에서 가속도 계산
2. 속도 갱신 `v += a·DT`, 위치 갱신 `p += v·DT` (반암시적 오일러)
3. 시각 `t + DT` 기준으로 충돌 판정, 아래 순서로 **처음 걸린 것**이 결과
   1. 행성: `거리 < planet.r + SHIP_R` → `planet`
   2. 블랙홀: `거리 < rH + 2` → `hole`
   3. 소행성: `거리 < rock.r × 0.85 + SHIP_R` → `rock`
   4. 외계인 몸체: `거리 < 13 + SHIP_R` → `ufo`
   5. 맵 경계: 우주선 중심이 `[SHIP_R, w − SHIP_R] × [SHIP_R, h − SHIP_R]` 밖 → `wall`
   6. 목적지: `거리 < goal.r` → `win`
4. 결과가 없으면 비행 시계 증가 후 외계인 사격 처리(5.5)
5. 총알 이동 및 피격 판정 → `shot`
6. 비행 시간이 `MAX_FLIGHT` 이상이면 `drift`

거리는 `sqrt(dx*dx + dy*dy)`로 계산한다(§2.1).

### 5.5 외계인 사격

- 각 외계인은 `delay` 초에 첫 사격 시도, 이후 `interval` 초마다 시도한다(비행 시계 기준).
- 시도 시점에 우주선이 `range` 안에 있으면, 그 순간 우주선 위치를 향해 속도 `bs`의 총알을 발사한다(예측 사격 없음). 범위 밖이면 이번 시도는 건너뛴다.
- 총알은 직진하며, 수명 5초가 지나거나 맵 밖 20유닛을 벗어나면 제거한다.
- 발사 전에는 사격하지 않는다.
- 부록 A는 다음 사격 시각을 외계인 객체에 `_next`로 얹어 두고 시뮬레이션마다 지운다. 실제 구현에서는 **레벨 객체를 건드리지 말고** 시뮬레이션 상태(`SimState`) 안의 `nextFire: number[]`로 옮긴다. 레벨 객체가 불변이어야 워커 병렬 스캔이 안전하고, 같은 레벨로 두 번 시뮬레이션해도 결과가 같다(§16.5).

### 5.6 공전 행성

`orbit: {cx, cy, rad, period, phase}`가 있으면 위치는
`angle = phase + 2π·t/period`, `x = cx + rad·cos(angle)`, `y = cy + rad·sin(angle)`. period가 음수면 반대 방향. 블랙홀과 소행성, 외계인은 고정이다.

### 5.7 예측선

- 조준 중 매 프레임, 현재 `level_step`에서 발사했다고 가정하고 `step_ship`만 `preview / DT` 스텝 돌려 경로를 얻는다(총알은 무시).
- **실제 비행과 같은 함수**를 써야 한다. "보이는 대로 날아간다"가 이 게임의 신뢰 기반이다.
- 예측 중 충돌 결과가 나오면 거기서 멈추고 그 지점에 작은 × 표시.
- 단계별 `preview` 초가 길이를 결정한다(1단계 1.8초 → 6단계 0.8초).

### 5.8 결정론 보장

- 시뮬레이션을 `requestAnimationFrame`의 `delta`로 직접 돌리지 않는다. `src/game/clock.ts`가 자체 누산기를 돌린다: `acc += Math.min(delta, 0.1)`; `while (acc >= DT && steps < 48) { step(); acc -= DT; }`. 이렇게 해야 게임과 CLI 도구가 같은 스테핑 코드를 쓴다.
- 화면이 숨겨지면(`src/platform/lifecycle.ts`, §15.3) 누산기를 0으로 리셋하고 일시정지한다.
- 난수는 시뮬레이션 결과에 쓰지 않는다. 소행성 모양, 별 배경 같은 장식에만 `seed` 기반 mulberry32(`src/core/rng.ts`)를 쓴다. `Math.random()`의 전역 상태에 의존하지 않는다.

### 5.9 발사대 행성 (v4.1에서 추가)

우주선은 출발점의 고정된 한 점에서 쏘는 것이 아니라, `start`를 중심으로 하는 **작은 행성 표면에 서 있다가 그 자리에서 법선 방향으로 이륙**한다.

```
발사 좌표 = start + PAD_R · (cos θ, sin θ)
발사 속도 = speed  · (cos θ, sin θ)
```

- 돔 중심 방향은 `atan2(goal.y − start.y, goal.x − start.x)`이고, 우주선은 그 방향 **±`ARC`(90°)** 안에서만 걸을 수 있다. 반원 밖은 도달할 수 없으므로 생성기·검증기가 이를 제약으로 쓴다(§8.4, §8.5).
- **이 방식이 §6.2의 검증값을 거의 바꾸지 않는 이유:** 이륙이 법선 방향이므로, 돔 표면에서 쏘는 것은 같은 직선 경로를 `PAD_R`만큼 앞에서 시작하는 것과 같다. 출발점이 중력 범위 밖이면 궤적이 그대로다. 차이는 (ㄱ) 돔 표면이 중력 범위에 걸칠 때 (ㄴ) 공전 행성이 있어 시간이 중요할 때만 생긴다.
- 실제 측정: 돔 반경 22에서 1-1·1-4·2-1·3-1·5-1은 §6.2와 **완전히 동일**하고, 4-1만 9.00°→9.50°로 바뀐다(§6.2의 표).
- `PAD_R`은 전역 상수다. 레벨마다 다르게 두지 않는다 — 플레이어가 배운 조작 감각이 단계마다 달라지면 안 된다.

렌더링용 표면 반경(18유닛)은 `PAD_R`보다 작다. 우주선 중심이 22에 있고 길이가 14이므로 꼬리가 표면에 살짝 묻혀 "얹혀 있는" 모양이 된다. 이 값은 그림에만 쓰고 물리에는 쓰지 않는다(§12.3).

| 단계 | 가장 가까운 중력원 | 거리 `r` | 범위 `R` | 여유 `R−r` | 출발점 가속도 |
|---|---|---|---|---|---|
| 1-1 | 행성0 | 357.95 | 170 | +187.95 | 0 |
| 1-4 | 행성0 | 161.55 | 150 | +11.55 | 0 |
| 2-1 | 블랙홀 | 280.00 | 180 | +100.00 | 0 |
| 3-1 | 행성0 | 205.18 | 150 | +55.18 | 0 |
| **4-1** | **행성0** | **167.63** | **170** | **−2.37** | **0.165 u/s²** |
| 5-1 | 행성0 | 210.95 | 170 | +40.95 | 0 |

4-1의 출발점은 범위 안으로 2.37유닛 들어가 있다. 다만 그 지점의 가속도는 0.165 u/s²로 해당 행성 최대 세기(850)의 0.02% 수준이라 실제 궤도에 미치는 영향은 거의 없다. 발사 전에는 우주선이 움직이지 않으므로(§5.2) 조준 중에 끌려가는 문제도 없다.

**결론 (v4.1에서 확정).** 발사대 행성을 도입하면서 규칙 8을 다시 썼다. `PAD_R = 22`에서 각 단계의 실제 발사 지점 가속도를 재면 다음과 같다.

| 단계 | 정답 θ에서의 발사 지점 가속도 | 돔 표면 전체의 최댓값 |
|---|---|---|
| 1-1, 2-1, 3-1, 5-1 | 0 | 0 |
| 1-4 | 2.45 u/s² | 3.64 |
| **4-1** | **13.35 u/s²** | **17.47** |

4-1의 13.35는 그 행성 최대 세기(850)의 1.6%다. 초기 속도 150 u/s에 대해 0.3초 동안 약 2°의 편향을 만든다 — 성공 폭이 9.5°이므로 감당 범위이고, 예측선이 그 휘어짐을 그대로 보여주므로 플레이어가 속지 않는다. 따라서 "가속도 1 u/s² 미만" 같은 임계값은 **너무 엄해서 쓰지 않는다.**

대신 역할을 둘로 나눈다.

- **합격 기준(§8.5 규칙 8)은 물리적 유효성만 본다** — 돔 표면의 어느 지점도 행성·블랙홀·소행성의 충돌 판정 안에 들어가면 안 된다. 무언가의 **안에서** 시작할 수는 없기 때문이다.
- **설계 품질은 경고로 본다** — 발사 지점 가속도가 1 u/s² 이상이면 보고한다. 지금 1-4와 4-1이 여기 걸리며, 이는 의도된 기록이다.
- **새로 만드는 단계는 생성기가 애초에 막는다** — §8.4 1단계의 배치 제약을 `PAD_R + 30`으로 올린다. 기존 단계에 소급 적용하지 않는다.

이렇게 하면 검증기가 모든 단계의 관문이라는 §8.1 원칙을 지키면서, 검증된 6단계를 손대지 않고, 앞으로 만들 단계의 품질도 떨어뜨리지 않는다.

### 6.3 배치 원칙 (생성기와 에디터가 따를 기본값)

1. 출발점에서 첫 중력 범위 경계까지 350유닛 이내. 멀수록 각도 오차가 증폭된다.
2. 공전 행성은 `g ≤ 700`, `R ≤ 110` 수준의 약한 관문으로만 쓴다. 주 스윙바이를 맡기면 결과가 혼돈적이 된다.
3. 의도하지 않은 경로는 소행성·외계인으로 막는다.
4. 행성 `g`는 750~850, `R`은 130~170, 블랙홀은 `g` 900, `R` 180, `rH` 16을 기준으로 삼는다. 이 범위를 벗어나면 성공 폭이 급격히 좁아지는지 반드시 스캔으로 확인한다.

### 7.1 전체 구조

- **초반부(1~5장, 40단계):** 장마다 새 요소 하나를 도입하고, 8단계에 걸쳐 익히고 섞는다. 사람이 설계 의도를 정하고 생성기·에디터로 제작한다.

### 7.5 후반부 생성 규칙 (6장 이후)

장 번호를 `c`(6 이상), 칸을 `s`(1~10)라 하면:

| 칸 | 역할 | 목표 최소 성공 폭 |
|---|---|---|
| 1 | 워밍업 | `W(c)` |
| 2, 3 | 연습 | `W(c) − 0.5` |
| 4 | 휴식 | `W(c) + 2` |
| 5, 6, 7 | 조합 | `W(c) − 1` |
| 8 | 휴식 | `W(c) + 1.5` |
| 9 | 도전 | `W(c) − 2` |
| 10 | 마무리(긴 맵) | `W(c) − 0.5` |

- `W(c) = max(4.5, 7 − 0.4 × (c − 6))`, 어떤 경우에도 **최소 성공 폭은 2.5° 미만 금지**(0.5° 양자화 기준 서로 다른 성공 각도가 5개 이상).
- 예측선: `max(0.5, 0.7 − 0.05 × (c − 6))`초.
- 요구 중력원 수: 칸 1~4는 2~3, 칸 5~9는 3~4, 칸 10은 4~5.
- 위험 요소 조합은 장마다 하나의 "테마"를 정한다(예: 6장 블랙홀 밭, 7장 포격 회랑, 8장 이중 공전). 테마는 Claude Code가 제안하고 사용자가 고른다.

| 방식 | 장점 | 한계 |
|---|---|---|
| Claude Code가 좌표를 직접 작성 | 도구 개발 불필요 | 중력 궤도는 직관으로 예측이 안 됨. 사전 검증에서 감으로 배치했을 때 성공 폭이 0.25~1°에 그쳤고, 격자 탐색을 거쳐야 7~11°가 나왔다. 수십 단계를 이렇게 만들 수 없다 |
| 에디터로 사람이 전부 제작 | 재미와 모양을 사람이 직접 판단 | 한 단계마다 수십 번의 배치·확인 반복. 풀이 가능성을 사람이 보장하기 어려움 |
| **생성기 + 검증기 + 에디터** | 생성기가 풀이가 보장된 후보를 대량으로 만들고, 검증기가 난이도를 수치화하고, 사람은 에디터에서 고르고 다듬기만 한다 | 초기 도구 개발 비용 |

역할 분담:
- **Claude Code:** 도구 개발, 레시피 작성, 생성기 실행, 결과 요약 보고. 좌표를 손으로 쓰지 않는다.
- **사용자:** 에디터에서 후보를 플레이해 보고 고르기, 필요하면 위치를 살짝 옮기기, 채택.
- **검증기:** 게임에 들어가는 모든 단계의 최종 관문. 규칙을 통과하지 못하면 채택·커밋할 수 없다.

### 8.2 작업 흐름

```
① 레시피 작성      Claude Code가 §7.3 표를 recipes/ch2.json 으로 옮김
② 후보 생성        npm run gen -- --recipe recipes/ch2.json --slot 3 --count 6
③ 결과 보고        candidates/2-3/*.json + 요약표(성공 폭, 난이도 점수, 비행 시간) + 궤적 썸네일 SVG
④ 에디터에서 선택   npm run editor → 후보 목록 → 플레이 테스트 → 필요 시 수정
⑤ 채택             에디터 [채택] → src/levels/data/2-3.json 저장(정답·지표 자동 기록)
⑥ 전체 검증        npm run validate → 통과 시 커밋
```

사용자가 Claude Code에 요청하는 예:
- "2장 레시피 만들고 2-2~2-8 후보를 칸마다 5개씩 생성해줘. 요약표만 보여줘."
- "2-5 후보 3번을 채택했어. 검증 돌리고 커밋해줘."
- "7장 테마 후보 3개 제안해줘."

② 생성은 **오래 걸리는 배치 작업**이다(§8.9). 실행해 두고 다른 일을 하는 흐름을 전제로 한다.

### 8.3 레시피 형식

```json
{
  "chapter": 2,
  "defaults": { "speed": 160, "startZone": "bottom", "goalZone": "top" },
  "slots": [
    {
      "slot": 2, "role": "연습",
      "name": "지평선만 피하기",
      "hint": "블랙홀만으로도 궤도를 꺾을 수 있어요",
      "intro": null,
      "map": { "w": 400, "h": 760 },
      "preview": 1.0,
      "required": [ { "type": "hole", "count": 1 } ],
      "optional": [],
      "hazards": { "ufos": 0, "rocksMax": 6 },
      "window": { "min": 7, "max": 12 },
      "timing": null
    }
  ]
}
```

- **`name` 과 `hint` 는 사람이 짓는다.** 생성기가 만들 수 없는 유일한 항목이다. 레시피와 단계 JSON 에는 **한국어 원문**을 쓰고, 번역은 `src/i18n/levels.ts` 에 따로 둔다(§13.7) — 번역을 고친다고 검증된 단계 파일이 바뀌지 않게. `name` 이 없으면 레시피 검사가 거부한다. 장 테마와 이름을 짜는 일에는 AI 를 써도 좋다 — 좌표와 달리 검증으로 판정할 수 있는 종류가 아니다.
- `required`: 성공 경로가 **반드시 거쳐야 하는** 중력원. `optional`: 배치하되 필수가 아닌 중력원(방해·장식). 공전 행성은 `{ "type": "orbit", "count": 1, "role": "gate" }`.
- `startZone`, `goalZone`: `bottom | top | left | right | center | any`. 생략하면 `defaults`.
- `window`: 목표 성공 폭(°). **규칙 1 의 최소 폭이자 "너무 쉬움" 경고의 상한**이다(§8.5).
- `timing`: 공전 단계에서 `{ "minFraction": 0.55, "maxFraction": 0.85 }`. 정의는 §8.5 를 본다.
- `seedCount` 기본값은 **2000**이다(v5에서 v3 값으로 복구, 이유는 §8.9). 후보가 부족하면 늘려 재실행한다.
- 초반부 5장 레시피가 `recipes/ch1.json` ~ `ch5.json` 에 있다. §7.3 표를 그대로 옮긴 것이다.

### 8.4 생성기 알고리즘 (`tools/generate.ts` + `src/tools-shared/generator.ts`)

사전 검증에서 실제로 성공한 절차를 그대로 자동화한다.

1. **배치 샘플링:** 시드별로 출발점을 `startZone`에 두고, 필수·선택 중력원을 무작위 배치한다. 제약: **출발점은 모든 중력 범위 밖 `PAD_R + 30`(= 52)유닛 이상**(돔 표면 전체가 범위 밖이어야 한다, §5.9), 첫 필수 중력원의 범위 경계는 출발점에서 350유닛 이내, 중력원 중심끼리 `R₁ + R₂ − 60` 이상 떨어짐(범위 약간 겹침 허용), 맵 경계에서 `r + 20` 이상.
2. **각도 전수 스캔:** 목적지와 소행성 없이 −180°~180°를 0.25° 간격으로 시뮬레이션(외계인·총알 포함). 궤적마다 "지금까지 들어간 중력 범위" 비트마스크를 기록한다.
3. **목적지 격자 평가:** 맵을 10유닛 격자로 나누고, 궤적이 `goal.r` 이내로 지나간 칸에 그 각도를 표시한다. 단, **모든 필수 중력원 범위를 이미 거친 뒤**에 지나간 경우만 인정한다. 칸마다 연속 성공 각도 구간의 최대 폭을 구한다.
4. **목적지 선택:** `goalZone` 안에서, 출발점과 거리가 맵 대각선의 40% 이상이고 중력원 중심에서 `R × 0.5` 이상 떨어진 칸 중 폭이 레시피 범위에 드는 최선의 칸. **주 구간이 돔 중심 방향 ±`ARC` 안에 들어야 한다**(§5.9). 목적지를 정하면 돔 중심 방향도 정해지므로, 이 검사는 목적지 후보마다 다시 해야 한다.
5. **지름길 차단:** 목적지를 넣고 다시 전수 스캔. 주 구간 외에 폭 1° 이상의 성공 구간이 있으면, 그 궤적 위에서 주 구간 궤적들과 35유닛 이상 떨어진 지점에 소행성을 놓고 반복한다. `rocksMax` 안에서 해결 안 되면 이 시드는 폐기.
6. **공전 타이밍:** 공전 행성이 있으면 주기를 24등분한 발사 시점마다 3~5를 수행해, 주 구간 폭이 최소 폭 이상인 시점의 비율이 `timing` 범위인지 확인.
7. **장식 소행성:** 선택적으로 2~4개, 주 구간 궤적들에서 30유닛 이상 떨어진 곳에.
8. **검증(§8.5) 통과 후보만** 저장하고, 난이도 점수 순으로 정렬해 `count`개를 출력.

**M8 에서 실제로 돌려 보고 정한 두 가지**

- **4단계의 "최선의 칸"** = 성공 폭이 레시피 범위의 **한가운데**에 가장 가까운 칸. 범위 가장자리에 걸친 단계는 수치를 조금만 건드려도 규칙 밖으로 나간다.
- **8단계는 "상위 `count`개"가 아니라 정렬 후 고르게 솎는다.** 한 칸의 후보들이 난이도 점수가 같은 경우가 흔해서(레시피의 `window` 가 이미 난이도를 묶어 둔다) 앞에서 자르면 53개 중 아무 10개가 된다. 고르게 뽑으면 찾은 것의 전 범위를 보고 고를 수 있다 — "10개 만들고 좋은 걸 고른다"는 작업 흐름이 그래야 성립한다.

**필수 중력원은 사실상 2개까지다 (M10 에서 측정).** 3단계의 비트마스크는 궤적이 필수 범위를 **전부** 거칠 것을 요구하는데, 1단계가 중력원을 무작위로 놓으므로 그런 궤적은 필수 개수가 늘수록 급격히 드물어진다. 5-8(800×1200, 필수 3)은 **4,800시드에서 후보 0개**였고 기각의 64%가 "쓸 만한 목적지 칸 없음"이었다. 2개로 줄이면 같은 칸이 수백 시드 안에서 나온다. 그래서 §7.3 의 "필수 중력원 N"은 **화면에 있는 중력원 수 N, 그중 정답 경로가 반드시 거치는 것 2개**로 읽는다(5-6·5-7 도 이미 그렇게 만들어졌다). 나머지는 `optional` 로 둔다 — 배치에는 들어가고 플레이어는 쓸 수 있지만 정답이 거치도록 강제하지 않는다.

필수를 3개 이상으로 쓰려면 1단계가 무작위 배치가 아니라 **출발점에서 바깥으로 사슬을 이루도록** 놓아야 한다. 생성 알고리즘의 변경이라 M13(후반부 생산 체계)에서 다룬다.

**병렬화:** Node의 `worker_threads`로 시드 단위 병렬 처리한다(에디터에서는 Web Worker). 워커 안에서는 레벨 객체를 절대 변경하지 않는다(§5.5의 `nextFire` 규칙이 이것 때문이다). 진행률을 10초마다 한 줄씩 출력해, 긴 배치 작업 중에도 살아 있음이 보이게 한다.

### 8.5 검증기 (`tools/validate.ts`, `src/tools-shared/metrics.ts`)

에디터와 CLI가 같은 지표 코드를 쓴다(노드 금지 규칙은 `core`와 동일).

**지표**

| 지표 | 정의 |
|---|---|
| `main_window` | 가장 넓은 연속 성공 구간 폭(°). 공전 단계는 최적 발사 시점 기준. **규칙 1 과 난이도 점수가 보는 값** |
| `main_window_at_solution` | 저장된 `solution.launch_step` 에서의 폭. 고정 단계는 위와 같다. **`meta.metrics.main_window` 에 저장되는 값**(M7에서 갈라냄 — 아래 설명) |
| `solution` | 주 구간 중앙 각도(0.5° 반올림)와 발사 스텝 |
| `flukes` | 주 구간 외 성공 구간 목록과 합계 폭 |
| `essential` | 필수 중력원을 하나씩 제거했을 때 정답이 실패하는지 |
| `timing_fraction` | 발사 가능 시점 비율(공전 단계). **주기를 24등분한 발사 시점 중 성공 폭이 `MIN_WINDOW`(2.5°) 이상인 시점의 비율.** 생성기와 검증기가 반드시 같은 문턱을 써야 한다 — M8 에서 문턱이 달라 생성기가 통과시킨 값과 기록된 값이 어긋난 적이 있다 |
| `timing_range` | 정답 각도로 성공하는 발사 시점 구간(주기 안의 초). 힌트의 공전 표시에 사용 |
| `flight_time` | 정답 비행 시간 |
| `clearance` | 정답 경로가 행성·블랙홀·소행성 판정 경계에 가장 가까이 간 거리 |
| `difficulty` | §8.6 점수 |

**필수 규칙(하나라도 어기면 실패)**

1. `main_window ≥ max(2.5, 레시피 최소 폭)`
2. 주 구간 외 성공 구간은 각각 1° 미만, 합계 2° 미만
3. `required` 중력원은 모두 `essential`
4. `flight_time ≤ 15초`
5. `clearance ≥ 6유닛`
6. 공전 단계는 `timing_fraction`이 레시피 범위 안
7. 저장된 `solution`으로 시뮬레이션하면 `win`
8. **돔 표면(`start` 중심 반경 `PAD_R`)의 어느 지점도 행성·블랙홀·소행성의 충돌 판정 안에 들어가지 않음** — 무언가의 안에서 출발할 수는 없다. 근거는 §6.2의 결론
9. **정답 θ가 돔 중심 방향 ±`ARC` 안** — 반원 밖은 우주선이 걸어갈 수 없으므로 도달 불가능한 단계가 된다

**경고(통과는 하되 보고)**

- `main_window`가 레시피 최대 폭 초과(너무 쉬움)
- `clearance < 10`(아슬아슬해서 의도치 않게 어려울 수 있음)
- **발사 지점(정답 θ)의 합산 가속도가 1 u/s² 이상** — 돔 표면이 중력 범위에 걸쳐 있다는 뜻이다. 검증된 1-4(2.45)와 4-1(13.35)이 여기 걸리며 이는 의도된 기록이다(§6.2). 생성기가 만든 단계가 여기 걸리면 배치 제약이 새는 것이므로 원인을 찾는다
- **4번 휴식 칸**의 난이도 점수가 3번보다 높음
- **8번 마무리 칸**의 성공 폭이 7번(도전)보다 좁음 — §7.2 가 "도전보다 폭은 넓게" 라고 적은 대로다. **8번은 난이도가 아니라 폭으로 본다**(M10에서 갈라냄): 마무리는 긴 맵을 쓰므로 §8.6 의 G 항 때문에 점수가 늘 올라간다. 어려워서가 아니라 맵이 커서다
- **7번 도전 칸**이 장에서 가장 어렵지 않음(§7.2). 8번은 위와 같은 이유로 빼고 본다
- 장 1칸의 점수가 이전 장 7칸보다 높음 — `chapterJumpWarnings`. 장 안에서는 알 수 없으므로 **전 단계를 한꺼번에 훑을 때만** 본다(`npm run validate` 를 인자 없이). 한 장만 보면 아무 말도 하지 않는다

**`main_window` 를 둘로 나눈 이유 (M7).** 공전 단계에서 "최적 발사 시점의 폭"과 "저장된 정답 시점의 폭"이 다를 수 있다. 4-1 이 실제로 그렇다 — 최적은 스텝 960 의 10.00°, 저장된 정답은 스텝 800 의 9.50°(§6.2, §16.5 기준값). 두 값은 쓰임이 다르다.

- **규칙 1 과 난이도 점수**는 최적 시점을 본다. "가장 잘 맞췄을 때 이 단계가 얼마나 너그러운가"가 설계 관문이다.
- **`meta.metrics.main_window` 에 저장하는 값은 정답 시점 기준**이다. 이 값을 읽는 쪽이 힌트의 방향 표시(§14.3)이고, 그 호는 `meta.solution.angle` 을 중심으로 그린다. 최적 시점의 폭을 쓰면 호가 실제보다 넓게 그려져 플레이어를 속인다.
- 둘이 다르면 저장할 때 `main_window_best` 와 `best_launch_step` 을 함께 남기고, 검증기가 경고 한 줄로 보고한다.

**레시피에 기대는 검사는 M8 에서 켰다.** `checkLevel(L, m, limits)` 에 레시피의 `window` 와 `timing` 을 넘기면 규칙 1 의 최소 폭, 규칙 6, "너무 쉬움" 경고가 함께 동작한다. 생성기는 언제나 넘기고, 등록된 단계를 그냥 훑는 `npm run validate` 는 넘기지 않는다(그 단계들은 이미 채택된 것이라 레시피가 없다).

**사전 검증 6단계 실측값** (v5 `npm run validate` 결과. 규칙 보정의 근거다):

| 단계 | 성공 폭 | 비행 시간 | `clearance` | `timing_fraction` | 난이도 |
|---|---|---|---|---|---|
| 1-1 | 7.00° | 4.03초 | 17.18 | — | 0.55 |
| 1-4 | 11.25° | 3.59초 | 13.18 | — | 1.29 |
| 2-1 | 9.75° | 3.20초 | 12.11 | — | 1.52 |
| 3-1 | 7.00° | 3.75초 | 10.12 | — | 2.58 |
| 4-1 | 10.00°(최적) / 9.50°(정답 시점) | 5.71초 | 18.38 | 0.50 | 2.14 |
| 5-1 | 7.25° | 5.88초 | 8.13 | — | 4.56 |

고정 중력원은 모두 `essential`, 공전 관문은 비필수 — §8.5 가 예상한 대로다. 비행 시간 3.20~5.88초와 `clearance` 8.13~18.38유닛은 규칙 4(15초)·규칙 5(6유닛)에서 충분히 멀다. (v4 에 적혀 있던 "3.3~6.0초, 8.1~18.2유닛"은 돔 도입 전의 어림값이었다.)

경고는 넷이 뜨고 **모두 의도된 기록**이다: 1-4·4-1 의 발사 지점 가속도(§6.2 결론), 5-1 의 `clearance` 8.13, 4-1 의 최적 발사 스텝 차이, 그리고 1-4 의 휴식 칸 곡선 경고다.

**5-1 의 장 넘김 경고도 남는다.** 5-1(4.56)이 4-7(3.89)보다 어렵다. 5-1 역시 §6.2 사전 검증 단계라 고정이고, 넓은 맵의 G 항이 붙는 자리다. 4-7 을 5-1 보다 어렵게 만들면 4장 안의 곡선이 망가진다.

**1-4 의 곡선 경고는 없어지지 않는다 (M10 확인).** v5 초안은 "1장이 8칸으로 차면 사라진다" 고 적었지만 그렇지 않았다. 1-4 는 §6.2 의 사전 검증 단계라 ID 와 내용이 고정인데 **행성을 둘 쓴다** — §8.6 의 연계 수 항이 붙어 1.29 가 되고, 같은 자리의 휴식 칸 규칙(직전 칸보다 낮을 것)을 1장에서만 만족시킬 수 없다. 1-3(변형, 8.00°, 0.23)을 억지로 어렵게 만들면 §7.2 의 1~3칸 의도가 깨지므로 **경고를 남겨 둔다.** 실제 차이는 0~10 척도에서 1.06 이고, 1장은 전 구간이 2.0 아래라 플레이 감각으로는 드러나지 않는다.

### 8.6 난이도 점수

```
A = clamp((8 − main_window) / 5.5, 0, 1) × 3.0          성공 폭
B = min((필수 중력원 수 − 1) × 0.6, 1.8)                 연계 수
C = min((외계인 수 + 비필수 블랙홀 수) × 0.4, 1.2)       위험 요소
E = clamp((1.8 − preview) / 1.3, 0, 1) × 1.5            예측선
F = 공전 단계면 clamp((0.5 − timing_fraction) / 0.3, 0, 1) × 1.5, 아니면 0
G = 맵이 두 축 모두 화면 초과면 1.0, 한 축이면 0.5, 아니면 0
difficulty = A + B + C + E + F + G      (대략 0~10)
```

가중치는 초기값이다. M8에서 플레이 테스트 후 조정하고, 조정하면 모든 단계의 점수를 다시 계산해 곡선 경고를 확인한다.

### 8.7 스테이지 에디터 (`src/editor/`)

개발 서버에서만 뜨는 **개발자용** 웹 페이지다(`editor.html`, `npm run editor`). 게임과 같은 `src/core/`·`src/tools-shared/`를 import하므로 에디터의 검증 결과가 CLI와 어긋날 수 없다. (v3의 계획으로 돌아온 것이고, v4의 `EditorPlugin` 방식은 폐기했다.)

**에디터의 결과가 출시에 반영되는 경로는 하나다.** [채택하고 저장] → `src/levels/data/<ID>.json` 이 실제로 바뀜 → `npm run validate` → 커밋 → 기본 브랜치 푸시 → Pages 배포(§15.1). 중간에 손으로 옮겨 적는 단계가 없다.

- **배포 번들에서 빠지는 방식:** `editor.html`은 저장소 루트에 있지만 `vite build`의 입력이 아니다(`rollupOptions.input`은 `index.html` 하나). 개발 서버는 아무 `.html`이나 서빙하므로 개발 중에는 그냥 열리고, `dist/`에는 파일도 코드도 남지 않는다. M7·M12에서 산출물을 직접 확인한다(§19).
- **파일 저장**은 개발 서버에만 붙는 **Vite 플러그인**(`tools/editor-plugin.ts`, `apply: 'serve'`)이 맡는다. 빌드에는 관여하지 않는다. **쓰기 경로는 `src/levels/data/`와 `candidates/`로 제한**하고, 경로를 정규화한 뒤 저장소 안인지 검사하고 허용 폴더 접두사를 확인한다. `..`·절대 경로·널 바이트·`.json`이 아닌 확장자는 거부한다. 이 판정은 `tests/editor-plugin.test.ts`가 지킨다.
- **저장 형태:** 키 순서를 §6.1 스키마 순서로 고정하고 비어 버린 배열은 뺀다. §2.2대로 좌표 변경이 git diff에서 바로 읽혀야 하기 때문이다. 손대지 않고 저장하면 `meta.source`를 건드리지 않는다 — 열어 보기만 했는데 `verified`가 `editor`로 떨어지면 §6.2의 기록이 조용히 사라진다.
- 되돌리기·다시하기는 직접 구현한다(상태 스냅샷 50단계). 레벨 하나가 작은 JSON이라 스냅샷 방식으로 충분하다.
- 데스크톱 브라우저 사용을 기본으로 한다.

**화면 구성**

```
┌──────────────────────────────┬────────────────┐
│                              │ 단계 정보       │
│   맵 캔버스                   │  ID, 맵 크기, 속도│
│   + 궤적 오버레이              │  예측선         │
│                              ├────────────────┤
│                              │ 선택 요소 속성   │
│                              ├────────────────┤
│                              │ 검증 결과       │
│                              │  지표, 규칙 ✓/✗ │
│                              │  난이도 점수     │
├──────────────────────────────┴────────────────┤
│ 선택│행성│공전│블랙홀│소행성│외계인│출발│목적지 ┃ 되돌리기 다시하기 ┃ 플레이 │ 채택 │
└───────────────────────────────────────────────┘
```

**기능**

- 요소 추가·삭제·드래그 이동(5유닛 격자 스냅, Shift로 해제). 중력 범위 원의 테두리 손잡이로 `R` 조절, 공전 행성은 중심 이동과 반경 손잡이.
- 속성 패널에서 모든 수치를 입력·슬라이더로 수정. 필수/비필수/관문 역할 지정.
- **실시간 검증:** 수정 후 **200ms** 뒤 Web Worker에서 1° 간격 대략 스캔 → 결과 표시 → 궤적 부채꼴 → 0.25° 정밀 스캔과 지표 전체로 갱신. **규칙 판정에 쓰는 것은 0.25° 결과뿐이다** — 대략 스캔의 숫자를 기록하거나 채택 판정에 쓰지 않는다. (v4의 600ms 디바운스는 GDScript 속도 때문이었다. 스캔이 0.06~0.5초인 지금은 필요 없다 — §8.9.)
  실측 첫 결과(M7): 1-1 **223ms**, 5-1 **255ms**, 4-1 **234ms** — §18의 0.3초 안이다. 전체 갱신은 1-1 271ms, 5-1 361ms, 4-1 2.35초(24번 스캔).
- **채택 잠금:** 필수 규칙에 하나라도 걸리면 [채택하고 저장] 버튼이 비활성이다. 검증기를 통과하지 않은 단계를 저장할 방법이 에디터에 없다(§8.1, §19).
- **궤적 오버레이:** 2° 간격 부채꼴을 실패 원인별 색으로(충돌 주황, 벽 회색, 블랙홀 보라, 피격 빨강, 성공 초록). 주 구간은 굵게.
- **타이밍 지도(공전 단계):** 가로 발사 시점 × 세로 각도의 성공 여부 격자. 칸을 누르면 그 조건의 궤적을 강조.
- **후보 목록:** `candidates/<단계ID>/`를 불러와 썸네일과 지표로 비교.
- **플레이 테스트:** 같은 페이지에서 실제 게임 루프를 띄워 플레이하고, 나가면 마지막 시도 궤적을 에디터에 겹쳐 표시. 게임 코드를 그대로 import하므로 별도 빌드가 없다.
- **정답 재생:** 저장된 `solution`으로 비행을 재생.
- **채택:** 필수 규칙 통과 시에만 활성화. `meta`(정답, 지표, 난이도, 수정일)를 채워 `src/levels/data/<ID>.json`에 저장하고 `chapters.ts` 목록 반영을 안내.
- JSON 복사·붙여넣기.

### 8.8 비교 대상으로 검토했던 대안 (참고)

v4에서는 레벨을 Godot 씬(`.tscn`)으로 두고 에디터 기즈모를 그대로 쓰는 방식을 검토했다. 드래그 편집은 공짜로 얻지만 생성기가 씬을 대량 출력해야 하고 후보 비교·지표 표시를 결국 커스텀 UI로 붙여야 하며 git diff가 읽기 어려워진다. v5에서는 애초에 그 선택지가 없고, JSON + 전용 캔버스 하나뿐이다(§2.2).

### 8.9 생성기 성능 (v5에서 재측정)

v5의 스캔은 Node(V8)에서 돈다. **실측값**(Intel Xeon 2.10GHz, Node 22, `npm run bench`):

| 단계 | Node 22 (v5) | Godot 3.5 GDScript (v4 측정) | 비율 |
|---|---|---|---|
| 1-1 (행성1, 소행성5) | **0.061초** | 4.90초 | 80× |
| 5-1 (행성2, 블랙홀, 외계인2, 소행성6) | **0.517초** | 9.01초 | 17× |

비율이 크게 다른 이유는 5-1의 총알·외계인 처리가 Node 쪽에서도 무겁기 때문이다. **v4의 성능 관문(§17 M0의 ≤2초 / 2~5초 / >5초 판단표)은 이 수치로 해소되었고, §17에서 뺐다.**

이 차이가 실제로 어디에 걸리는지 구분해 둔다.

| 작업 | 빈도 | v5 |
|---|---|---|
| 에디터 실시간 검증 (단일 스캔) | 요소를 옮길 때마다 | 0.06~0.5초. **사람이 기다렸다고 느끼지 않는다** |
| `validate` (단계당 1~12 스캔) | 커밋 전마다 | 40단계 전체가 수십 초 |
| 생성기 배치 (시드 × 여러 스캔) | 장마다 몇 번 | 수 분~수십 분 |

그래서 v4에서 성능 때문에 깎았던 설정을 되돌린다.

- 에디터 디바운스 600ms → **200ms**. Web Worker 하나면 충분하다(v4는 `WorkerThreadPool`이 필요했다).
- 레시피 `seedCount` 기본값 500 → **2000**으로 복구(v3 값). 후보가 부족하면 늘려 재실행한다.
- 2단계 스캔(1° 대략 → 0.25° 정밀)은 **유지한다.** 비용 문제가 아니라 첫 결과를 즉시 보여주는 UX 때문이다.
- 내부 루프에서는 여전히 객체를 새로 만들지 않는다. 스크래치 배열을 재사용하고, 부록 A의 연산 순서는 건드리지 않는다(§2.1).

전수 스캔이 빠른 이유 하나는 궤적 대부분이 일찍 벽에 부딪혀 끝나기 때문이다(1-1 기준 1440각도 중 1219개가 `wall`). 평균 스텝 수가 최대치보다 훨씬 작다.

### 8.9.1 공전 단계 생성 비용

§8.4의 6단계를 문자 그대로 읽으면 공전 행성이 있는 시드마다 "주기를 24등분한 발사 시점마다 3~5를 수행"한다. 시드 하나가 **스캔 약 120회**(24시점 × 지름길 차단 반복)다.

v4(Godot, 스캔 3초)에서는 시드 하나에 6분, 500시드면 4코어로도 **12시간**이 넘어 4장 전체가 불가능했다. v5는 스캔이 0.06~0.5초이므로 시드 하나가 **7~60초**다. 2000시드를 단일 스레드로 돌리면 여전히 4~33시간이지만, `worker_threads`로 코어 수만큼 나누면 4코어에서 1~8시간으로 내려간다. 실행해 두고 다른 일을 하면 되는 범위다.

그래도 계산 순서 최적화는 **그대로 채택한다**(M8):

1. 기준 위상 **2개**에서 3~5단계를 먼저 수행해 후보를 거른다.
2. **거기서 살아남은 시드에 대해서만** 24등분 타이밍 검사를 돌린다.

지표 정의(`timing_fraction`)와 검증 규칙 6은 그대로다 — 계산 순서만 바꾸는 것이라 결과가 달라지지 않는다. v4에서는 기준 위상을 1개로 할지 2~3개로 할지 M8에서 정하기로 미뤄 두었는데, v5의 여유로는 **2개를 기본**으로 하고 통과율이 낮으면 늘린다.

## 9. 게임 흐름과 상태 머신

### 9.1 앱 화면

`Title` → `LevelSelect` → `Play` → `Result` → (`Play` 재시도 | 다음 `Play` | `LevelSelect`)

- 캔버스는 하나이고 계속 살아 있다. 화면 전환은 캔버스 위에 겹치는 **DOM 오버레이**의 표시·숨김이다(`src/ui/screens.ts`). `Result`는 반투명이라 뒤의 궤적이 그대로 보인다(§13.4).
- 오버레이를 열 때마다 DOM을 새로 짓지 않고 `index.html`의 컨테이너를 채워 넣는다. 화면이 바뀌어도 게임 상태는 메모리에 그대로 있다.
- 브라우저 뒤로 가기(`popstate`)와 안드로이드 뒤로 버튼을 **같은 핸들러**로 받는다(§15.3).

### 9.2 Play 내부 상태

`src/game/session.ts`가 아래 상태를 관리한다.

| 상태 | 들어오는 조건 | 하는 일 | 나가는 조건 |
|---|---|---|---|
| `ready` | 단계 시작·재시작 | 단계 시계 진행(공전 행성 움직임), 조준·화면 이동 허용 | 조준 드래그 시작 → `aiming` |
| `aiming` | 조준 드래그 중 | 각도 갱신, 예측선, 각도 표시 | 발사 조건 충족 후 손 뗌 → `flying` / 취소 → `ready` |
| `flying` | 발사 | 시뮬레이션, 카메라 추적, 궤적 기록 | 결과 발생 → `ending` |
| `ending` | 결과 발생 | 시뮬레이션 정지, 폭발 또는 도착 연출 0.8초 | 연출 종료 → `Result` 화면 |

`ready`와 `aiming`에서 단계 시계는 계속 흐른다. `ending` 동안 공전 행성 애니메이션은 계속 보이지만 판정은 멈춘다.

## 10. 입력 명세 (한 손가락)

### 10.0 단위 환산

v5에서는 환산이 사실상 필요 없다. 포인터 이벤트의 좌표가 **CSS 픽셀**이고, CSS 픽셀은 안드로이드 dp와 같은 크기 기준(≈1/160인치)이다. v3에서 정한 px 기준값을 그대로 쓴다. (v4에서는 엔진이 실제 기기 픽셀을 주어 고DPI에서 기준이 3배 좁아졌고, 그래서 `dp()` 함수가 필요했다.)

- 캔버스는 `width = CSS폭 × devicePixelRatio`로 만들고 `ctx.setTransform(dpr, 0, 0, dpr, 0, 0)`으로 프레임을 시작한다. **그 뒤의 모든 좌표 계산은 CSS 픽셀이다.**
- `devicePixelRatio`는 **2.5로 상한**을 둔다. 3배 이상 기기에서는 픽셀 수만 늘고 화면 차이가 보이지 않는다(§15.4). 필드는 어차피 저해상 월드 버퍼를 확대해 올린다(§12.0).
- 안전 영역은 CSS `env(safe-area-inset-*)`로 받는다. `index.html`의 뷰포트 메타에 `viewport-fit=cover`가 필요하다.
- 이 문서의 `dp(26)` 같은 표기는 v5에서 **CSS 픽셀 26**을 뜻한다. 별도 함수는 두지 않는다.

### 10.0.1 입력 설정

- **Pointer Events**(`pointerdown`/`pointermove`/`pointerup`/`pointercancel`)를 캔버스에서 처리한다. 마우스·터치·펜이 한 경로로 들어온다.
- `pointerdown`에서 `setPointerCapture()`를 걸어 손가락이 캔버스 밖으로 나가도 이벤트를 놓치지 않는다.
- **첫 번째 포인터만 추적**하고(`pointerId`를 고정) 추가 손가락은 무시한다.
- 캔버스에 `touch-action: none`을 준다(브라우저 스크롤·확대 제스처 차단). 페이지 전체에는 `overscroll-behavior: none`.
- `pointercancel`과 `visibilitychange`(숨겨짐)는 발사하지 않고 **취소**로 처리한다.

### 10.1 누르는 순간의 해석 (`ready` 상태에서만)

1. 누른 점이 미니맵 영역 안 → **미니맵 이동 모드**
2. 그 외 **어디를 눌러도 조준 모드**

v4.0까지는 우주선 근처(`dp(90)`)를 눌러야 조준이 시작됐다. 발사대 행성(§5.9)을 도입하면서 조준 기준점이 우주선이 아니라 **돔 중심**이 되었으므로, 화면 어디를 눌러도 방향이 정해진다. 우주선을 손가락으로 가리지 않아도 되고, 화면 구석에서 끌면 미세 조정이 쉬워진다.

### 10.2 조준 모드

- 방향 벡터 = 손가락 위치 − **돔 중심(`start`)의 화면 위치**. 우주선이 그 방향의 표면 자리로 걸어간다.
- 벡터 길이가 `dp(26) + 표면 반경` 이상이면 각도 θ를 계산해 0.5° 단위로 양자화하고, `±ARC`로 잘라낸 뒤 우주선 위치·예측선·표시 각도를 갱신한다. 손가락이 멀수록 같은 움직임에 대한 각도 변화가 작아지므로 자연스러운 미세 조정이 된다.
- 그보다 가까우면 "취소 영역": 예측선을 숨기고 행성 둘레에 취소 표시.
- **툭 친 것은 발사하지 않는다.** 화면 어디나 조준이 시작되므로 실수 발사를 막아야 한다. 손을 뗄 때 **`dp(8)` 이상 움직였거나 250ms 이상 눌렀을 때만** 발사한다. 둘 다 아니면 취소로 처리한다.
- 손을 뗄 때 취소 영역이면 **취소**(각도는 마지막 값 유지, 예측선 숨김).
- 손가락이 화면 밖으로 나가거나 앱이 포커스를 잃으면(`NOTIFICATION_APPLICATION_FOCUS_OUT`) 발사하지 않고 취소.

### 10.3 화면 이동

- **빈 곳을 끌어 화면을 옮기는 조작은 없다.** §10.1 규칙 2와 물리적으로 양립할 수 없다(누르면 조준이 되어 버린다). 큰 맵은 §10.4의 미니맵으로 살펴본다.
- 한 손가락만 추적한다는 §10.0.1 규칙은 그대로다. 두 손가락 이동은 넣지 않는다.
- **확인 완료(v5).** 큰 맵에서 미니맵만으로 항로 파악이 되는지 사용자가 실기기로 확인했고, 된다. 예비로 두었던 보완책(미니맵 키우기, 발사 전 자동 훑기 연출)은 넣지 않는다.

### 10.4 미니맵 이동 모드

- 누른 점과 드래그 중인 점에 해당하는 월드 위치로 카메라 중심을 즉시 옮긴다.

### 10.5 비행 중·연출 중

- 비행 중 탭은 분사(§22.1), 궤도 행성에서 도는 중이면 나가기(§22.4). 실패 연출 중 탭은 0.3초 뒤부터 바로 다시 시도(§13.4). HUD 의 재시작 버튼은 언제나 동작한다.

### 10.6 보조

- 진동: `src/platform/haptics.ts`로 발사·게임오버·도착 시 짧게(§15.3). 설정에서 끌 수 있다.
- **키보드**(코드 검토 3, 데스크톱·itch.io): 손가락과 같은 상태 머신을 두드린다. ←/→ 조준 0.5°(Shift 5°, 누르면 조준 중으로 쳐서 예측선·각도가 보인다), Space/Enter 발사·궤도 나가기·시트의 주 버튼(다음 단계 / 다시 시도)·실패 연출 중 다시, 비행 중 ←/→ 진행 방향 ±40° 분사, Esc 조준 취소, R 다시. 오버레이·데모·힌트 시트가 열려 있거나 `<select>` 에 포커스가 있으면 먹지 않는다. 마우스는 포인터 이벤트로 이미 된다.

## 11. 카메라와 뷰포트

`src/game/camera.ts`에 카메라를 직접 짠다. 60줄 남짓이고, v4에서 `Camera2D` 설정으로 대신했던 것을 전부 대체한다.

- **배율(v5 이후 개정, 사용자 결정 "가로 꽉 채우기"):** HUD 는 맵 위에 겹친다. 위(HUD 아래 끝)·아래(각도 판) **가림 띠**를 잰다.
  - 맵 전체가 가림 띠 사이에 배율 0.85 이상으로 들어가면(태블릿·데스크톱·전체 화면 폰) 그 배율로 전체를 보인다.
  - 아니면 **맵 폭 = 화면 폭**(`화면폭 / 400`). 단 세로로 640유닛은 늘 보이게 상한을 둔다(가로 화면).
  - 이유: 폰 브라우저는 주소창이 세로를 먹어, 전체를 넣으면 맵이 화면 폭의 79% 로 줄었다(393×696 실측, 행성 지름 35px). 폭 맞춤이면 같은 화면에서 요소가 1.24배다.
  - 대가: 그 화면에서 40단계 중 31단계는 조준할 때 목적지가 가림 띠 밖이다. 아래 훑어보기와 미니맵으로 메운다.
- 맵이 화면보다 좁은 축은 가운데 정렬하고 여백은 `void` 색.
- **클램프:** 가로는 맵 안. 세로는 가림 띠만큼 맵 바깥까지 — 맵 맨 위·아래가 HUD 밑에 갇히지 않게. 띠 사이에 맵이 다 들어가면 그 사이 가운데.
- **`ready` 진입 시(`frameStart`):** 들어가는 만큼 넓게 담는다 — ① 단계의 물체 전부 ② 발사대와 목적지 ③ 둘 다 안 되면 발사대를 목적지 반대쪽 가장자리에 붙여 목적지 쪽을 최대한 보인다.
- **훑어보기:** 단계를 처음 열 때 목적지가 안 보이면, 목적지를 0.6초 보여 준 뒤 0.9초에 걸쳐 발사대 장면으로 내려온다(끝에서 살짝 지나쳤다 돌아옴, §12.7). 화면을 누르면 바로 끝난다. 재시도·모션 줄이기에서는 하지 않는다.
- **미니맵**은 맵이 다 안 보이고, 단계의 물체도 한 화면에 다 안 들어갈 때만 띄운다(빈 가장자리만 가려지면 띄우지 않는다). 자리는 잰 HUD 아래 끝 바로 밑.
- **`flying`:** 목표점 = 우주선 위치 + 속도 × 0.35(앞을 조금 더 보여줌). `cam += (목표 − cam) × (1 − e^(−6·dt))`로 감쇠 추적한다.
- **미니맵 이동 중에는 보간을 끈다**(즉시 반응해야 한다).
- **월드 → 화면 변환은 카메라만 제공한다.** `ctx.setTransform`으로 한 번 걸고 그 안에서는 월드 좌표로만 그린다. 선 굵기는 월드 단위로 주되 `max(1/scale, 굵기)`로 바닥을 둔다 — **화면 기준으로 굵기를 계산하면 배율이 두 번 먹는다**(v4에서 실제로 낸 버그다).
- **맵 경계 표시:** 맵 사각형을 옅은 선으로 그리고 모서리에 짧은 꺾쇠. 맵 밖은 사선 해칭으로 "벽"임을 표시.

## 12. 렌더링 명세

**테마: "달토끼 당근 로켓" — 8비트 픽셀 아트**(v5 이후, Claude Design 시안). 시안 원본과 통합 안내는 `docs/design/rabbit-rocket/` 에 있다(`INTEGRATION.md`). 그 전의 아스테로이드식 벡터 선화는 이 테마로 대체되었다.

필드는 `src/render/field.ts`의 `FieldRenderer` 하나가 §12.2 순서대로 그린다. 요소마다 객체나 DOM을 만들지 않는다 — 그리기 순서를 명시적으로 통제하기 위해서다. `requestAnimationFrame` 한 번에 화면 전체를 다시 그린다.

**한 아트 픽셀 = 월드 1유닛.** 스프라이트 크기가 곧 판정 크기다(§5.4) — 반경 22 행성은 지름 45px 원으로 찍힌다. 그림이 판정과 어긋나면 "닿지 않았는데 부딪혔다"가 되므로, 반경이 바뀌는 그림은 아틀라스가 아니라 **생성기**가 그 반경으로 만든다.

### 12.0 스프라이트 파이프라인

| 파일 | 내용 |
|---|---|
| `src/render/sprites/pixel.ts` | 격자(`Grid`: 칸마다 팔레트 글자 하나)·외곽선·최근접 회전·시드 난수. 시안 `sprites.js` 를 그대로 옮겼다 |
| `src/render/sprites/rocket.ts` | 토끼 로켓 7표정(idle·aim·fly·win·bump·sad·sleep) × 16방향, 불꽃 2프레임, 귀 젖힘, UFO, 작은 효과(점·×·총알·먼지·별·zz·반짝이) |
| `src/render/sprites/world.ts` | 행성(반경·색 세트·고리), 달, 블랙홀, 토끼굴(포털), 소행성(시드·16프레임), 별 타일 |
| `src/render/sprites/bake.ts` | `Grid` → 오프스크린 캔버스로 한 번 구움(`SpriteCache`). 단계별 그림은 `L:` 접두어로 묶어 단계를 바꿀 때 버린다 |

- **아틀라스 PNG 는 싣지 않는다.** 생성기가 시안의 아틀라스와 **픽셀 단위로 같은** 그림을 만든다는 것을 `tests/sprites.test.ts` 가 182프레임의 해시(`tests/fixtures/atlas-frames.json`)로 지킨다. 생성기를 고치면 이 테스트가 먼저 깨진다. (소행성은 시안의 시드를 알 수 없어 제외 — 게임에서는 단계의 `seed` 를 쓴다.)
- **저해상 월드 버퍼:** 월드를 1유닛 = 1px 인 오프스크린 캔버스(뷰 크기 + 2)에 먼저 그리고, 화면 캔버스에 **최근접 확대 한 번**으로 올린다(`src/main.ts` 의 `draw`). 카메라 소수 오프셋은 기기 픽셀 단위로 맞춰 떨림이 없다. 스프라이트를 화면 해상도로 하나하나 그리던 때보다 저사양에서 빠르다(§18).
- 배율은 **맞춤(§11) 그대로 소수**다. 시안은 정수 배율을 권하지만 390×844 화면에서 정수로 내리면 맵이 화면 폭의 68% 로 줄어든다. 소수 배율의 픽셀 크기 차이(한 칸이 2px 또는 3px)는 최근접 확대라 번지지 않는다. **결정(사용자 확인): 맞춤 배율을 유지한다.**

### 12.2 그리기 순서

하늘(맵 바깥 → 맵 → 별) → 맵 꺾쇠 → 중력 범위 → 외계인 사격 범위 → 직전 궤적 → 궤적 → 소행성 → 행성 → 블랙홀 → 외계인 → 목적지 → 총알 → 발사대(달·눈금·방향 표시) → 예측선 → 우주선과 끝 연출

### 12.3 요소별

- **별:** 192×192 별 타일(시드 고정)을 반복해 깐다. 카메라 이동의 30%만 따라가는 시차. 맵 안에만 보인다. 타일이 작으면 같은 무늬가 벽지처럼 보여 시안의 64 보다 키웠다.
- **맵 경계:** 네 모서리에 길이 24의 2px 간격 점 꺾쇠(`dim`). 맵 바깥은 `void` 색.
- **행성:** 반경 `r` 의 구(球) 스프라이트. 색 세트는 `sides % 6` 으로 고른다(단계마다 고정). `ring: true` 면 고리. 회전하지 않는다.
- **중력 범위:** 반경 `R` 의 1px 점선 원(4 찍고 6 쉼, `gravity`). 안쪽으로 줄어드는 성긴 점선 원 하나가 2.4초 주기로 세 단계 깜빡이며 "끌려 들어감"을 보인다. 블랙홀은 `hole` 색, 1.2초 주기.
- **블랙홀:** 검은 핵 + 짙은 띠 + 강착 원반, 8프레임 회전. 시안의 크기 그대로면 검은 부분이 지평선 판정(`rH + 2`)보다 작아 "검은 곳에 안 닿았는데 빨려 들어갔다"가 되므로 **검은 부분(그림 반경의 0.75)이 판정을 덮도록** 그림 반경을 `(rH + 2) / 0.75` 로 키운다(`holeArtRadius`).
- **소행성:** `rock(r, seed, frame)` 16프레임으로 천천히 돈다. 판정은 §5.4대로 원.
- **외계인:** UFO 2프레임 교대. 사격 범위는 `danger` 점선 원, 비행 중 우주선이 안에 있으면 짙은 빨강과 번갈아 깜빡인다.
- **총알:** 4×4 스프라이트.
- **목적지:** 토끼굴(포털), 반경 `goal.r` 전체가 도착 판정, 8프레임.
- **우주선:** 당근 로켓에 탄 토끼. 16방향(22.5° 간격) 프레임, 표정은 상태로 고른다 — 준비 `idle`, 조준 `aim`, 비행 `fly`(불꽃 2프레임, 귀 젖힘), 도착 `win`, 충돌 `bump` → `sad`, 표류 `sleep`.
- **발사대 행성(§5.9):** 반경 18(`DOME_DRAW_R`)의 달. 돔 중심 방향 ±`ARC` 에 15°마다 1px 눈금 점, 45°마다 길게 — **이 눈금이 각도 눈금이다.** 조준 중에는 `line`, 평소에는 `dim`. 발사 전 로켓은 `PAD_R + 4` 에 서 있다가 발사 후 0.1초에 걸쳐 발사 좌표(`PAD_R`)로 붙는다 — 그림만의 보정이고 물리는 `PAD_R` 에서 나간다.
- **방향 표시 힌트(§14.3):** 달 바깥(로켓 너머)에 성공 구간을 `win` 색 2px 점 쐐기로. 조준 중이 아니면 한 칸씩 건너뛴다.
- **궤적:** 1px 점(`line`). 재시도 시 직전 시도 궤적을 `dim` 색으로 1회분 유지.
- **예측선:** 2×2 노랑 점을 6스텝(0.025초)마다 — 성기면 노란 별과 섞여 한 줄로 읽히지 않는다. 점은 바깥으로 흐른다(모션 줄이기면 멈춤). 충돌 예측 지점엔 × 스프라이트.
- **충돌:** 그 자리에서 75ms 간격으로 좌우 떨림(+2 −2 +2 −1 +1 −1 0), 앞에 먼지 2프레임, 머리 위에 어지러운 별 셋이 돈다. 진행도 0.9 부터 `sad`. 블랙홀은 떨림 대신 돌며 작아진다. 표류(30초)는 잠든 얼굴과 zz.
- **도착:** 토끼굴 중심으로 빨려 들어가며 16방향 프레임이 빠르게 돌고, 둘레에 반짝이 6개.

끝 연출은 진행도(0~1)만 시간으로 계산하고, 그리기는 §12.2 순서 안에서 한다. 파티클 시스템을 따로 두지 않는다.

### 12.4 모션 줄이기

설정에 **모션 줄이기** 항목을 둔다(§13.6). 켜면 중력 범위 수축 링·포털·블랙홀·소행성·UFO의 프레임 교대, 예측선 흐름, 불꽃, 충돌 떨림과 별 회전을 끄고 정지 그림만 남긴다. 게임 규칙 정보(범위·충돌 표정·먼지)는 그대로 보인다.

기본값은 **OS 설정을 따른다**: `matchMedia('(prefers-reduced-motion: reduce)')`가 참이면 켜진 상태로 시작한다. 사용자가 설정에서 직접 바꾸면 그 값이 우선하고 저장된다. (v4에서는 엔진이 OS 설정을 읽지 못해 앱 자체 설정만 두었는데, 웹으로 돌아오면서 되살아난 항목이다.)

### 12.6 테마 (v5에서 추가)

색을 나중에 갈아 끼울 수 있게 **토큰 한 겹**을 둔다. 지금 테마는 하나(`dark`)뿐이고 선택 UI도 두지 않지만, 구조만 지켜 두면 나중에 테마를 더하는 일이 "색 목록 하나를 더 쓰는 작업"이 된다.

**규칙**

- 캔버스 색은 전부 `src/render/palette.ts`(`NES`·`PIX`·`C`)에서만 꺼낸다. **`#RRGGBB`나 `rgba(...)` 리터럴을 다른 파일에 쓰지 않는다.** 게임 화면은 투명도를 쓰지 않는다(§12.1). `alpha()` 는 에디터·도구용이다.
- DOM 색은 전부 `src/ui/styles.css`의 `:root` CSS 변수(`--sky`, `--ink`, `--paper`, …)로만 쓴다. 변수마다 NES 칸 번호를 주석으로 단다. 규칙 안에서 색 리터럴을 직접 쓰지 않는다.
- `npm run check`의 **색 리터럴 검사**(`tools/check-colors.mjs`)가 위 두 곳 밖의 색 리터럴을 오류로 잡는다.

**테마가 지켜야 하는 것 — 색이 규칙을 나타낸다**

| 의미 | 반드시 지켜져야 하는 것 |
|---|---|
| 중력 범위 | 궤적·눈금(`line`)과 확실히 다른 색 |
| 블랙홀 | 행성 중력과 다른 색 (다른 규칙이다) |
| 위험 | 외계인·총알·사격 범위가 **경고로 읽히는** 색 |
| 목적지 | 나머지 어느 것과도 헷갈리지 않는 단독 형태(토끼굴) |

- 색으로만 구분되지 않게 형태도 다르다(위험은 붉은 점선 원과 UFO, 목적지는 토끼굴). **테마를 바꿔도 형태가 뜻하는 바는 건드리지 않는다.**
- 글자는 밝은 패널(`--paper`·`--white`) 위의 검정(`--ink`)이라 대비가 충분하다. 하늘(`--sky`) 위에 글자를 직접 놓지 않는다.

**결정(v5 이후):** 화풍 전환은 범위 밖(§20)이었으나 사용자가 Claude Design 으로 만든 시안을 주어 **픽셀 아트로 전환했다.** 렌더러를 다시 썼고(§12.0~12.3), 물리·판정·레벨 데이터는 건드리지 않았다. 색 테마를 하나 더 두는 일은 이제 `PIX`·`C`·`:root` 를 갈아 끼우는 작업이다. 테마 선택 UI는 테마가 2개 이상 생기는 시점에 §13.6 설정에 추가한다.

### 12.7 탄성 (v5 이후)

사용자 요청: "반응이 너무 빠르고 정직하다." 그림과 화면에만 용수철을 넣는다. **물리·판정·조준 각도는 그대로다** — 조준선과 실제 발사 각도가 어긋나면 퍼즐이 거짓말을 하게 된다.

- 캔버스(`src/render/spring.ts` 의 감쇠 용수철, `putScaled` 로 늘이고 줄여 찍는다):
  - 로켓: 조준을 시작하면 달 쪽으로 웅크리고(놓으면 튀어 오름), 발사 순간 진행 방향으로 늘어났다 출렁이며 돌아온다.
  - 달: 발사 반동으로 발사 방향으로 눌린다.
  - 행성·블랙홀: 로켓이 중력 범위에 들어서는 순간, 그리고 부딪힌 천체가 출렁인다(가로로 늘면 세로로 준다).
  - 토끼굴: 도착하면 크게 한 번 튄다.
  - 카메라 훑어보기는 끝에서 살짝 지나쳤다 돌아온다.
  - **충돌 흔들림**(코드 검토 3): 부딪힌 직후 0.2초, 화면이 2~3 유닛 떨린다(`crashShake`). 카메라 값은 두고 찍을 때만 밀어 물리·입력 좌표는 그대로다. 도착·표류에는 없다.
- DOM(`styles.css`): 버튼은 눌리면 줄었다가 놓으면 튀어 돌아온다. 판·카드·타이틀 버튼은 튀어나오듯 나타나고(카드는 차례로), 결과·힌트 시트는 아래에서 솟는다. 단계가 바뀌면 HUD 의 단계 번호가 한 번 튄다.
- 모션 줄이기(§12.4)를 켜면 전부 끈다 — 게임 설정은 `<html class="reduce">`, OS 설정은 `prefers-reduced-motion`.

## 13. UI와 문구

모든 화면은 안전 영역을 반영한다(CSS `env(safe-area-inset-*)`, `index.html`에 `viewport-fit=cover`). 글꼴은 픽셀 글꼴 **Galmuri11/Galmuri14**(한·영·일), 중국어는 **Fusion Pixel 12px SC**(§13.7). 저장소에 실은 서브셋이며 외부에서 받지 않는다(§15.4). 색·글꼴·버튼 스타일은 `src/ui/styles.css`의 `:root` 변수에 모은다(§12.6).

### 13.1 타이틀

- 로고 "SWINGBY"를 Galmuri14 로 크게, 검정 외곽선과 보라 그림자(픽셀 글자), 아래 작은 글씨로 "스윙바이".
- 배경에서 토끼 로켓이 행성을 스쳐 꺾여 나가는 1-1 데모가 반복 재생. (시안의 타이틀은 고정 장식 장면이었지만, "이 게임이 무엇인지"를 첫 화면에서 보여 주는 데모를 남겼다.)
- 버튼 넷(v5 이후, 사용자 결정): **스테이지**(단계 선택으로. 나중에 스토리 모드), **인피니티**(§22.3. 6-1 을 깨기 전에는 잠겨 "6-1 을 깨면 열려요"), **설정**, **언어 · Language**(§13.7 의 언어만 고르는 화면).

### 13.2 단계 선택

- 상단에 장 탭(1장 행성, 2장 블랙홀 …). 탭 아래에 단계 카드 그리드(초반부 8칸은 2열 4행, 후반부 10칸은 2열 5행).
- 카드: 단계 ID, 이름, 클리어 표시(✓), 잠김 표시. 깬 단계에는 **별(★★☆)과 최고 비행 시간**을 한 줄 더 — 다시 와서 더 잘 깰 이유를 보여 준다. 머리에 그 장의 별 합계 "★ 12/24".
- 단계는 순서대로 열린다. **앞 장에서 6칸을 끝내면(클리어 또는 건너뜀, `CHAPTER_OPEN`) 다음 장 탭과 그 장의 첫 칸이 열린다.** 전에는 8칸 전부였다 — 한 칸에 막혀 접는 이탈을 줄이려고 코드 검토 3 에서 완화했다(사용자 결정 2026-10). 남은 두 칸은 그대로 열려 있어 언제든 돌아와 깬다. 탭 아래에 "{k}칸 더 깨면 {n}장이 열려요" 안내. 개발자용 `?open`(§22.1)이면 전부 열림.
- **별 3개**(`src/levels/stars.ts`, 순수): 깨면 ★, **이번 방문에서 3회 안에** 깨면 ★, **힌트 없이**(긴 예측선·방향 표시가 이 단계에 없음) 깨면 ★. 단계마다 최고치를 저장한다(`LevelSave.stars`). 힌트는 단계에 영영 남으므로(§14.3) 한 번 받으면 셋째 별은 닫힌다 — 힌트의 값이다. 옛 저장의 깬 단계는 별 하나로 친다.
- 장 탭 옆 `?` 버튼으로 그 장의 새 요소 소개 카드(§7.4)를 다시 볼 수 있다.
- 상단 뒤로 버튼 → 타이틀.

### 13.2.1 새 요소 소개 카드

- `meta.intro`가 있는 단계를 처음 시작할 때, 게임 화면 위에 카드 한 장을 띄운다. 요소 그림(해당 요소를 벡터로 작게 애니메이션) + 제목 + 설명 한두 문장 + **확인** 버튼.
- 본 기록은 저장 데이터 `seen_intros`에 남긴다.

### 13.3 HUD (플레이 중)

- 좌상단: 뒤로 버튼(단계 선택으로), 단계 표기 `1-1 첫 스윙바이`
- 우상단: 힌트 버튼(전구 아이콘, 받은 힌트가 있으면 작은 점 표시), 재시작 버튼(원형 화살표 아이콘)
- 조준 중 화면 하단: `각도 23.5°`
- 첫 시도의 `ready` 상태에서만 하단에 레벨 `hint` 표시, 조준 시작하면 사라짐.
- 버튼은 최소 `dp(44)` × `dp(44)` 터치 영역.

### 13.4 결과 화면 문구

| 결과 | 제목 | 안내 |
|---|---|---|
| `win` | 도착했어요 | 비행 시간 {n.n}초 · 시도 {n}회 |
| `planet` | 행성에 충돌했어요 | 조금 더 바깥쪽으로 스쳐 지나가 보세요 |
| `hole` | 블랙홀에 빨려 들어갔어요 | 블랙홀 중심에서 거리를 더 두세요 |
| `shot` | 외계인 포격에 맞았어요 | 붉은 원 안에 머무는 시간을 줄여 보세요 |
| `ufo` | 외계인 우주선과 충돌했어요 | 발사 각도를 조금 바꿔 보세요 |
| `rock` | 소행성에 부딪혔어요 | 발사 각도를 조금 바꿔 보세요 |
| `wall` | 맵 경계에 부딪혔어요 | 궤도가 덜 꺾였어요. 행성에 조금 더 가까이 지나가 보세요 |
| `drift` | 30초 안에 도착하지 못했어요 | 행성 주위를 맴돌지 않게 각도를 바꿔 보세요 |

버튼: 실패 시 **다시 시도**(주 버튼), **단계 선택**, 이 단계에서 2회 이상 실패했으면 **힌트 보기**. 성공 시 **다음 단계**(주 버튼), **다시 하기**, **단계 선택**. 장의 마지막 단계 성공 시 **다음 장** 버튼과 "{n}장을 클리어했어요" 문구. 준비된 마지막 단계 성공 시 "준비된 단계를 모두 클리어했어요" 문구.

- 성공 시 안내 아래에 **별 세 칸** "★ 클리어 · ★ 3회 안에 · ☆ 힌트 없이"(§13.2) — 못 받은 칸은 ☆ 로 조건을 보여 다음에 노릴 것을 알린다. 최고 비행 시간을 줄였으면 안내 끝에 "· 최고 기록!".
- 결과 화면은 반투명 오버레이로, 뒤의 궤적이 보이게 한다.
- 실패 결과는 재시도 버튼을 누르지 않고 **화면 아무 곳이나 탭해도 재시도**되게 한다(연속 시도 흐름). 단, 버튼 영역 탭은 해당 버튼 동작만 한다. 실패 연출(0.8초) 중에도 0.3초 뒤부터 탭이 통한다. **성공 시트에는 걸지 않는다** — 궤적을 보려고 탭한 사람이 "다음 단계" 를 잃지 않게(코드 검토 3).

### 13.5 힌트 시트

- HUD 힌트 버튼이나 결과 화면 **힌트 보기**로 연다. 화면 아래에서 올라오는 패널.
- 시트가 열려 있는 동안 단계 시계는 멈춘다(공전 단계의 타이밍 보호).

| 항목 | 설명 문구 | 버튼 상태 |
|---|---|---|
| 긴 예측선 | 궤도를 더 멀리까지 미리 볼 수 있어요 | 광고 보고 받기 / 적용됨 |
| 방향 표시 | 성공하는 발사 방향을 알려 드려요 | 두 번 실패하면 열려요 / 광고 보고 받기 / 적용됨 |
| 건너뛰기 | 이 단계를 넘기고 다음 단계를 열어요 | 다섯 번 실패하면 열려요 / 광고 보고 건너뛰기 |

- 첫 힌트 무료 조건이면 버튼 문구는 **무료로 받기**, 받은 뒤 "이번 힌트는 무료로 드렸어요" 안내.
- 광고를 중간에 닫았을 때: "광고를 끝까지 보면 받을 수 있어요"
- 광고를 불러올 수 없을 때(버튼 비활성): "지금은 광고를 불러올 수 없어요. 잠시 후 다시 시도해 주세요"

### 13.6 설정

- 타이틀과 단계 선택 화면의 톱니바퀴 버튼으로 연다.
- 항목: **언어**(§13.7), 효과음 켬·끔, 진동 켬·끔, **모션 줄이기 켬·끔**(§12.4), 개인정보 옵션(해당 지역에서만), 개인정보처리방침(외부 링크), 버전 정보.

### 13.7 언어

한국어·영어·일본어·중국어(간체) 네 가지. **한국어가 원본이다** — §13.1~13.6 의 문구가 `src/i18n/ko.ts` 에 그대로 있고, 다른 언어는 그 키를 따른다.

| 무엇 | 어디 | 원문 |
|---|---|---|
| 화면 문구 | `src/i18n/{ko,en,ja,zh}.ts` | `ko.ts` |
| 단계 이름·힌트 | `src/i18n/levels.ts` (`LEVEL_TEXT`) | 단계 JSON 의 `name`·`hint` |
| 장 이름 | `src/i18n/levels.ts` (`CHAPTER_NAME`) | `chapters.ts` (`tools/register.ts` 의 `NAMES`) |

- **기본값은 `auto`** — 브라우저 선호 언어 목록(`navigator.languages`)에서 처음 맞는 것, 없으면 영어. 중국어는 지역을 가리지 않고 간체로 보낸다(번체를 따로 두게 되면 `detectLang` 에서 가른다). 설정에서 고르면 그 값이 이긴다. 저장 키는 `settings.lang`.
- **글꼴:** 본문·버튼은 Galmuri11(굵게는 Galmuri11 Bold), 로고·큰 제목은 Galmuri14. 갈무리는 간체자 92자가 없어 **중국어는 Fusion Pixel 12px SC** 를 앞에 둔다(`:lang(zh-Hans)`). 갈무리 굵은꼴에는 가나·한자가 없어 `unicode-range` 로 굵게도 보통 파일을 쓰게 하고 `font-synthesis: none` 으로 가짜 굵게를 막는다. 서브셋은 `npm run fonts`(`tools/subset-fonts.py`, `tools/font-chars.ts` 가 사전·단계 이름에서 글자를 모은다)로 다시 만든다. **`tests/fonts.test.ts` 가 네 언어 문구의 모든 글자가 그 언어의 글꼴에 있는지 본다** — 문구를 고치고 서브셋을 안 다시 만들면 CI 가 멈춘다. ✓ 하나만 시스템 글꼴로 넘어간다(픽셀 글꼴에 없다).
- 타이틀의 **언어** 버튼은 언어만 고르는 화면을 연다(자동 + 네 언어, 큰 버튼). 설정의 언어 칸도 그대로 둔다.
- 설정의 언어 이름은 **각 언어로** 쓰고(`한국어`·`English`·`日本語`·`简体中文`), 항목 이름에도 `· Language` 를 곁들인다. 못 읽는 언어로 바뀌어도 자기 언어를 찾아 돌아올 수 있어야 한다.
- `<html lang>` 을 바꾼다(중국어는 `zh-Hans`). 한자는 같은 코드라도 한·중·일 자형이 다르므로 **본문 글꼴을 언어마다 따로 준다**(`styles.css` 의 `--text`). 한국어는 띄어쓰기에서만(`keep-all`), 일본어는 문절 단위로(`auto-phrase`) 줄을 바꾼다.
- **관문:** `tests/i18n.test.ts` 가 키 누락·자리표시자 불일치·빈 문구를 막고, **등록된 단계마다 세 언어의 이름이 있는지**(원문에 힌트가 있으면 힌트도) 본다. 새 단계를 등록하고 번역을 빠뜨리면 CI 가 멈춘다.
- **§18 크기 확인:** 360×640 과 430×932 에서 네 언어 모두 HUD 가 겹치거나 버튼 글자가 줄바꿈되지 않는다. 자리가 모자라면 단계 이름이 두 줄에서 잘린다(전체 이름은 단계 선택 카드에 있다).
- 번역은 Claude 가 썼다. **출시 전에 원어민 검수**를 받는다. 개인정보처리방침·스토어 문구는 아직 한국어뿐이다.

## 14. 광고와 힌트

### 14.1 원칙

- 광고는 흐름을 끊지 않는 곳에만 둔다. **조준·비행 중 화면에는 어떤 광고도 없다.**
- 수익의 중심은 **보상형 광고**(플레이어가 원해서 보는 광고)다. 전면 광고는 빈도를 엄격히 제한한다.
- 배너 광고는 쓰지 않는다. 한 손가락 터치 게임이라 실수 클릭 위험이 크고 화면도 좁다.
- 광고 판단 로직은 `monetization/`의 순수 함수로 작성하고 테스트한다. 실제 SDK 호출은 `src/platform/ads.ts`의 `AdProvider` 인터페이스 뒤에 둔다.
- 광고를 불러오지 못하거나 오프라인이어도 게임은 완전히 동작해야 한다.

### 14.2 광고 제공자 구조

웹과 앱의 광고 SDK가 다르므로 인터페이스 하나 뒤에 제공자를 갈아 끼운다. 게임 코드는 어느 쪽인지 모른다.

```ts
export type RewardPlacement = 'hint_preview' | 'hint_direction' | 'skip';
export type RewardResult = 'rewarded' | 'dismissed' | 'failed';

export interface AdProvider {
  init(): Promise<void>;                                  // 동의 절차 포함
  isRewardedReady(): boolean;
  showRewarded(placement: RewardPlacement): Promise<RewardResult>;
  isInterstitialReady(): boolean;
  showInterstitial(): Promise<'shown' | 'failed'>;
  canOpenPrivacyOptions(): boolean;
  openPrivacyOptions(): Promise<void>;
}
```

- 호출 측은 반드시 타임아웃(10초)을 걸고, 초과하면 `'failed'`로 처리한다.
- **MockAdProvider** (`ads-mock.ts`, 개발 기본): 화면에 "테스트 광고" 오버레이를 2초 띄운 뒤 결과 반환. 쿼리 `?ads=fail`이면 항상 실패, `?ads=dismiss`면 항상 중간에 닫힘, `?ads=slow`면 5초 지연. 예외 흐름 확인용.
- **H5AdProvider** (`ads-h5.ts`, **웹 출시**): Google **H5 Games Ads**(Ad Placement API의 `adBreak`/`adConfig`). AdSense 또는 Ad Manager 계정과 **게임 도메인 승인**이 필요하다. 웹에서 AdMob SDK는 쓸 수 없다 — AdMob은 앱 전용이다.
  - 보상형은 `adBreak({ type: 'reward', beforeReward, adDismissed, adViewed, adBreakDone })`, 전면은 `type: 'next'`.
  - **광고가 뜨기 전에 게임 루프와 소리를 멈춘다**(`beforeAd`), 끝나면 재개(`afterAd`). 고정 스텝이라 멈췄다 이어도 결과가 달라지지 않는다(§5.8).
  - `adConfig`의 `preloadAdBreaks: 'on'`으로 미리 받아 둔다. `onReady` 전에는 `isRewardedReady()`가 거짓이다.
  - 승인 전이거나 광고 차단기가 있으면 스크립트가 아예 뜨지 않는다. **그 경우 Mock으로 넘어가지 말고 "광고 없음" 상태로 동작한다** — 힌트 버튼은 §13.5의 "지금은 광고를 불러올 수 없어요"를 보이고, 게임은 완전히 동작한다.
- **AdMobAdProvider** (`ads-admob.ts`, **앱**): Capacitor AdMob 플러그인으로 구현. 착수 시점에 Capacitor 버전과 호환되는 플러그인 버전을 확인해 `CLAUDE.md`에 고정 기록한다.
- 어느 제공자를 쓸지는 `src/platform/capabilities.ts`가 실행 환경(Capacitor 여부)으로 정한다. 개발 빌드는 언제나 Mock.
- 개발·비공개 테스트 빌드는 **반드시 각 SDK가 제공하는 테스트 모드**를 쓴다(AdMob 테스트 광고 ID, H5는 `adBreakTest`). 실제 광고 단위 ID는 출시 빌드에서만.
- 광고 단위 ID·퍼블리셔 ID는 `src/platform/ads.config.ts`(git 제외)에서 읽고, 형식 예시 `ads.config.example.ts`를 저장소에 둔다. 웹 빌드의 퍼블리셔 ID는 결국 스크립트 태그로 공개되지만 **저장소에는 두지 않고** 빌드 시 환경 변수로 주입한다.

**웹 광고의 한계 (v5에서 새로 인지한 것)**

- 웹 CPM은 앱보다 낮다. **웹은 유입과 검증, 수익의 중심은 앱**으로 본다.
- H5 Games Ads는 도메인 승인이 필요하고 심사에 시간이 걸린다. **M9 시작 전에 신청해 둔다.**
- 광고 차단기 사용률이 데스크톱에서 높다. 기대치는 모바일 웹 기준으로 잡는다.

### 14.3 보상형 광고: 힌트와 건너뛰기

| 항목 | 효과 | 열리는 조건 | 유지 |
|---|---|---|---|
| 긴 예측선 | 이 단계의 예측선 길이가 2.5초로 늘어남 | 언제든 | 이 단계에 영구 적용 |
| 방향 표시 | 조준할 때 우주선 둘레에 성공 발사 방향을 초록 호로 표시. 공전 단계는 공전 궤도 위에 "이 구간에 있을 때 발사" 표시도 추가 | 이 단계에서 2회 이상 실패 | 이 단계에 영구 적용 |
| 건너뛰기 | 이 단계를 `skipped`로 기록하고 다음 단계를 엶 | 이 단계에서 5회 이상 실패 | 나중에 직접 클리어하면 `cleared`로 바뀜 |

- 방향 표시의 호는 `meta.solution.angle`을 중심으로 `meta.metrics.main_window`의 80% 폭으로 그린다(구간 가장자리는 불안정하므로). 공전 표시는 `meta.metrics.timing_range`를 공전 각도로 바꿔 그린다.
- **첫 힌트 무료:** 게임 전체에서 처음 쓰는 힌트(긴 예측선 또는 방향 표시) 1회는 광고 없이 준다. 건너뛰기는 해당 없음.
- 광고를 끝까지 보지 않고 닫으면 보상 없음.
- 모든 단계가 `cleared` 또는 `skipped`면 다음 장이 열린다. 단계 선택 카드에서 건너뛴 단계는 ↷ 표시로 구분한다.

### 14.4 전면 광고 규칙 (`ad_policy.should_show_interstitial`)

전면 광고는 **성공 후 [다음 단계]로 넘어갈 때만** 검토하고, 아래를 **모두** 만족할 때만 보여준다.

1. 넘어가는 단계가 2장 이후다(1장 전체는 광고 없음).
2. 마지막 전면 광고 이후 클리어 3회 이상.
3. 마지막 전면 광고 이후 180초 이상.
4. 앱 실행 후 120초 이상.
5. 최근 90초 안에 보상형 광고를 보지 않았다.
6. 넘어가는 단계에 새 요소 소개 카드가 뜨지 않는다.

- 실패 후 재시도, 단계 선택으로 이동, 앱 복귀, 앱 시작 시에는 절대 호출하지 않는다.
- 광고가 준비되지 않았으면 기다리지 않고 바로 다음 단계로 넘어간다.
- 수치(3회, 180초, 120초, 90초)는 `src/monetization/ad-policy-config.ts` 한곳에 모은다.
- 시각은 `performance.now()`나 `Date.now()`를 직접 읽지 않고 **호출자가 넘긴 값**으로 판단한다(§2.1의 순수 규칙, 테스트 가능).

### 14.5 동의와 개인정보

- **앱:** 첫 실행 시 Google UMP(사용자 메시지 플랫폼) 동의 절차를 거친다. 양식은 법적으로 필요한 지역 사용자에게만 뜬다. 이어서 iOS에서는 앱 추적 투명성(ATT) 요청을 띄운다. 거부하면 비개인화 광고로 동작한다.
- **웹:** H5 Games Ads는 AdSense/Ad Manager의 동의 처리를 따른다. 별도 UMP 호출이 없으므로 게임이 할 일은 **개인정보처리방침 링크를 설정 화면에 두는 것**뿐이다(§13.6, §15.5). 쿠키·광고 식별자를 게임 코드가 직접 다루지 않는다.
- iOS 추적 요청 문구(`NSUserTrackingUsageDescription`): "맞춤 광고를 보여드리는 데 사용돼요. 허용하지 않아도 게임은 똑같이 즐길 수 있어요."
- 설정 화면의 **개인정보 옵션**으로 동의 양식을 다시 열 수 있다(해당 지역에서만 표시).
- 게임 코드 자체는 개인정보를 수집·전송하지 않는다. 수집 주체는 광고 SDK뿐이며, 스토어 신고와 개인정보처리방침(§15.5)도 이 기준으로 작성한다.

### 14.6 테스트 (`ad-policy.test.ts`, `hints.test.ts`)

- 전면 광고 규칙 1~6 각각의 경계값(예: 179초 거부, 180초 허용).
- 실패 후 재시도 경로에서 전면 광고 판단이 호출되지 않음.
- 힌트 열림 조건(실패 2회, 5회), 첫 힌트 무료 1회, 건너뛰기 후 다음 단계·다음 장 열림 판정.
- 보상형 결과가 `dismissed` 또는 `failed`면 보상이 주어지지 않음.

## 15. 플랫폼과 스토어 출시

출시 형태가 둘이다. **웹이 먼저, 앱이 그다음.** 코드베이스는 하나이고 앱은 그것을 Capacitor로 감싼 것이다.

### 15.1 웹 출시 (첫 번째 출시 형태)

v4에서는 웹이 "개발 중 확인 수단"이었고 출시는 범위 밖이었다(v4 §20). v5에서는 **첫 번째 출시 형태**다. 설치 없이 링크로 도달하는 경로가 광고 수익에서 앱보다 앞선다.

- 기본 브랜치에 푸시하면 `.github/workflows/pages.yml`이 **검사 → 테스트 → 빌드 → GitHub Pages 배포**를 한다. **회귀 테스트(§16.5)가 배포 관문이다.** 깨진 물리는 올라가지 않는다.
- `vite.config.ts`의 `base`는 `'./'`다. 하위 경로에 올라가도 자산을 찾는다.
- 주소: `https://dooholee96-code.github.io/swingbypuzzle/`. 저장소 Settings → Pages → Source를 **"GitHub Actions"** 로 한 번 설정해야 한다.
- 개발 중 폰 확인은 `npm run dev`(같은 Wi-Fi에서 표시된 주소로 접속). **배포 직전 확인은 `npm run preview`** — 개발 서버에서 되는 것이 빌드에서도 된다는 보장은 없다(§16.6).
- **오프라인 동작(M11):** 서비스 워커로 재방문 시 네트워크 없이 실행되게 한다. 캐시 전략은 앱 셸 precache + 버전이 바뀌면 통째 교체. **부분 갱신은 금지** — 물리 코드와 레벨 데이터의 버전이 섞이면 §16.5가 지키는 것이 무너진다.
- **홈 화면에 추가(M11):** `manifest.webmanifest`(이름 "스윙바이", 세로 고정, 아이콘, `display: standalone`, 배경·테마 색은 §12.6 토큰과 같은 값).
- 웹 광고는 §14.2의 `H5AdProvider`. 도메인 승인 신청은 M9 시작 전에.

### 15.2 앱 빌드 (Capacitor)

v4의 Godot 익스포트 자리다. Capacitor는 웹 자산을 WebView로 감싸는 셸이므로 **게임 코드가 그대로다.**

- **Android를 먼저** 빌드한다. iOS는 Mac과 Xcode 환경이 준비되면 추가하며, 그때 게임 코드 변경 없이 플랫폼 폴더만 늘어나도록 유지한다.
- `npx cap add android` → `android/`가 생긴다. **이 폴더는 생성물이므로 git에서 제외**하고, 손으로 고친 설정(권한, 방향 고정, 스플래시)은 `capacitor.config.ts`와 재현 가능한 패치로 둔다.
- 절차: `npm run build` → `npx cap sync` → Android Studio에서 실행·서명.
- 설정: 세로 고정(`android:screenOrientation="portrait"`), 전체 화면, `webContentsDebuggingEnabled`는 디버그 빌드에서만.
- 앱 이름 "스윙바이", 앱 ID `com.<개발자명>.swingby`(출시 전 사용자와 확정).
- **구형 안드로이드 WebView가 유일한 호환성 위험이다.** WebView는 크롬과 함께 갱신되지만 구형 기기에서 뒤처질 수 있다. 빌드 타깃을 **ES2020**으로 낮추고, M12 점검표에 구형 WebView 확인을 넣는다.

### 15.3 플랫폼 계층 (`src/platform/`)

브라우저와 WebView의 차이를 한 곳에 가둔다. 게임 코드는 `capabilities.ts`가 알려주는 것만 본다.

| 기능 | 웹 | 앱 (Capacitor) |
|---|---|---|
| 저장 | `localStorage` | 같음 |
| 진동 | `navigator.vibrate()` (지원 시) | Haptics 플러그인 |
| 뒤로 버튼 | `history.pushState` + `popstate` | `App.addListener('backButton')` |
| 생명주기 | `visibilitychange`, `pagehide` | `App.addListener('appStateChange')` |
| 광고 | `H5AdProvider` | `AdMobAdProvider` |

- **저장:** 시작 시 한 번 읽어 메모리에 두고, 변경 시 500ms 디바운스로 기록. 화면이 숨겨질 때 즉시 기록. 읽기·파싱 실패 시 기본값으로 시작하고 손상 값은 `swingby.save.v1.bak`으로 옮긴다. `localStorage` 자체가 막힌 환경(사생활 보호 모드)에서는 **메모리에만 두고 게임은 정상 동작**한다.
- **생명주기:** 숨겨지면 시뮬레이션 일시정지, 누산기 리셋, 소리 끄기. 돌아오면 그대로 이어서 진행(고정 스텝이라 결과가 달라지지 않음).
- **뒤로 버튼:** 힌트 시트·결과 화면 닫기 → 플레이에서 단계 선택 → 단계 선택에서 타이틀 → 타이틀에서 "게임을 종료할까요?" 확인(앱) 또는 브라우저 기본 동작(웹). 웹에서는 화면을 열 때 `pushState`로 항목을 쌓아 브라우저 뒤로 가기가 같은 흐름이 되게 한다.
- **진동:** 발사 시 가벼운 충격(20ms), 게임오버 시 강한 충격(60ms), 도착 시 짧게 2회. 설정에서 끌 수 있다. iOS 사파리는 `navigator.vibrate`를 지원하지 않으므로 **없으면 조용히 건너뛴다**(오류가 아니다).

### 15.4 성능 규칙

- `ctx.shadowBlur`·CSS `filter: blur()` 금지. 픽셀 테마는 발광을 쓰지 않는다(§12.1).
- 화면 캔버스는 하나. 요소마다 DOM을 만들지 않는다. 오프스크린 캔버스는 **월드 버퍼 하나와 구운 스프라이트**(§12.0 `SpriteCache`)뿐이고, 매 프레임 새로 만들지 않는다.
- `devicePixelRatio` 상한 2.5(§10.0).
- 매 프레임 객체 할당 최소화: 예측선·궤적 점 배열은 미리 잡아 재사용한다.
- **폰트는 저장소에 싣는다.** `src/ui/fonts/` 의 서브셋 4개(Galmuri11·Galmuri11 Bold·Galmuri14·Fusion Pixel SC, 합계 68KB, SIL OFL 1.1 — 원문은 `public/licenses/`)를
  `@font-face`로 선언하고 `font-display:swap`을 준다. CDN에서 받아오지 않는다 —
  첫 화면에 외부 요청이 없어야 오프라인(§15.1)에서 같고, 사용자 IP가 제3자에게 가지 않아
  개인정보처리방침(§15.5)이 단순해진다. 중국어 글꼴은 중국어 글자가 화면에 나올 때만 받는다(`unicode-range`).
- 목표: 중급 Android 기기에서 60fps, 저사양 기기(CPU 4배 감속 기준) 50fps 안팎.

### 15.6 itch.io (v5 이후 추가)

웹 빌드를 itch.io 에도 올린다. 비용 0, 피드백 통로. 절차·설정·문구는 `store/itch/README.md`.
- `npm run build:itch` → `build/itch/swingby-itch.zip`. `VITE_TARGET=itch` 빌드는 두 가지가 다르다:
  - **힌트를 광고 없이 준다**(`FreeHintProvider`). itch 는 자기 도메인(itch.zone)의 iframe 에서 돌려 H5 광고(우리 도메인만 승인)가 뜨지 않는다. 그대로 두면 힌트가 "광고를 불러올 수 없어요" 로 영영 잠긴다. 실패 횟수 조건(§14.3)은 그대로다.
  - **서비스 워커를 쓰지 않는다**(sw.js 도 빼고 묶는다).
- 다른 출처의 iframe 에 띄워 확인했다: 화면, 저장(localStorage), 서비스 워커 0개, 두 번 실패 후 힌트가 "무료로 받기" → 광고 없이 적용.
- 페이지 표지(630×500)는 게임 스프라이트로 따로 그렸고, 스크린샷 다섯 장과 함께 `store/itch/` 에 있다.
- 수익은 "$0 or donate" 정도다. 광고 수익은 우리 웹·앱에서 낸다.

### 15.5 출시 준비물 (`store/` 폴더)

Claude Code가 초안을 만들고 사용자가 확인한다.

- **아이콘·스플래시:** 보라 바탕에 선 토끼 로켓(픽셀). `npx tsx tools/make-icons.ts` 가 스프라이트 생성기에서 favicon·192·512·스토어 1024px 를 한 번에 만든다.
- **스크린샷 구성안 5장:** 스윙바이 궤적, 블랙홀, 외계인, 넓은 맵과 미니맵, 단계 선택. 실제 게임 화면에 짧은 한국어 문구.
- **스토어 문구:** 짧은 설명, 전체 설명, 검색 키워드. 웹용 `<meta name="description">`과 OG 이미지도 같은 문구에서.
- **개인정보처리방침(한국어):** 게임은 개인정보를 직접 수집하지 않고 광고 SDK가 광고 식별자 등을 처리한다는 내용과 문의처. **웹 출시가 먼저이므로 이것이 M9보다 앞선다** — 광고를 켜는 순간 공개 URL이 필요하다. GitHub Pages의 `/privacy`에 함께 올린다.
- **데이터 보안·개인정보 라벨 메모:** 구글 플레이 데이터 보안 양식과 애플 개인정보 라벨에 적을 항목을, 착수 시점의 AdMob 공식 안내 기준으로 정리.
- **타깃 연령:** 콘텐츠는 전체 이용가 수준이지만 스토어 타깃층은 **만 13세 이상**으로 설정한다. 아동을 타깃층에 넣으면 가족 정책과 아동 대상 광고 설정이 추가로 필요해진다.
- **등급 설문:** 구글 플레이와 앱스토어의 연령 등급 설문. "광고 포함" 표시.
- **오픈소스 고지:** 사용한 라이브러리 라이선스 고지를 설정 화면에 포함한다. v5는 런타임 의존성이 없어 v4보다 훨씬 짧다.

## 16. 검증 도구와 테스트

CLI 도구는 `tsx`로 실행하는 평범한 TypeScript 파일이다. 게임과 **같은** `src/core/`·`src/tools-shared/`를 import하므로 결과가 어긋날 수 없다. 레벨을 디스크에서 읽는 것만 `tools/levels-fs.ts`가 맡고, 스키마 검사(`parseLevel`)는 게임과 공유한다.

### 16.1 `npm run solve [단계ID]`

- 각도 −180°~180°를 0.25° 간격으로 전부 시뮬레이션해 결과별 개수와 **성공 연속 구간**을 출력한다.
- 공전 행성이 있는 단계는 주기를 12등분한 발사 시점마다 반복한다.
- 출력 예: `1-1 첫 스윙바이  t=0.00  성공: -69.25..-62.5 (7.00°)  {wall:1219, rock:128, planet:65, win:28}`
- 이 출력이 §6.2 표와 일치하는 것이 M1의 완료 기준이다.

### 16.2 `npm run fan -- <단계> [시작각] [끝각] [간격]` (선택)

궤적을 결과별 색으로 그린 SVG를 `tools/out/`에 저장. 레벨 디자인 시 눈으로 확인하는 용도. SVG는 문자열로 직접 써서 저장한다(렌더링 불필요).

### 16.3 `npm run validate [단계ID|장번호]`

- §8.5 필수 규칙과 경고를 검사하고 표로 출력한다. 인자가 없으면 `chapters.ts`에 등록된 전 단계.
- 실패가 하나라도 있으면 종료 코드 1. 커밋 전에 반드시 실행한다.

### 16.4 `npm run gen -- --recipe <파일> --slot <칸> [--count N] [--seeds N]`

- §8.4 알고리즘. 결과를 `candidates/<단계ID>/cand-XX.json`과 `summary.md`(지표 표), `cand-XX.svg`(궤적 썸네일)로 저장한다.
- 10초마다 진행률 한 줄 출력(§8.4). 시드 단위로 `worker_threads`에 나눈다.
- 끝나면 후보 표와 **떨어진 이유별 개수**를 낸다. 후보가 안 나올 때 레시피의 어느 제약이 빡빡한지가 그 표에서 읽힌다.
- 워커는 부모의 tsx 로더를 물려받지 않으므로 `tools/gen-worker-boot.mjs` 가 한 번 걸어 준다. 저장소에서 `.mjs` 인 파일은 그것과 `tools/check-core.mjs` 뿐이고, 둘 다 로더보다 먼저 도는 코드라서다.

- **배포 전에는 반드시 `npm run preview`로 빌드 결과를 확인한다.** 개발 서버에서 되는 것이 빌드에서도 된다는 보장은 없다(실제로 자산 경로 문제를 한 번 겪었다).

### M20. 인피니티 뱀서라이크 (예정 — 사용자 아이디어 2026-10, 시작은 지시를 받은 뒤)
뱀파이어 서바이버의 "한 판 안에서 자라는 선택"을 인피니티(§22.3)에 옮긴다. 공격은 없다 — 성장은 전부 **살아남는 쪽**이다.
- **범위(사용자 결정):** ① **레벨업·패시브·시간 위협**까지. 영구 성장(판 사이 해금)과 추적 외계인은 뒤로(M21 후보).
- **경험치(사용자 결정):** **버틴 시간 + 당근.** 시간이 기본, 당근은 보너스 — 가만히 돌기만 해도 오르고 위험을 무릅쓰면 빨리 오른다. 당근의 "분사 +1" 은 없어지고 레벨업 카드로 옮긴다. 레벨업 간격은 뒤로 갈수록 길게(1·2·3·5·8… 뱀서처럼).
- **레벨업:** 판이 멈추고(힌트 시트와 같은 `paused` 길) 카드 **3택1**. 카드는 **시드로** 뽑는다 — 오늘의 우주는 같은 날 같은 제안(고르는 건 사람 몫). 고르면 바로 이어 난다. 모션 줄이기면 애니메이션 없이.
- **패시브(초안 8종, 각 3단계):** 분사 최대 +1 / 꺾는 각 40→50→60° / 분사 시간 재충전(20초에 1) / 당근 자석(먹는 반경 16→40→70) / 방패(충돌 1회 무시, 쓰면 다시 받을 수 있다) / 총알 느리게 / 비행 중 예측선 / 포획 링 넓게. 중력 약하게는 **뺀다** — 스윙바이 자체를 없애는 성장이라서.
- **시간 위협:** 지금은 거리(ring)로만 빡세진다. 시간으로도 — 외계인 연사·블랙홀 비율·파편 밀도가 분마다 오른다(칸 생성에 시간 항 하나). 다시 만드는 칸이 바뀌지 않게 **칸을 만들 때의 시각**을 시드에 섞지 않고, 창을 갈아 끼울 때만 밀도 계수를 읽는다.
- **지킬 것:** ① 결정론 — 보정값은 `Sim` 에 객체 하나(`mods`)로 들어가고 스테이지·검증기·리플레이는 빈 객체. 물리 상수는 바꾸지 않는다(§0.4). ② 점수는 그대로 버틴 시간(§22.3) — 성장은 더 오래 버티는 수단이다. ③ HUD 에 경험치 바와 레벨, 받은 패시브 아이콘 줄. ④ 문구는 사전(§0.6).
- **시작할 때 묻는다:** 패시브 8종의 최종 목록과 수치, 레벨업 간격. 먼저 2~3종으로 브라우저에서 손맛을 보고 늘린다.
- **완료 기준:** 레벨업 → 카드 → 이어 날기 → 끝까지 브라우저 확인, 오늘의 우주 두 번이 같은 카드를 내놓는 테스트, 스테이지 회귀(§6.2) 그대로.

### M21. 인피니티 보스전 — 슈팅 구간 (예정 — 사용자 아이디어 2026-10, M20 뒤)
시간이 차면 보스가 나타나고, 그동안은 **1945 같은 세로 슈팅**으로 논다. 평상시(중력 비행) → 경보 → 보스전 → 보상 → 복귀의 리듬이 인피니티에 생긴다.
- **사용자 결정(2026-10):** 조작은 **드래그로 직접 이동**(중력·관성 없음, 데스크톱은 마우스·방향키). 피격은 **보스전에만 목숨 3**(맞으면 잠깐 무적, 다 잃으면 판 끝; 방패 패시브는 목숨 +1). **체력을 다 깎아야 끝** — 우주선은 당근을 **자동 연사**하므로 피하며 조준만 한다. 주기는 **2분마다**, 1분 전에 경보.
- **흐름:** 경보(HUD 깜빡임·소리) → 카메라가 우주선에 멈추고 하늘만 세로로 흐르는 아레나(천체는 그리지 않는다) → 보스(모선 UFO)가 위에서 내려와 패턴으로 탄을 뿌린다 → 체력 0 → 폭발 연출 → 보상(레벨업 카드 1장 + 당근) → 보스전에 들어갈 때의 자리·속도로 중력 비행 복귀. 보스전 시간도 점수(버틴 시간)에 든다.
- **보스:** 처음엔 한 종류, 체력·패턴 수가 회차마다 는다(2회차 탄 두 줄, 3회차 조준탄 추가…). 패턴은 시드로 — 오늘의 우주는 같은 날 같은 보스.
- **구현 틀:** `src/core/boss.ts` 에 **별개의 작은 시뮬레이션**(고정 스텝, DOM 없음). 입력은 "손가락의 월드 위치" 하나를 스텝 경계에서 읽는다. 스윙바이 물리(§5)는 건드리지 않고, 스테이지·검증기·리플레이에는 보스가 없다. 세션은 `mode: 'fly' | 'boss'` 로 갈라 그리기·입력·HUD 를 바꾼다. 그림은 생성기(모선·당근탄·체력 바), 팔레트 칸만(§12.6). 효과음 `shoot` 는 있고, 피격·보스 폭발은 새로.
- **지킬 것:** 한 손가락(§10) — 드래그만으로 다 된다. 고정 스텝·결정론(§5.8) — 같은 입력 기록이면 같은 결과. 모션 줄이기면 탄막 깜빡임·흔들림을 끈다.
- **시작할 때 묻는다:** 보스 생김새(모선 UFO / 거대 소행성 / 블랙홀 눈?), 첫 보스의 체력(=붙잡아 두는 시간, 20~30초 권장), 당근탄 연사 속도.
- **완료 기준:** 경보 → 보스전 → 승리 → 복귀 → 패배를 브라우저로 확인, 같은 시드·같은 입력 기록이 같은 결과인 테스트, 스테이지 회귀(§6.2) 그대로.

## 18. 품질 기준

- 60fps 목표. 한 프레임 물리 스텝은 최대 48회로 제한.
  - 실측(타이틀 데모, 헤드리스 Chromium CPU 감속): 선화 ×1 60 · ×4 33.8 · ×6 21.4 fps → 픽셀 + 월드 버퍼 ×1 60 · ×4 52.0 · ×6 32.8 fps.
- 예측선 계산은 프레임당 1회, 최대 432스텝(1.8초).
- **웹 초기 로드: JS 100KB(gzip) 이하, 첫 화면 전체 200KB 이하.** 현재 JS 46.9KB + CSS 3.3KB(gzip) + 글꼴(한국어 첫 화면 기준 Galmuri 세 파일 56KB, 중국어는 Fusion 13KB 추가). 네 언어 사전이 모두 들어간 값이다(§13.7) — 언어별로 나눠 받으면 6KB 쯤 줄지만 오프라인 캐시가 복잡해져 그대로 둔다. 라이브러리를 들이는 판단은 이 예산에 비추어 한다. (v4에서 엔진 런타임 때문에 뺐던 항목을 되살렸다.)
- **Android 앱 설치 크기 15MB 이하 목표**(Capacitor WebView 셸 + 웹 자산). v4의 35MB는 엔진 런타임을 포함한 수치였다.
- 중급 기기에서 **웹 첫 로드 3초 이내, 재방문 1초 이내**(서비스 워커 캐시). 앱 콜드 스타트 2초 이내.
- 화면 크기 360×640부터 430×932까지(CSS 픽셀) 세로 화면에서 UI가 겹치지 않을 것.
- 발사 입력부터 우주선 이동 시작까지 체감 지연 없음(같은 프레임에 발사).
- 에디터 실시간 검증의 첫 결과(1° 대략 스캔)가 **0.3초 안에** 보일 것(§8.9).
- 접근성: 배경 대비 4.5:1 이상, 터치 목표 44×44 이상, `prefers-reduced-motion` 존중(§12.4).

## 20.1 v4.1 변경 — 발사대 행성

데모(조작 감각 확인용 프로토타입)로 조준 방식을 세 가지 시험한 결과다.

1. **골프식 홀드 스윕**(누르고 있으면 각도가 돌아감) — 시험 후 **버렸다.** 성공 폭이 7~11°인 게임에서 각도가 저절로 돌면 플레이어가 각도를 고르는 게 아니라 잡아채게 되어, 정밀 조준 퍼즐이 타이밍 게임으로 바뀐다. 4장은 공전 타이밍과 겹쳐 이중 타이밍이 된다.
2. **반원 계기판**(우주선은 제자리, 바늘만 회전) — 동작은 하지만 "각도를 설정한다"는 느낌이라 버렸다.
3. **발사대 행성**(우주선이 표면을 걸어 다니다 그 자리에서 이륙) — **채택.** 각도가 설정값이 아니라 우주선이 서 있는 위치가 된다.

바뀐 절: §1(플레이어가 정하는 것), §4(θ의 정의), §5.1(`PAD_R`, `ARC` 추가), **§5.9 신설**, §6.2(4-1 기준값과 돔 반경 측정), §8.4(배치 제약 `PAD_R + 30`, 목적지 ±`ARC` 검사), §8.5(규칙 8 재정의 + 규칙 9 추가 + 경고 추가), §10.1~10.3(어디든 터치, 화면 이동 삭제), §12.3(발사대 행성, 흐르는 예측선), §16.5(4-1 폭 9.5°).

## 21. v4.1 → v5 변경 요약

### 왜 되돌렸나

v4는 "엔진이 카메라·UI·씬·익스포트를 대신해 준다"는 계산에서 나왔다. 실제로 만들어 보니 세 가지가 달랐다.

1. **엔진이 대신해 준 양이 예상보다 작았다.** 이 게임은 캔버스 하나에 선을 그리고 화면 네 개를 전환한다. 카메라(§11)는 60줄이고 화면 전환(§9.1)은 DOM 표시·숨김이다. 반대로 엔진 때문에 **새로 생긴** 제약이 있었다 — 32비트 `Vector2` 회피(v4 §2.1), 익스포트 필터 관리, `class_name` 해석 문제, dp 환산(v4 §10.0).
2. **화면을 볼 수 없었다.** 개발 환경에서 Godot 4를 구할 수 없어 **M2~M5 다섯 마일스톤을 한 번도 실행하지 않고** 작성했다. 코드는 늘었는데 확인된 것이 없는 상태가 쌓였다. 웹은 브라우저만 있으면 바로 뜬다. 이 경험이 §0.10과 §16.6이 된 이유다.
3. **웹 출시가 목표에 들어왔다.** 광고 수익이 목적이라면 설치 없이 링크로 도달하는 경로가 앱보다 먼저다. v4는 웹을 "개발 중 확인 수단"으로만 두었다(v4 §20).

성능은 반대 방향으로도 확인되었다. 검증 스캔이 Node에서 **17~80배 빠르다**(§8.9). v4에서 12시간으로 추산해 M8의 미결 과제로 남겼던 공전 단계 생성이 실용 범위에 들어왔다.

### 22.1 분사 (M14) — 완료

- **조작:** 비행 중 캔버스를 탭하면 우주선 → 탭 지점 방향(월드 좌표로 잰다)으로 꺾는다. HUD 버튼은 캔버스 위 DOM 이라 분사를 쓰지 않는다.
- **효과:** `applyTurn`(`src/core/simulate.ts`) — 속력은 두고 방향을 최대 `TURN_MAX`(40°, `constants.ts`)만큼 돌린다. ±180° 를 넘으면 가까운 쪽으로.
- **결정론:** 탭은 `Sim.queueTurn` 으로 줄을 세우고 **다음 스텝 경계에서만** 적용한다. 적용한 것은 `sim.turns` 에 `{ step, dir }` 로 남는다. `simulate(L, θ, ls, G, turns)` 가 같은 기록으로 한 비트도 다르지 않게 되풀이한다(`tests/turns.test.ts`). 한 스텝 안의 두 번째 탭은 버린다(횟수만 줄고 효과가 없으면 억울하다).
- **단계 데이터:** `turns: n`(없으면 0), 정답은 `meta.solution.turns`. 로더가 둘 다 검사한다. 검증기 규칙 7 이 정답을 분사 기록째 되풀이하고, 정답이 쓴 횟수가 `turns` 를 넘으면 실패로 본다.
- **HUD:** 왼쪽 위, 뒤로 버튼 바로 밑에 "분사 ■■□"(채운 칸 = 남은 횟수). 분사가 있는 단계에서만 보인다. 아래 가운데는 각도·힌트 판 자리라 피했다.
- **연출:** 쓴 자리에서 새 진행 방향 반대로 연기 네 덩이가 퍼지고, 탭한 곳에 반짝임, 로켓이 늘어났다 출렁인다(§12.7). 효과음 `boost`, 진동 15ms.
- **개발자용 숨은 옵션** (사용자 요청으로 배포 사이트에서도 켜진다. 화면에 안내하지 않고, 저장하지 않으므로 주소에서 빼면 꺼진다. `src/main.ts` 의 `PARAMS`):
  - `?turns=N` — 모든 단계에 분사를 N번(최대 9) 더 준다. 그 상태로 깬 단계는 평소처럼 클리어로 남는다.
  - `?open` — 모든 장·단계와 인피니티를 연다. 클리어 표시는 그대로다(`Progress.allOpen`).
  - 함께 쓸 수 있다: `?open&turns=3`.
  - 출시(M12) 전에 남길지 정한다. 지금은 누구든 주소를 알면 쓸 수 있다.
- 1~5장은 손대지 않았다 — 분사 없이 되풀이한 결과가 예전과 같음을 테스트가 묶는다.

### 22.2 6장 (M15) — 완료

**검증 규칙 추가** (`src/tools-shared/turns.ts`, `metrics.ts`). 단계에 `turns` 가 있으면:

| 규칙 | 내용 | 기준 |
|---|---|---|
| 10 | **분사 없이는 안 풀린다.** 걸을 수 있는 범위(±ARC) 안의 모든 각도를 분사 없이 날려 성공 폭 합계가 0 | 0° |
| 1 | 성공 폭은 **정답의 분사를 건 채** 잰다. 분사는 진행 방향 기준(왼쪽으로 40°)으로 다시 건다 — 각도를 틀면 그 순간의 진행 방향도 바뀌고, 사람은 "그때 왼쪽"을 탭하지 화면의 같은 점을 탭하지 않는다 | 2.5° 와 레시피 최소 |
| 11 | **분사 타이밍** — 정답을 포함한 연속 성공 폭 | 0.15초 이상 |
| 11 | **탭 방향** — 진행 방향 기준 0~179° 를 같은 쪽으로 훑은 연속 성공 폭. 40° 넘게 벗어난 탭은 모두 40° 꺾이므로 최대로 꺾는 정답은 옆쪽 어디를 탭해도 된다 | 20° 이상 |
| 2 | 우연한 성공은 **보지 않는다** — 다른 순간의 분사로 푸는 길은 그 단계의 자유다 | — |

- 범위 밖 각도를 세지 않는 이유: 게임은 조준을 걸을 수 있는 범위로 자른다(`clampArc`). 쏠 수 없는 각도의 성공은 지름길이 아니다.
- 난이도에 분사 항을 더한다: 한 번에 0.8, 타이밍 폭이 0.4초보다 좁으면 최대 1.0.
- `meta.metrics` 에 `turn_timing`·`turn_delta` 를 기록한다.

**생성기** (`generateTurnOne`, 레시피에 `"turns": 1`):
1. 배치는 보통 단계와 같다.
2. 걸을 수 있는 각도(1°)를 분사 없이 날려 칸마다 "분사 없이 닿는 갈래 수"를 센다. **행성만으로는 그늘이 생기지 않는다** — 인력이 행성 뒤로 궤적을 모은다(처음 만든 판은 모든 칸이 지워졌다). 그래서 적게 닿는 칸을 고르고, 남은 갈래는 소행성으로 막는다(6).
3. 각도(2°) × 순간(0.6초부터 0.1초 간격, 4초까지) × 왼쪽·오른쪽 최대 분사로 갈래를 날려 분사 뒤 궤적이 지나간 칸을 모은다. **0.6초 전 분사는 쓰지 않는다** — "범위 밖으로 쏘기"와 다르지 않다.
4. 각도 폭이 레시피 범위에 들고, 이웃한 순간(±0.1초)에도 닿는 칸을 목적지로.
5. 정답을 다듬는다: 타이밍 가운데 → 각도 가운데 → 타이밍 가운데. 절대 방향(`dir`)으로 기록한다.
6. 분사 없이 닿는 길(걸을 수 있는 범위 안)을 소행성으로 막는다. 정답 궤적에서 BLOCK_GAP 떨어진 곳에만.
7. 장식 소행성, 마지막은 §8.5 + 규칙 10·11.
- 측정: 한 후보에 2초쯤, 칸마다 시드 100개에서 후보 4~57개. 장 전체 160초(4스레드).

### 22.3 인피니티 (M16) — 완료

정한 수치(사용자가 바꿀 수 있다): **점수 = 버틴 시간(초)**, 최고 기록 저장. 분사는 처음 **2번**, 당근 아이템 하나에 +1, **최대 5**. **6-1 을 깨면** 타이틀의 인피니티가 열린다.

**우주** (`src/tools-shared/infinity.ts`, DOM 금지)
- 400×400 **칸** 단위. 칸의 내용은 판 시드와 칸 좌표만으로 정해진다 — 어느 순서로 불러도 같다(`makeChunk`). 한 판의 비행은 그 칸들 위에서 스테이지처럼 결정론적이다. 시드 난수는 칸을 만들 때만 쓴다.
- 칸을 2×2 작은 칸(200)으로 나눠 작은 칸마다 하나: 중력원 1~2, 나머지에 소행성·외계인·당근. 가운데에서 ±50 흔든다.
- **곧은 빈 길 금지:** 작은 칸 가운데만 쓰면 그 사이 경계선이 통로가 된다 — 재 보니 3000 유닛 넘게 아무것도 안 걸리는 직선이 있었다. 작은 칸 모서리 격자점에 작은 파편(r 9~14)을 둬서 끊었다. 직선 수천 개를 쏴 "중력 범위·소행성에 처음 걸리기까지의 거리"를 재면 **99% 가 900 유닛(6초) 안, 가장 긴 것도 2000 유닛 안**이다(`tests/infinity.test.ts` 가 지킨다). 완전한 0 은 아니다 — 무작위 배치라 아주 드물게 긴 직선이 남는다.
- **숨 고르는 출발 구간:** 출발점 둘레 260 은 비우고, ring 0~1(±600)은 파편·소행성을 성기게 둔다. 처음 시험에서 위로 곧게 쏘자 2초 만에 파편에 부딪혔다. 곧은 길 금지는 ring 2 부터 잰다.
- **멀어질수록:** ring 2 부터 블랙홀·공전 행성, ring 3 부터 외계인. 당근은 조금씩 드물어진다.
- **월드 원점 1,000,000:** core 의 벽 판정(0..w)을 그대로 쓰려고 출발점을 아주 멀리 둔다. 한쪽으로만 6000초 넘게 날아야 벽이다.
- **공정성 측정:** 무작위 판 100개에서 분사 없이 가장 좋은 발사각만 골라도 중앙값 13.8초, 90% 가 10.6초 이상 버틴다. 아무 데나 위로 쏘면 중앙값 5.3초 — 조준이 의미가 있다.

**창과 물리**
- 우주선 둘레 5×5 칸만 `Level` 의 배열(창)에 올린다. 우주선이 칸을 넘으면 그 스텝 경계에서 배열을 갈아 끼우고 `Sim.refreshBodies()` 가 중력원 목록을 다시 묶는다. 가장 먼 중력 범위(190)도 창 밖에서는 우주선에 닿지 않는다.
- **외계인 사격 시각은 객체끼리 잇는다** — 사격 시각이 배열 순번으로 저장되어 있어, 창이 바뀌면 같은 외계인을 찾아 시각을 옮긴다. 새로 들어온 외계인은 지금부터 delay 초 뒤 첫 사격.
- `Sim.endless` 로 30초 표류 제한을 끈다.
- 당근은 우주선 중심 16 안에 들어오면 먹는다. 먹은 것은 창을 다시 열어도 돌아오지 않는다.
- **같은 시드·같은 발사면 창을 갈아 끼우며 날아도 결과가 같다**(테스트).

**화면**
- HUD: 단계 이름 자리에 버틴 시간과 최고 기록, 왼쪽 위 분사 칸 5개. 힌트 버튼은 없다. 미니맵도 없다(끝없는 맵).
- 끝: "여기까지 버텼어요 · n초 · 최고 m초", 최고 기록이면 한 줄 더. 다시 시도는 언제나 **새 판**(새 시드). 두 번째 버튼·뒤로는 타이틀.
- 처음 열면 소개 카드 "인피니티"(당근 그림). 단계에 붙지 않는 **모드 카드**다(`MODE_KEYS`).
- 그림: 창이 바뀌면 배열 순서가 바뀌므로 천체 스프라이트와 출렁임 용수철을 순번이 아니라 **성질·객체로** 찾는다. 화면 밖 물체는 그리지 않는다. 창에 천체 160여 개가 있어도 60fps(헤드리스 측정).
- 인피니티의 판은 단계 기록·광고 횟수에 넣지 않는다. 실패 후 보상형 광고로 이어하기는 아직 없다(§14 와 함께 검토).
- 궤도 행성(M17)을 칸에 더했다(§22.4). 점수는 링에서 쉰 시간을 뺀다.
- **오늘의 우주**(코드 검토 3, 사용자 결정 2026-10): 타이틀의 [인피니티]는 고르기 판을 띄운다 — **오늘의 우주**(날짜가 시드, `src/tools-shared/daily.ts`)와 **무작위 우주**(매번 새 시드). 날짜는 기기의 현지 날짜 `YYYY-MM-DD` → FNV-1a 시드. 서버 없이 "친구와 같은 판" 경쟁이 생긴다. 오늘 기록은 `save.infinity.daily {day, best, runs}` 에 두고 날짜가 바뀌면 비운다. HUD·결과는 "오늘 최고" 로 적고, 전체 최고(`infinity.best`)는 어느 우주든 센다. 다시 시도는 같은 모드.
- **공유**: 결과 시트의 [공유] — `navigator.share` 가 있으면 공유 시트(폰), 없으면 클립보드에 "스윙바이 오늘의 우주 10/6 — 13.5초 버텼어요" + 주소. 주소는 `shareUrl()` — itch.io 빌드는 iframe 안의 CDN 주소라 붙이지 않는다. 문구는 사전(네 언어).

### 22.4 궤도 행성 · 7장 (M17) — 완료

**물리** (`src/core/simulate.ts`, 단계 데이터 `docks: [{ x, y, r, cr, sides }]`, 정답 `meta.solution.releases: [스텝]`)
- 중심에서 `cr` 안에 들어오면 **붙잡힌다**. 들어온 쪽으로 돌고, 속력은 지킨다. 중력은 없다.
- **한 바퀴 6초로 고정**(`DOCK_LAP`). 비행 속력(150) 그대로 링(r 50)을 돌면 초당 170° 가 넘어 탭으로 노릴 수 없다.
- **탭하면 다음 스텝 경계에서 그 자리의 접선으로 나간다.** 분사는 쓰지 않는다. 탭한 스텝을 `releases` 에 남기고 그대로 되풀이한다(결정론).
- **두 바퀴(12초)가 지나면 저절로 나간다**(`DOCK_HOLD_LAPS`). 저절로 나간 것은 기록하지 않는다 — 기록 없이도 똑같이 재현된다.
- 나온 링은 6 유닛 멀어질 때까지 다시 붙잡지 않는다. 링 안 몸체(r)에 닿으면 행성 충돌.
- **도는 시간은 30초 표류 시계에서 뺀다**(`dockedSteps`). 총알은 도는 동안에도 맞는다.
- 조준 예측선은 링에 닿으면 끝난다(거기서 붙잡히므로). 도는 동안에는 "지금 나가면" 예측선(`predictRelease`)을 그린다.

**검증 규칙** (`src/tools-shared/docks.ts`, `metrics.ts`). 사람은 시각이 아니라 **자리**를 보고 탭한다 — 로켓이 굴 쪽을 향하는 순간. 그래서 여유를 잴 때 나가기를 **링 위 각도 φ** 로 다시 건다.

| 규칙 | 내용 | 기준 |
|---|---|---|
| 12 | **탭으로 나가지 않으면 안 풀린다** — 걸을 수 있는 범위 안 모든 각도를 탭 없이(지나치거나 두 바퀴 뒤 저절로 나가서) 날려 성공 폭 합계가 0 | 0° |
| 1 | 성공 폭은 나가기를 같은 φ 에 건 채 잰 발사 각도 폭 | 2.5° 와 레시피 최소 |
| 13 | **나가기 타이밍** — 정답 φ 를 포함한 연속 성공 폭을 초로(60°/초) | 0.15초 이상 |
| 2 | 우연한 성공은 보지 않는다(분사 단계와 같은 이유) | — |

- 난이도에 나가기 항: 한 번에 0.6, 타이밍 폭이 0.4초보다 좁으면 최대 1.0. `meta.metrics.release_timing`.

**생성기** (`generateDockOne`, 레시피 `"docks": 1`): 궤도 행성을 출발점과 목적지 영역 사이에 → 탭 없이 닿는 칸 수와 붙잡히는 각도를 센다 → 가장 넓게 붙잡히는 각도로 쏘고 φ 를 3° 간격으로 훑어 나간 뒤 궤적의 칸을 모은다 → φ 폭 12°(0.2초) 이상이고 탭 없이 닿는 갈래가 적은 칸을 목적지로 → 남은 지름길은 소행성으로 막는다. 붙잡힌 뒤의 길은 발사 각도와 상관없이 φ 와 도는 방향으로만 정해져서 분사 단계보다 빠르다(한 후보 1초 안, 장 전체 69초).

**7장 "궤도 행성"** — 8칸 모두 궤도 행성 하나. 처음 배우는 장이라 앞쪽은 나가기 여유가 넉넉한 것(0.5~0.6초)으로 골랐다. 이름·힌트는 정답 궤적을 그려 보고 맞췄다(7-2·7-3·7-8 은 처음 지은 힌트가 실제 길과 달라 고쳤다).

## 부록 A. 물리 참조 구현 (검증 완료, JavaScript)

**이것이 정답의 기준이다.** `src/core/`의 TypeScript는 이 코드의 로직과 연산 순서를 그대로 옮긴 것이다. 둘이 다르면 **이 코드가 옳다.** 실행 가능한 사본이 `docs/reference/sim.js`에 있다.

```js
// ===== 결정론적 물리 코어 (게임과 검증기에서 공용) =====
const DT = 1/240;
const SHIP_R = 5;
const MAX_FLIGHT = 30;

function dist(ax,ay,bx,by){ const dx=ax-bx, dy=ay-by; return Math.sqrt(dx*dx+dy*dy); }
function bodyPos(b, t){
  if(!b.orbit) return [b.x, b.y];
  const o = b.orbit, a = o.phase + 2*Math.PI*t/o.period;
  return [o.cx + o.rad*Math.cos(a), o.cy + o.rad*Math.sin(a)];
}
function gravs(L){ return (L.planets||[]).concat(L.holes||[]); }
function accel(G, x, y, t){
  let ax=0, ay=0;
  for(const b of G){
    const [bx,by] = bodyPos(b,t);
    const dx=bx-x, dy=by-y, r2=dx*dx+dy*dy, R2=b.R*b.R;
    if(r2>=R2 || r2<1) continue;
    const r=Math.sqrt(r2), f=1-r/b.R, m=b.g*f*f;
    ax+=m*dx/r; ay+=m*dy/r;
  }
  return [ax,ay];
}
// 우주선 1스텝 + 충돌 판정 (총알 제외). 반환: null=계속, 문자열=결과
function stepShip(L, G, s, t){
  const [ax,ay]=accel(G,s.x,s.y,t);
  s.vx+=ax*DT; s.vy+=ay*DT; s.x+=s.vx*DT; s.y+=s.vy*DT;
  const tt=t+DT;
  for(const p of (L.planets||[])){ const [px,py]=bodyPos(p,tt); if(dist(px,py,s.x,s.y)<p.r+SHIP_R) return 'planet'; }
  for(const h of (L.holes||[])){ if(dist(h.x,h.y,s.x,s.y)<h.rH+2) return 'hole'; }
  for(const a of (L.rocks||[])){ if(dist(a.x,a.y,s.x,s.y)<a.r*0.85+SHIP_R) return 'rock'; }
  for(const u of (L.ufos||[])){ if(dist(u.x,u.y,s.x,s.y)<13+SHIP_R) return 'ufo'; }
  if(s.x<SHIP_R||s.y<SHIP_R||s.x>L.w-SHIP_R||s.y>L.h-SHIP_R) return 'wall';
  if(dist(L.goal.x,L.goal.y,s.x,s.y)<L.goal.r) return 'win';
  return null;
}
function fireUfos(L, st, ship, ft){
  for(const u of (L.ufos||[])){
    if(u._next===undefined) u._next=u.delay;
    while(ft>=u._next){
      const dx=ship.x-u.x, dy=ship.y-u.y, d=Math.sqrt(dx*dx+dy*dy);
      if(d<u.range) st.bullets.push({x:u.x,y:u.y,vx:dx/d*u.bs,vy:dy/d*u.bs,age:0});
      u._next+=u.interval;
    }
  }
}
function stepBullets(L, st, ship){
  for(const b of st.bullets){ b.x+=b.vx*DT; b.y+=b.vy*DT; b.age+=DT; }
  st.bullets=st.bullets.filter(b=>b.age<5&&b.x>-20&&b.y>-20&&b.x<L.w+20&&b.y<L.h+20);
  for(const b of st.bullets){ if(dist(b.x,b.y,ship.x,ship.y)<3+SHIP_R) return 'shot'; }
  return null;
}
// 전체 비행 시뮬레이션 (검증용)
function simulate(L, angleDeg, launchStep){
  const G=gravs(L);
  for(const u of (L.ufos||[])) delete u._next;
  const a=angleDeg*Math.PI/180;
  const s={x:L.start.x,y:L.start.y,vx:Math.cos(a)*L.speed,vy:Math.sin(a)*L.speed};
  const st={bullets:[]};
  let t=launchStep*DT, n=0, maxN=MAX_FLIGHT/DT;
  while(n<maxN){
    const r=stepShip(L,G,s,t); t+=DT; n++;
    if(r) return r;
    fireUfos(L,st,s,n*DT);
    const rb=stepBullets(L,st,s); if(rb) return rb;
  }
  return 'drift';
}
if(typeof module!=='undefined') module.exports={DT,SHIP_R,MAX_FLIGHT,bodyPos,gravs,accel,stepShip,fireUfos,stepBullets,simulate};
```

## 부록 C. 검증 스크립트 참조 (Node)

**v4에서 실제로 실행해 §6.2의 성공 구간을 모두 재현했다.** 결과는 §6.2의 실측 표에 기록했다.

이 스크립트는 v4 이후에도 남겨 둘 가치가 있다. M1에서 GDScript `solve` 결과가 §6.2와 어긋날 때, 이 Node 구현과 값을 단계별로 비교하면 정밀도 문제(§2.1)인지 연산 순서 문제(§5.4)인지 빠르게 가려낼 수 있다. `docs/reference/`에 `sim.js`, `levels.js`, `check.js`로 보관한다.

```js
const S = require('./sim.js');
const LEVELS = require('./levels.js');
const which = process.argv[2] !== undefined ? [parseInt(process.argv[2]) - 1] : LEVELS.map((_, i) => i);
for (const i of which) {
  const L = LEVELS[i];
  const orbiting = (L.planets || []).find(p => p.orbit);
  const launches = orbiting
    ? Array.from({ length: 12 }, (_, k) => Math.round(k * Math.abs(orbiting.orbit.period) / 12 / S.DT))
    : [0];
  for (const ls of launches) {
    const counts = {}, wins = [];
    for (let a = -180; a < 180; a += 0.25) {
      const r = S.simulate(L, a, ls);
      counts[r] = (counts[r] || 0) + 1;
      if (r === 'win') wins.push(a);
    }
    const runs = [];
    for (const a of wins) {
      const last = runs[runs.length - 1];
      if (last && Math.abs(a - last[1] - 0.25) < 1e-6) last[1] = a; else runs.push([a, a]);
    }
    const txt = runs.map(([s, e]) => `${s}..${e} (${(e - s + 0.25).toFixed(2)}°)`).join(' ');
    console.log(`L${i + 1} ${L.name}  t=${(ls * S.DT).toFixed(2)}  성공: ${txt || '없음'}  ${JSON.stringify(counts)}`);
  }
}
```
